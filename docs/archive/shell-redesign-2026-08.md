## 12. ★my-brainをデータベースとして再設計・タスクの付随提案(AIエージェント化)(2026-08-02)

§11の続き。ユーザーの指示は2つあった。

> 見えていなかったような、タスクに付随するタスクなどもAIエージェントとして
> 提案して欲しい。私は非常に物忘れが多かったり、気が利かなかったり、計画を
> あらかじめ立てるのが面倒だったり、と言った性質があります。例えば、旅行に
> 行くというタスクを登録した時に(した後でも)、新幹線はとった？とか、朝何時に
> 出るか確認した？とか。会議をするというタスクなら、会議室は取ったか？とか、
> リマインドメールはしたかとか。

> my-brainにまとめますが、ちゃんとデータベースとして構造を考えて欲しい。謎に
> たくさんファイルが乱立していくのではなく、今後それらが増減しても対応できる
> ようにデータを整理して欲しい。

土台に2つ問題があった。(1)my-brainが15ファイルもルート直下と `logs/` `inbox/`
`journal/` に散らばり、命名も主題(taste/sources/goals)と所有者(-user/-proposed/
-stats)と日付が混ざっていた。(2)`Task` が id/title/dueDate/done/note だけで、
提案を出す器そのものが無かった。A(構造)→B(タスク)→C(Coworkのプロンプト)の順で
解いた。

### 12.1 my-brainの構造: 「役割 × 日付」の2軸

**恒久的なものは主題ごとに1ファイル、日付で増えるものは `days/YYYY-MM/` の中だけ**
(種類は4つに固定・これ以上増やさない)。月フォルダを開けばその月のすべてが揃う。

```
my-brain/
  README.md                 地図と規約(人が読む)
  me/taste.md               興味・好み・関連キーワード・生活圏・願い・ゴールに効くキーワード
  me/patterns.md            ★新: 手配漏れ・物忘れ・後回しの傾向(毎晩の仕分けが育てる)
  me/goals.md               ゴールとチェックインの記録
  days/YYYY-MM/facts.md     その日の事実(アプリ)
  days/YYYY-MM/voice.md     声のメモの文字起こし(アプリ)
  days/YYYY-MM/summary.md   その日のまとめ＝自動生成の日記(Cowork)
  days/YYYY-MM/feedback.md  カードへの反応ログ(アプリ)
  inbox/candidates.md       タスク・ウィッシュの候補(Coworkが書き、アプリが取り込む)
  sources/list.md / stats.md / proposed.md / dismissed.md
  analysis/taste.md         嗜好の分析レポート(Cowork週次・人が読む)
  cowork/rejected.md        審査で不合格にしたサイト(発掘タスク所有・移行対象外)
```

旧→新の対応(移行はCoworkに一度だけ実行させる。プロンプトは
`COWORK-ROUTINES.md` §「① 一度だけの移行タスク」):

`goals.md`→`me/goals.md` / `sources.md`→`sources/list.md` /
`source-stats.md`→`sources/stats.md` / `sources-proposed.md`→`sources/proposed.md` /
`sources-user.md`→`sources/dismissed.md` /
`logs/feedback-YYYY-MM.md`→`days/YYYY-MM/feedback.md` /
`inbox/voice-YYYY-MM.md`→`days/YYYY-MM/voice.md` /
`journal/YYYY-MM.md`→`days/YYYY-MM/facts.md` /
`journal/summary-YYYY-MM.md`→`days/YYYY-MM/summary.md`。
`profile.md`・`inbox/journal-*.md` は廃止(未使用)。

**規約**: 各ファイルの先頭の front-matter に `owner: app | cowork | human` を書き、

### 12.2 タスクの付随提案(commit `22fd72d`)

**データモデル(`lib/types.ts`)**: `SubTask{id,title,done,doneAt?,fromSuggestion?}` /
`TaskSuggestion{id,title,why?}` / `Task.subtasks?/suggestions?/suggestedAt?`
(`suggestedAt` が未設定なら「まだ提案を作っていない」)。

**生成(`lib/taskSuggest.ts` + `app/api/suggest-subtasks/route.ts`)**: 材料は3つ——
タスク本体 / `me/patterns.md` の傾向(Coworkが育てる) / **過去に済ませた似たタスクと
その手順**。モデルは `gemini-flash-lite-latest`(`callGemini` を再利用・JSONモード)。
**AIが出すのは文面だけで、件数の上限(6)・既存との重複・空・長すぎの排除はコード側で
切る**(briefPipelineと同じ分担)。プロンプトはユーザー承認済みで、要点は
「タスクに書かれていない固有名を作らない(ただし『新幹線』『会議室』のような、その
タスクなら誰でも思いつく一般的な手配は書いてよい)」「その場で済んだ/まだを答えられる
粒度」「タスク本体そのものは書かない」「傾向に当たるものを先に置く」。

**★似たタスクの探し方**: 文字の2-gramの **Jaccard係数**(しきい値0.3)で測る。
最初は「一致した2-gramの数」で書いたところ、「歯医者に行く」と「金沢へ旅行に行く」が
**「に行く」という助詞まじりの共通部分だけで似ている**ことになってしまい、無関係な
過去タスクの手順を提案の材料に渡していた。両方の長さで割った比率にして解決
(`similarity`/`findSimilarTasks`)。

**画面(`components/TaskDetail.tsx`)**: 中央にタスク(題は直接編集)、その周りに提案が
ふわふわ漂う。タップ=採用してサブタスクへ、×=却下。下にサブタスクのチェックリスト
(チェック・削除・手で追加)、「ほかの手配も見る」で作り直し。漂う表現はインボックスと
共通化した(`components/FloatingBubble.tsx` の `floatStyle(id,index,total)` +
CSSの `inbox-drift`。位置と揺れはidのハッシュから決まるので再描画で飛び回らない)。
`TasksTab` の行はタップで開き、行自体にも `手順 2/5` と未確認の提案数(GOLDの✨バッジ)を
出す。提案を頼むのは(1)インボックスで候補を承認した直後、(2)タスクを開いたとき
`suggestedAt` が無ければその場で、(3)「ほかの手配も見る」。

単体テスト17項目PASS。Chromiumで、タスクを開く→提案が漂う→タップで採用→サブタスクに
入る→チェック→リロードしても残る、承認直後に提案が作られる、を確認
(この環境に `GEMINI_API_KEY` は無いのでAPIはスタブして経路を確認した。
**実キーでの提案の質は本番デプロイでユーザーが確認する**)。

- 図形の語彙は新設せず、バインダーの`PlaneShape`/`PlaneFill`をそのまま借りる
  (そのため`Binder.tsx`の`PlaneFill`を export した)。置き場所もバインダーが
  「帯の位置で種別を分ける」のと同じ考え: タスク=左上の四半円(side) /
  ブリーフ=右上の円(target) / ジャーナル=下端の半円(stamp)。定義は`lib/apps.ts`の

- 色は`SHADE`1色だけ。地との明度差しか持たない。
- **視差の掛け方には落とし穴がある**: 初版は`(-index + dragRatio)`全体に
  PARALLAX(0.55)を掛けたため、静止時に別のアプリの図形が画面に居座った。
  正しくは**図形どうしの間隔だけ**に掛ける(`(i - index + dragRatio) * PARALLAX`)。
  これで`i === index`のとき必ず0になり、静止時は自分の図形がちょうど収まる。
- 間隔を1画面ぶんより狭くした副作用で隣の図形が端からはみ出すため、
  中心からの距離で溶暗させる(`opacity = 1 - |d|`)。視差と溶暗の重ね。

## 14. ★ネオバウハウス化 第2弾: 性能の回帰を断つ・背景をバインダーの構図へ・
ダッシュボードを操作しやすく(2026-08-02続報)

§13を実機(iPhone)で確認したユーザーからの報告に対応した。とりわけ

> 重大な問題として、タブの切り替えが非常に重く、タップしてもタブが切り替わらない
> 問題が起きています。また、ストックタブのカードが非常に動作が重いです。

は**§13で私が入れた回帰**だった。原因を3つとも特定して直した。

### 14.1 ★性能の回帰(最優先)

**測り方**: `PerformanceObserver`で`longtask`(50ms以上メインスレッドを塞いだ
処理)を拾い、実機に寄せるためCDPの`Emulation.setCPUThrottlingRate {rate:4}`で
CPUを4分の1に落として計測する。**必ず本番ビルド(`next start`)で測る**
(dev buildは桁違いに遅く、数字が意味を持たない)。

**原因1: タブをタップしただけで両隣のアプリがまるごとマウントされていた。**
§13の`onNavPointerDown`が`setNeighborsMounted(true)`を呼んでおり、指が触れた
瞬間にタスクとジャーナルのタブが丸ごと構築され、460ms後にまた捨てられていた。
横スワイプの出だしを軽くするつもりの先読みだったが、**ただのタップでも必ず
発火する**ため、実機では数百msメインスレッドが止まり「タップしても切り替わらない」
ように見えていた。
→ **一度マウントしたら二度と外さない**(`mountedApps: AppId[]`。増えるだけ)。
初回描画のあと`requestIdleCallback`(無ければ`setTimeout`)で残り2つを先読みする
ので、指が触れる頃には既に用意できている。マウント/アンマウントの往復自体が
無くなった。

**原因2: ドラッグ中、60fpsでReactが再レンダーされていた。**
`navDragX`/`dashP`をReact stateで持っていたため、指が動くたびに
**マウント済みの全アプリの全タブ**が再レンダーされていた。§13より前は1タブしか
マウントしていなかったので露見しなかった。
→ **CSSカスタムプロパティへ一本化**。ポインタハンドラはrAFで
`document.documentElement.style.setProperty("--drag", px+"px")`(と`--dash`)を
書くだけで、**ドラッグ中のReactのレンダーはゼロ回**になった。トラックは
`translateX(calc(var(--app-offset) + var(--drag)))`、ダッシュボードのピル・
シートは`--dash`(0〜1)から`calc()`で全部導く。
- **`@property`は使っていない**(Safari 16.4以降にしか無い)。トランジションは
  カスタムプロパティ自身ではなく、そこから導かれる**transform/width/height/
  opacity/bottom**の側に掛ける。この掛け方ならカスタムプロパティが
  アニメーション可能である必要が無く、古いSafariでも成立する。
- 状態は属性で持つ: `data-dragging` / `data-dash-dragging`(この間だけ
  transitionを切って指に1:1で追従させる) / `data-dash-active`(本物のnavを
  隠す)。どれもReactの再レンダーを伴わない。

**原因3: 再レンダーがタブへ伝播していた。**
→ 1アプリぶんの列を`AppColumn`として切り出し`React.memo`で包み、`tabProps`と
コールバック類を`useMemo`/`useCallback`化。`PosterCard`(`common.tsx`)も
`memo`で包んだ。ストックの棚に`content-visibility:auto` +
`contain-intrinsic-size`を入れ、画面外の棚を描かないようにした。

**★計測で見つかった本物のバグ**: 列のdivに`position:relative`が無く、
`AppBackdrop`の`inset:0`が**トラック(幅1170px)に対して**解決されていた。
帯が608x844 / 1170x354 / 1170x287という有り得ない大きさで描かれていた
(見た目では気づけない類の崩れ)。列に`position:relative`と`overflow:hidden`を
与えて解決(203x844 / 390x354 / 390x287)。

**結果(いずれも4倍スロットリング)**:

| 操作 | 修正前(dev) | 修正後(本番ビルド) |
|---|---|---|
| タブをタップ | longtask 1525ms / 1744ms | 484ms / 371ms / 65ms |
| 横スワイプ1回 | longtask 17件 3693ms | **0ms** |
| ストックを縦スクロール | 0ms | **0ms** |

**ストックに残っているコストは私の変更が原因ではない**。1枚あたりのコストを
枚数を変えて測ると 0枚:54ms / 8枚:332ms / 20枚:346ms / 40枚:427ms と**枚数に
比例しない**。CDPのProfilerで自己時間を取るとJSは約40ms(lucideのSVGを作る
`createElementNS`が42ms)しかなく、**`(program)`=832msがスタイル計算・
レイアウト・描画**だった。つまりカードの意匠そのもの(グラデーション＋ぼかした
box-shadow＋パンチ穴の内側影＋SVGアイコン)の描画コストで、§13以前から
あったもの。ユーザーが気に入っている見た目を削ることになるため、ここは
**意図的に手を止めた**。さらに軽くしたい場合は意匠の相談から始める必要がある。

### 14.2 背景をバインダーの表紙の構図へ(`AppBackdrop.tsx` / `lib/apps.ts`)

ユーザー指定「既存の図形的なモチーフとグリッドは守りなさい。特にアーカイブの
バインダーの表紙が良い例なのでそれを参考にしなさい」「色の話ではなく、図形の
モチーフやその配置で各アプリが違うことを表現して」に沿って作り直した。
構図は**バインダーの表紙とまったく同じ文法**:
**無地の下地 ＋ 帯(位置が識別) ＋ 帯の中の正方形セルに図形**。

| アプリ | バインダーの対応 | 帯 | 図形 |
|---|---|---|---|
| タスク | side(タイケン) | 左端の縦帯 40% | 四半円を縦に3つ |
| ブリーフ | geo(バショ) | 上端の帯 23% | 円を横に2つ |
| ジャーナル | stamp(モノ) | 下端の帯 26% | 半円を横に3つ |

- 色はグレー2段(帯`SHADE`/図形`SHADE_DEEP`)のみ。アクセント色は使わない。
- **★セルの一辺は「帯の短辺」と「帯の長辺÷個数」の小さい方**(`cellSide`)。
  短辺だけで決めると合計が長辺を超えて最後の1個が切れる。実際に一度そうなり、
  スクリーンショットで発覚した——**バインダーのタイケンで踏んだのと同じ轍**
  (§7.28)。列は必ず1画面ぶんなのでvw/svhでそのまま書ける。
- 交差方向は`flex-start`(帯の内側の縁に揃える)。下端の帯はこれで図形が
  タブバーに隠れず読める(帯自体は画面の下端まで伸ばす)。

**「スワイプすると画面外で図形が切れて見える」の構造的な解決**: §13は背景だけを
別のトラックにして視差でずらし、レイヤーごとに`overflow:hidden`していたため、
**切り取り線が画面の真ん中に来ていた**。背景を**各列の中**へ入れた。列は幅
ちょうど1画面・`overflow:hidden`なので、切り取り線は必ず画面の端と一致する=
画面の中で図形が切れることが構造的に起こらない。トラックのtransform1つで
背景も中身も同時に動くので、アプリ間の動きも繋がる。溶暗(opacity)は撤去し、
奥行きは`.app-backdrop-inner`を`--drag`の-0.16倍だけ遅らせて出す。

**「画面中央に小さい図形が残っている」**: §13で新設した`EmptyMark`(空状態に

## 15. ★背景をバインダーの grid2x2 の文法へ・タップハイライトと

> まだ動きが非常に不安定です。ジャーナルにスワイプするとUIが一瞬消えてバグります。

### 15.1 ★背景の文法を取り違えていた(grid2x2 が正)

指示どおり `components/Binder.tsx` のアクセント生成を読み直したところ、
**私が倣うべきだったのは `geo`(バショ)の `grid2x2`** だった:

```
正方形のブロック → 真の2x2の正方形セルに分割 → セルごとに
                    明度の段(TONE_STEPS)と図形(PLANE_SHAPES)を置く
```

`PLANE_SHAPES` は円・半円・四半円(扇形)に **triangleUp/triangleDown を含む**。
つまり「正方形のグリッドに三角や丸や扇形を配置」そのもの。ところが§14で作った
背景は `side`(タイケン)の文法 = **同じ図形ひとつを1列に並べる総柄**で、グリッドでも
なく三角も使っていなかった。系統から間違っていた。

**作り直し(`components/AppBackdrop.tsx` / `lib/apps.ts`)**: `AppSymbol` を
`{ anchor, cells }` にした。`cells` は2x2の4枚(左上・右上・左下・右下)で、各セルは
`{ bg, shape, fg }`、`null` なら下地のまま = グリッドに穴を空ける(バインダーの
`units` 構図が「図形入りのセル」と「無地の色面」を混ぜているのと同じ)。

| アプリ | ブロックの位置 | 図形の系統 |
|---|---|---|
| タスク | 上 | 扇形(quarterBR)・三角(triangleDown)・円 |
| ブリーフ | 中央 | 円・半円(semicircleDown)・扇形(quarterTL) |
| ジャーナル | 下 | 扇形(quarterTR/quarterBL)・三角(triangleUp) |

- ブロックは列の幅ちょうど(`width:100%; aspect-ratio:1/1`)で、それを grid で
  2x2に割るだけなので、**セルは常に「画面幅の半分」を1辺とする真の正方形**に
  なり、器からはみ出しようがない(§14の `min()` 計算そのものが不要になった)。
- 色はグレーの明度3段のみ。一度この幅を広げたら(pale +7 / deep -11)白に近い
  図形と濃い下地の組み合わせができ、**透かしではなく画面の主役になって本文が
  読めなくなった**ので、`{ pale: 1, mid: -4, deep: -9 }` へ締めた。

**★あわせて見つけた描画順のバグ**: 背景は `position:absolute; zIndex:0` だったが、
CSSの描画順では **位置指定のある z-index:0 の要素は、同じ親の中の「位置指定の
無い通常フローの中身」より後に描かれる**。つまり背景がタブの本文の上に乗って
おり、ブリーフの休刊見出しの2行目が実際に消えていた(スクリーンショットで発覚。
§14の帯の頃から起きていて、帯が画面の端にあったため気づけなかった)。列に
`isolation:isolate` を与えて独立した重なりの単位にし、背景を `zIndex:-1` へ
落とした(列の外へ抜け落ちる心配が無い)。

### 15.2 「四角い当たり判定が見える」

`app/globals.css` に `-webkit-tap-highlight-color` の指定が無く、iOS Safari が
タップした要素の**矩形**に半透明のグレーを重ねていた。タブバーのボタンは
`flex:1` の横長の箱なので、見えている丸いアイコンよりずっと大きい四角が
浮かび上がる。`html, body` に `-webkit-tap-highlight-color: transparent` を
足した(このプロパティは継承するので1箇所で全体に効く)。

### 15.3 「スワイプするとUIが一瞬消えてバグる」

まず**Chromiumでは再現しなかった**。当初疑った2点は測って否定している:
- 「`--drag`を0にした後に`--app-offset`がuseEffectで遅れて書かれ、1フレーム
  元の位置へ戻る」→ 離した直後を毎フレーム記録したが、初回フレームから
  既に新しいoffsetで、戻るフレームは無かった(Reactが同期でflushしている)。
- 「プリロードがpersistのたびにキャンセルされ、ジャーナルが未マウントのまま
  スワイプされて中身が空になる」→ 0.4秒おきに触り続けても3列とも
  マウント済みだった(`requestIdleCallback`のtimeoutが効いている)。

代わりに、**コード上に明確に存在する取りこぼしを2つ**見つけて直した。どちらも
「UIが消える」という症状と直接つながる。

1. **`pointercancel` が `--dash` を戻していなかった**(`AppShell.tsx`)。
   ダッシュボードを縦に引いている最中にiOSがポインタを取り上げると、
   `pointerup` が来ないので `settleDash` が呼ばれず、`--dash` が途中の値のまま
   残る。`[data-dash-active="1"] .app-nav { opacity: 0 }` が効いたままになるので
   **タブバーがそのまま消える**。さらに画面全体を覆うscrimも残る。iOSは画面端の
   ジェスチャー等で pointercancel を頻繁に投げる。`cancel` ハンドラを分け、
   縦に引きかけていたら必ず閉じ切るようにした。
2. **閉じている間のscrimがタップを飲んでいた**(`globals.css`)。scrimは
   `position:fixed; inset:0` で、`opacity:0` でも**タップは受け取る**。
   ダッシュボードを一度開いて閉じたあと、実際にアンマウントされるまでの
   340msの間ずっと下のUIへのタップを吸っていた(BottomSheetで同じ不具合を
   踏んだ記録が §7.7/§7.30 にある)。`[data-dash-active="0"] .dash-scrim` で
   `pointer-events:none` にし、あわせて `backdrop-filter` も切る(画面全体を
   覆うぼかしのレイヤーが生き続けると、アプリを横へスライドさせるtransformの
   たびに合成をやり直すことになるため)。

あわせて、`--drag` と `--app-offset` を**同じ同期の書き込みで揃える**ように
した(Chromiumでは症状が出なかったが、片方だけ先に反映される余地を構造的に
残さないため)。

## 16. ★背景を「グリッドが割れる／まとまる」構造へ作り直し(2026-08-03)

§15までの背景は何度作り直しても「秩序なく図形が置かれている」と却下された。
ユーザーから参考動画2本(Pinterest)と、寸法まで踏み込んだ指定が出て決着した。

### 16.1 指定された3つの並べ方

| アプリ | グリッド | 図形 |
|---|---|---|
| ブリーフ | **画面幅いっぱい(100vw)を1辺とする正方形**を画面中心から上下へ展開 | 各マスに内接する正円。上下ははみ出して切れてよい |
| タスク | 上を**四分割した細かいグリッド(1辺 25vw)** | 画面左の一列だけに「左下が角の扇形」。他は空 |
| ジャーナル | タスクと同じ細かいグリッド | **すべてのマス**に円 |

地は BG(グレー)のまま、**図形のあるところだけがそれより薄い**1色。明度は2値。

参考動画Bが決め手だった: 2x2の扇形のグリッドが4x4へ**細分化していく**動き。
つまり3つの並べ方は別々の絵ではなく、**同じグリッドの粗さが違うだけ**で、
アプリ間の遷移はその細分化/統合そのもの、という構造だと判明した。

### 16.2 実装(`components/AppBackdrop.tsx` / `lib/apps.ts`)

DOMは常に「細かいマス」1枚 = div 1つ。**4列 x 10行 = 40枚**しか無く、3つの
並べ方は同じ40枚の置き方が違うだけ:

- タスク    … 左の列(10枚)だけ等倍、他は大きさ0
- ジャーナル… 40枚すべてが等倍の円
- ブリーフ  … 各マスが自分の属する大きな円の中心へ寄る。**円を実際に描くのは
              その組の代表1枚だけ**が4倍に育ち、残りは吸い込まれながら消える

**★代表1枚に絞ったのは性能のため。** 最初は16枚すべてを4倍に育てて重ねて
いた(重なるので見た目は同じ1つの円)。ところが 390px の円を40枚ぶん塗ることに
なり、4倍スロットリングでの**横スワイプの long task が 0ms → 287ms** へ増えた
(§14で潰したはずの回帰を自分で再導入していた)。代表1枚にすると塗りは3枚ぶんで
済み、**0ms へ戻った**。見た目も「小さい円が吸い込まれて大きな円が生まれる」と
なり、細分化の逆再生としてむしろはっきりした。

### 16.3 ★動かすのは transform と border-radius だけ

各マスは **固定位置・固定サイズ(25vw角)の箱**で、`top/left/width/height` には
一切触らない。変わるのは:

- `transform: translate(...) scale(...)` … 位置と大きさ
- `border-radius`(**%指定**)          … 円 50% / 扇形 `0 100% 0 0` / 角 0

マスが常に正方形なので、拡大しても円が楕円に潰れない(%の角丸が拡大に正しく
追従する)。そして **transform はレイアウトを起こさない**ので、40枚あっても
毎フレームの再レイアウトが発生しない。三角形(clip-path)は border-radius と
補間できないため背景では使わない(バインダーの表紙では従来どおり使う)。

### 16.4 進み具合は連続値ひとつ(--p)だけ

```
--appi  … いま何番目のアプリか(整数)      AppShell が書く
--dragn … 指の移動量 ÷ 画面幅              AppShell が書く
--p     … calc(var(--appi) - var(--dragn)) 0=タスク 1=ブリーフ 2=ジャーナル
--t1    … clamp(0, --p, 1)                 タスク→ブリーフ の進み
--t2    … clamp(0, --p - 1, 1)             ブリーフ→ジャーナル の進み
```

各マスの transform / border-radius は `v0 + (v1-v0)*t1 + (v2-v1)*t2` という
1本の calc() で書いてある。**JSは毎フレーム何も計算せず、Reactのレンダーも
1回も走らない。** 指を離した瞬間は --p が目的地へ飛ぶが、`.app-backdrop-cell`
の transition(520ms)が追いつかせる。ドラッグ中は `[data-dragging="1"]` で
transition を切ってあるので指に1:1で追従する。

`--p` は CSSカスタムプロパティなので @property 無しには補間できない。だから
**補間するのは常に「そこから導かれた transform / border-radius」の側**という、
このコードベースで一貫している方針(§14.1)をここでも守っている。

## 17. 背景の動きをグリッドに沿わせる・グレーを強く・タブ手前の帯を直す(2026-08-03続報)

§16を実機で見たユーザーから3点。

### 17.1 ★「アニメーションがグリッドと無関係すぎる」

§16は、まとまる先の**中心へ translate でマスを寄せて**いた。40個の図形が画面を
斜めに飛び回るので、グリッドとの関係が全く読めなかった。

**マスを一度も動かさない設計に変えた。** 変わるのは大きさ(と角の丸め方)だけで、
`transform-origin` を左上に置いてあるため、伸縮するのは右辺と下辺
＝**グリッドの境目そのもの**。粗いマスの左上にあたるマスが右下へ伸びて4倍の
マスに育ち、その内側にいた他のマスは自分の左上へ畳まれて消える。つまり
「境目が滑って4つのマスが1つのマスにまとまり、そのマスに沿って円が現れる」。

あわせて**2つのグリッドの境目を完全に一致させた**: 細かいグリッドの行数を
粗いグリッドのちょうど4倍(`ROWS = BIG_ROWS * BIG` = 12行)にしてある。どちらも
画面中心を軸に上下へ展開するので、この関係のときだけ細かい4x4マスがちょうど
粗い1マスに収まる。ずれていると、育つ途中でマスがグリッドから外れて見える。

副産物として `translate` が消え、`transform: scale()` だけになった。§16で
「16枚を重ねると塗りが膨らむ」ために入れた代表1枚の工夫も、そのまま活きている
(粗いマスの左上の1枚だけが育つ)。

### 17.2 グレーを強く

地を BG そのままにせず、背景だけ `shade(BG, -4)` の少し濃いグレーにし、図形を
`shade(BG, 3)` の薄い色にした。地と図形の差は 10 → 18 になり、パターンが
はっきりする。**BG 自体は変えていない**(アプリ全体の地色なので)。

### 17.3 ★タブ手前の帯が背景を切っていた

nav の手前にあった帯は「透明→BG へのグラデーション」で、**不透明な BG を
塗りつぶして**いた。背景が無地だった頃は問題なかったが、パターンになった
いまはその帯が円を横一直線に切り取り、しかも塗る色(BG)が背景の地の色と違う
ため、タブバーの上にはっきり継ぎ目が出ていた(切り抜き画像で確認)。

色を塗るのをやめ、**背後をぼかすだけ**に変えた(`backdrop-filter: blur(12px)` +
下へ向かって効きを強めるマスク)。ぼけるのはその上を流れるタブの中身だけで、
背景のパターンはそのまま透ける(パターンはトラックの外＝別レイヤーにあるため
backdrop-filter の対象に入らない)。実測でも、帯の位置のピクセルが図形の色
(248)のままで、BG(240)のベタ塗りが乗っていないことを確認した。

`npx tsc --noEmit` / `npx eslint .`(既知の`<img>`警告3件のみ) / `npm run build`

**WebKit実機での最終確認は引き続き必須**(特に backdrop-filter は Safari で

## 18. アプリを一周ループに・タブ切替とロード画面のアニメーション(2026-08-03続報)

### 18.1 並びと一周ループ

APPS の並びを左から **ジャーナル / タスク / ブリーフ** に変更し、右端からさらに
右へ払うと先頭へ**回り込む**ようにした。

- 位置は 0〜2 に丸めない**通し番号 `pos`** で持つ(`AppShell`)。丸めると端で
  位置が飛び、ループのアニメーションが繋がらない。トラックの `--app-offset` は
  この通し番号から出す(-66.7% → -100% → -133% … と単調に伸びていく)。
- 列は増やさない。代わりに各列へ `translateX(±300%)` を掛けて、いまの位置から
  見て「いちばん近い、同じ余りの場所」へ置き直す(`wrapOf`)。これでどちらの
  向きへ払っても必ず隣に列がいる。値が変わるのはアプリが切り替わった瞬間だけ
  なので、ドラッグ中は静止している。
- 端のゴム(EDGE_RESIST)は不要になったので撤去。
- 背景の補間も輪にした。**0〜3 の3区間**(0=ジャーナル 1=タスク 2=ブリーフ
  3=またジャーナル)で一周ぶんを覆い、横へ払う向きが決まった瞬間に `--appi` を
  その範囲へ収まるよう選び直す(左へ払うなら 0〜2、右へ払うなら 1〜3 が基準)。

### 18.2 タブを切り替えたときのアニメーション

1. **選択中の印が滑る**。以前は各ボタンの背景を出し入れしていたので、黒い枠が
   「消えて別の場所に現れる」だけだった。印を1枚だけ置いて隣のタブへ 320ms で
   滑らせる(実測 x=22→93→164→235)。
2. **中身が少し下から起き上がる**(`globals.css` の `tab-in`、260ms)。
   ★これは以前わざと廃止した経緯がある: opacity/transform をアニメーション
   する要素が新しい重なりコンテキストを作り、内側の `zIndex:26`(ブリーフの
   育成カードのフッター)が nav 手前の帯(`zIndex:15`)より手前に出せなくなる。
   いまは**そのフッターを持つブリーフタブだけ**枠自体に `zIndex:16` を与えて
   帯より手前へ出している。ブリーフは中身をスクロールしない(`scrollLocked`)
   ので、帯のぼかしが効かなくなっても失うものが無い。他のタブは従来どおり
   帯の下に潜り、ぼかしが正しく効く。

### 18.3 ロード画面

文字と「図形が転がる」演出を廃止し、**2x2 のグリッドの中で黒い幾何学が
切り替わり続ける**アニメーションにした(`load-cell`)。背景と同じ語彙で、
角の丸め方だけを動かして円・半円・四半円・正方形を行き来する。4マスに
開始をずらしてあるので組み合わせが絶えず変わる。

### 18.4 ★性能: 一度 1034ms まで悪化させ、`contain` で戻した

4倍スロットリング・本番ビルドでの横スワイプの long task:

| 状態 | 合計 |
|---|---|
| §17 の時点 | 55ms |
| 今回の変更を入れた直後 | **1034ms** |
| 補間の区間を5→3に、48枚の calc を3クラスへ畳む | 506ms |
| `.app-backdrop-cell` に `contain: layout paint style` | **157ms** |

- 最初に疑った「calc() が複雑すぎる」は**外れ**だった(3区間へ減らしても
  変わらなかった)。切り分けのため折り返しの transform を一時的に外して測ると
  506→247ms になり、**折り返しの transform でおよそ半分**と分かった。
- 効いたのは `contain`。背景のマスは中身を持たない色面で、外のレイアウトにも
  描画にも影響しないと宣言すると、48枚ぶんの再計算をブラウザが切り詰められる。
- 残る 157ms は 3フレーム × 約52ms(実機換算で1フレーム十数ms)。1ジェスチャー
  あたりなので許容と判断したが、実機で重ければ最初に外す候補は
  **nav 手前の帯の backdrop-filter**(§17.3、単体で約55ms)。

### 18.5 検証

`npx tsc --noEmit` / `npx eslint .`(既知の`<img>`警告3件のみ) / `npm run build`
通過。Chromium(390x844)で:
- 一周ループ: 左へ4回で ブリーフ→ジャーナル→タスク→ブリーフ→ジャーナル、
  右へ4回で逆順に戻ることを確認。`--app-offset` が -66.7% → -200% と単調に
  伸び、`--appi` は 2→0→1→2→0 と丸められていることを実測。

**WebKit実機での最終確認は引き続き必須。**

## 19. タブバー: ブラーの隙間・印の縦ズレを直し、アイコンを面の幾何学へ描き直す(2026-08-03続報)

実機のスクリーンショット(IMG_1651.PNG)とともに4点の指摘。

### 19.1 ★ブラーが効かない帯・UIが途切れて見える

nav 手前のぼかしの帯(§17.3)は、スクロールルート(`data-tab-scroll-root`)の
**中**に置かれており、その左右16pxの padding の内側にしか広がっていなかった。
つまり画面の左右16pxだけ素通しで、しかも帯の左右の端が硬い直線なので、
そこで背景と中身の見え方が食い違い「一定範囲だけブラーがかからない・UIが
不自然に途切れる」ように見えていた。padding を打ち消して
`left:-16, right:-16` にし、硬い端を画面の外へ追い出した。実測で帯が
x=-16 幅=422(=画面の0〜390を完全に覆う)であることを確認。

### 19.2 ★選択中の印が縦にズレていた

以前の印は「アイコン＋文字」の箱の高さに合わせて置かれていたため、
文字を消すと印だけが下に残った。印の枠を `top: NAV_PILL_PAD` /
`height: TAB_SQUARE` に固定し、アイコンの正方形の枠と同じ箱を共有させた。
実測で印の中心y=812・枠の中心y=812 で一致。

### 19.3 タブバーの形を幾何学に揃える

- タブ1つぶんの枠 = **正方形**(`TAB_SQUARE`=44)。
- 選択中の印 = その枠に内接する**正円**(44x44・`border-radius:50%`)。
  枠から枠へ 320ms で滑る(印は1枚だけで、出し入れしない)。
- ピルの内側の余白 `NAV_PILL_PAD`(6)。`components/Dashboard.tsx` の
  モーフ用ピル(`PILL_H = 44 + 6*2`)と必ず同じ値にすること。開閉の途中で
  本物の nav と portal 側のピルが入れ替わるので、ズレると継ぎ目が出る。
- **文字は出さない**。読み上げと押した時のトーストのために
  `AppTabDef.label` は残し、`<button aria-label>` に載せてある。

### 19.4 ★アイコンを線画から面へ描き直す(`components/TabIcons.tsx` 新設)

lucide の線画をやめ、アプリ全体の幾何学の語彙(円・半円・四半円・三角・
長方形、角度は 0/45/90/180 のみ)で**面だけ**で描いた11個を新設した。
「書く」入口の丸ボタン(✨/＋/ペン)も同じ語彙に置き換えたので、
`AppShell` が lucide から読むのは設定アイコンだけになった。

- 2色で描く: `color` が図形、`hole` が図形から抜く色。抜きは下地の色を
  上に重ねて表現するので、黒い円の上でも白地の上でも同じ形に見える。
- **★未選択の色は不透明でなければならない**(`TAB_ICON_OFF = "#9C9C9B"`)。
  最初 `rgba(26,26,24,0.42)` にしていたところ、図形が重なるところだけ色が
  二重に乗り、ハートの中央とピンの帯に濃い継ぎ目が出た。この値は同じ

- **アーカイブは「棚に並んだバインダー」**(高さの違う3冊＋棚板)。最初は

- svg の外枠は1つに集約し、種類ごとに切り替えるのは中身の図形だけ
  (`shapes()`)。**外枠のコンポーネントを `TabIcon` の中で定義すると
  eslint の `react-hooks/static-components` に引っかかる**(毎レンダー
  別のコンポーネントになり、中身が作り直される)。

### 19.5 性能: 回帰なし。ただし節の間で数字を比べないこと

同じ `perf.mjs`(4倍スロットリング・本番ビルド)で、この回の変更を

## 20. タブバーを元に戻す・背景を「はけて、入ってくる」動きへ作り直す(2026-08-03続報)

§19 のタブバー(正方形の枠＋正円の印＋面のアイコン)は「全くダメ」と却下。
背景も「白い図形が動くだけにしか見えない」と却下され、寸法まで踏み込んだ
指定が出た。

### 20.1 タブバーは元の形に戻す

§18 までの見た目(角丸の印がタブからタブへ滑る・lucideの線画アイコン)へ
そのまま戻し、**変えたのは2点だけ**にした:
- 文字を出さない(読み上げ用のラベルは `aria-label` に残す)。
- そのぶんアイコンを 19px → **22px** にした。

`components/TabIcons.tsx`(面で描いた11個)は**削除**。`lib/apps.ts` も
`Icon: TabIcon`(lucide)へ戻した。印の寸法 `TAB_MARK_W`(44) /
`TAB_MARK_H`(34) は **`lib/constants.ts`** に置く。
★AppShell に置くと `Dashboard` → `AppShell` → `Dashboard` の循環参照に
なり、`ReferenceError: Cannot access 'fj' before initialization` で
ビルドが落ちる(実際に一度落とした)。共有する定数は必ず `lib/constants.ts` へ。

### 20.2 背景: グリッドを1段階大きく(50vw)し、3アプリで共有する

基準を 25vw → **50vw**(画面幅の半分)にした。画面はこれで縦に2列へ割れ、
分かれ目がちょうど画面の中央線に来る。行は画面中心を軸に上下へ展開する。

| アプリ | 左の列 | 右の列 |
|---|---|---|
| ジャーナル | 塗りつぶしの長方形(6マスを縦に貫く1本の帯) | 直線部分を画面右端に置いて左へふくらむ半円 |
| タスク | 左下が角の扇形を縦一列 | 地のまま |
| ブリーフ | 2x2マス(=画面幅いっぱい)に内接する円の四半分 | 同左 |

半円は「半円の形の要素」を作るのではなく、**マスと同じ直径の円を右へ半分
ずらして窓で切る**。楕円にならず、直線部分が必ず画面の端に一致する。

### 20.3 ★図形と地を同格に扱う

「薄い図形 / 濃い地」で固定するのをやめた。**ジャーナルだけは地が薄く
図形がグレー**で、タスク・ブリーフとは明暗が逆になる。アプリを移ると
地の色ごと入れ替わる。

### 20.4 ★モーフィングをやめ、「はけて、入ってくる」動きへ

§16〜§19 は、マスの中の図形を `border-radius` と `scale` で連続的に変形
(モーフィング)させていた。これが「白い図形が動くだけ」に見えていた原因。

作り直した構造:
- 各マスは **窓**(`overflow:hidden`)。
- その中に、3アプリぶん＋一周ぶんの**面(pane)を4枚並べた帯**が入っている。
- アプリを移ると帯ごと**ちょうど1マス分**スライドする。いまの図形は窓の外へ
  はけ、次の図形が窓の外から入ってくる。
- **面は自分の地の色を持つ長方形そのもの**。これが動くので、塗りつぶしの
  部分は「長方形が伸びてきて塗りつぶす」ように見える(=長方形をデザインの
  語彙に加えるという指定への答え)。
- **左の列は縦、右の列は横**に動かす。全部同じ向きだと、ただの視差
  (背景が一緒に流れているだけ)に見えてしまう。
- 行ごとに `--d`(34ms刻み)の `transition-delay` を持たせ、落ち着くときだけ
  帯が段々に塗り替わる。指で引いている間は transition 自体を切ってあるので
  1:1の追従は保たれる。

中の図形は**一切変形しない**。動くのは帯の `translate` 1つだけ。

### 20.5 ロード画面も同じ考え方へ

角の丸めを動かす(モーフィング)のをやめ、2x2の窓それぞれの中を図形が
通り過ぎていく形にした(`load-v` / `load-h`)。面が入りきったところで少し
止まるキーフレームにしてあるので、動きが刻まれて読める。マスごとに向き
(縦・横)と図形の並びをずらしてある。最後の面は最初と同じ図形なので、
一周したところで繋ぎ目が出ない。

### 20.6 ★性能は大きく改善した

同じ `perf.mjs`(4倍スロットリング・本番ビルド)で:

| | 横スワイプ1回(longtask合計) |
|---|---|
| §19(48マス・毎フレーム transform と border-radius を calc) | 967 / 988 / 1008ms |
| §20(12マス・帯の translate 1つだけ) | 260 / 288 / 169ms |

マスが 48→12 に減り、1マスあたり動かすプロパティも
「transform + border-radius の複雑な calc 2本」から「translate 1本」に

`npx tsc --noEmit` / `npx eslint .`(既知の`<img>`警告3件のみ) /

## 21. ★背景を指の動きから切り離し、図形ごとの入退場アニメーションへ(2026-08-03続報)

参考動画3本(Pinterest/Behanceのモーショングラフィックス)とともに、
「背景のアニメーションが本当に良くならない」という指摘。示された要件:

> アニメーションは一息でいくのでなくても良い。画面をスワイプした時に、その時の
> 背景が去るアニメーションと同時に、画面が先に遷移する。遷移しながら、または
> 遷移した後でも良いので、切り替え先の背景が登場するアニメーションを流す。
> 例えば画面左側がグレーなら、グレーの帯が上から伸びてくる。他の図形もそれぞれに
> アニメーションを与え、上側から少し時間差で下の図形がはけていく/登場する/移動する。

### 21.1 ★何が根本的に間違っていたか

§16〜§20 はどの版も **背景を指の動き(`--dragn`)に1:1で溶接**していた。
つまり背景は「スワイプの従属物」で、自分の時間を持てない。だから
`border-radius` のモーフィングでも、面のスライドでも、結局「1つの動きに
全部が乗っている」ようにしか見えなかった。図形ごとに違う入り方をさせようが
なかったのが本質。

**背景を指の動きから完全に切り離した。** `--dragn` / `--appi` の書き出しと、
横へ払う向きに応じた `--appi` の再基準化(`baseAppi`)は全部削除。背景は
`appId` を prop で受け取るだけで、**アプリが確定した瞬間に自分の
アニメーションを1本流す**。

### 21.2 3拍で組む

| 拍 | 時刻 | 何が起きるか |
|---|---|---|
| 1 | 0〜500ms | いま出ている図形が、来た道を戻るように**上から順に**はけていく |
| 2 | 180〜560ms | 新しい地の色が**上から下りてきて**画面を塗り替える |
| 3 | 360ms〜 | 新しい図形が1つずつ時間差で入ってくる |

図形ごとに入り方が違う:
- **帯**(ジャーナルの左半分) … 上から下へ伸びる(`scaleY` 原点上端)。
  グリッドを縦に横断する**1枚の長方形**として持つ(マスに割らない)。
- **半円**(ジャーナルの右) … 画面の外から左へ差し込む(`translateX`)。
- **扇形**(タスク) … その角(左下)を軸に開く(`scale` 原点左下)。
- **円**(ブリーフ) … 中心から立ち上がる(`scale` 原点中央)。

去る側は**同じアニメーションの逆再生**(`animation-direction: reverse`)。
来た道をそのまま戻るので語彙が増えず、CSSも半分で済む。
入りと去りで遅れが違うので、図形ごとに `--din` / `--dout` をインラインで渡し、
`.bd-piece { animation-delay: var(--din) }` /
`.bd-leaving .bd-piece { animation-delay: var(--dout) }` で切り替える。

**★去る動きが見えるように、新しい地の登場を180ms待たせている。** 最初の
実装では地の遅れが0で、地が即座に全面を塗ってしまい、その下で起きている
「去る」動きが一度も見えなかった(実測で判明)。

### 21.3 同じアプリへ戻るときも必ず animation を出し直す

`turn`(切り替えの回数)を `key` に混ぜてある。値が同じだとReactが要素を
再利用してしまい、CSSアニメーションが再生されない。ゴールのシートで踏んだ
のと同じ問題・同じ対処(§7.29)。

### 21.4 ロード画面も同じ語彙で作り直し

1マスの中で完結させるのをやめ、**2x1・2x2の長方形へ伸びる / グリッドを
横断して移動する / 回転する**を入れた。半円は使わない。
3枚の図形(長方形・円・扇形)がそれぞれ別のリズムで動く:
- 長方形: 1x1 → 2x1(上の行を横断) → 下の行へ移動 → 2x2(全面) → 1x1
- 円: グリッドの角から角へ渡り歩く(潰れないよう縦横同じ倍率だけ)
- 扇形: 90度ずつ回りながらマスを移る

`transform-origin` を左上に置いてあるので、`scale` がそのままグリッドの
升目に乗る。

### 21.5 ★性能はさらに良くなった

指で引いている間、背景は**一切動かない**(計算もしない)。

| §19(48マス・毎フレーム calc) | 967 / 988 / 1008ms |
| §20(12マス・帯の translate) | 260 / 288 / 169ms |
| §21(背景は指と無関係) | **62 / 114 / 272ms** |

## 22. タブバーを元の寸法へ・アイコンを提供された図形集から・背景の三角・
「画面の端が見える」の原因(2026-08-03続報)

背景のアニメーション(§21)は「すごく良くなりました」と受け入れられた上で、
4点の指摘。

### 22.1 ★「タブバー下部に画面の端が見えてしまう」の原因

`app/globals.css` の `html, body` が `#F0F0EE`(BG)のままで、背景
(AppBackdrop)の地の色 `#ECECEA` と**違っていた**。シェルの高さは
`100svh` 固定(§7でdvhの揺らぎを断つために選んだ値)なので、iOSで
ツールバーが引っ込んで表示領域が広がると、その差の帯が背景に覆われず
**body の色のまま残る**。地より明るいので、そこが「画面の端」の線として
見えていた。
- `html, body` の既定色を地と同じ `#ECECEA` にした。
- さらに **AppBackdrop がアプリごとに `body`/`html` の背景色を書き直す**
  (ジャーナルだけ地が明るいため。1アプリ切替につき1回の書き込みで、
  毎フレームの処理は無い)。
- あわせて、全画面の下地(`LoadingScreen`・シェル・認証待ち)と、
  ブリーフの育成カードのフッターのグラデーション(`BriefTab`)も、BG から
  **地と同じ `BD_GREY`** に揃えた。ここが BG のままだと、地の上に
  明るい矩形が乗って同じ「継ぎ目」を作る。
- 色は `lib/constants.ts` の `BD_GREY` / `BD_LIGHT` に集約した。

### 22.2 ★ぼかしの帯を撤去した(ちらつき・途切れの主因)

nav 手前の `backdrop-filter: blur(12px)` + `mask-image` の帯を**撤去**。
§19 の時点で「Safari はこの組み合わせのマスクを無視することがあり、
その場合ぼかしが矩形いっぱいに効いて硬い境目が出る」と書いていたとおりの
症状(「タブバーのあたりの画面が途切れて見える」)。加えて、画面全体を覆う
ぼかし層はスクロールのたびに合成をやり直すため、ちらつきの原因にもなる。
ピル自体が不透明な紙色で影も持っているので、帯が無くても下を流れる中身
とは十分に見分けが付く。

### 22.3 タブバーの寸法を元へ・印は内側にぴったり収まる正円

`lib/constants.ts` に `TAB_MARK = 52` / `NAV_PILL_PAD = 6` を置いた。
ピルの高さ = 52 + 6*2 = **64px**(以前と同じ)。選択中の印はその内側の
高さにぴったり収まる**正円**(直径52)。`components/Dashboard.tsx` の
モーフ用ピル(`PILL_H`)も同じ式から作るので、開閉の途中で入れ替わっても
継ぎ目が出ない。★共有する定数は必ず `lib/constants.ts` へ置くこと
(AppShell に置くと Dashboard との循環参照でビルドが落ちる・§20.1)。

## 23. ★幾何アルファベットを内蔵し、見出し・タグをそれで組む(2026-08-03続報)

### 23.1 `components/GeoType.tsx`(新設)

- 1文字は**高さ3ユニット**の箱。幅は文字ごとに違う(I は 0.75、M は 3.3)。
  縦棒の太さ **S=0.75** は全文字共通で、曲線の半径も S の差で線幅が揃うよう

## 24. ★幾何アルファベットを見本から**画像解析して転写**し直す(2026-08-03続報)

§23 で作った書体は「ただの幾何サンセリフを自作したもの」で、見本とは別物
だった。ユーザーから「画像は正方形を2×2のグリッドに分割して、それらに
長方形と扇形などを組み合わせて作られています。もう一度画像を分析して
作り直してください」という指摘。**§23 の字形の記述はすべて無効。**

### 24.1 見本の組み方(実測)

`scratchpad/analyze.py` で見本(FullSizeRender.jpeg)を解析した結果:

- 1文字は **162×162 の正方形**。中は **セル78px + 溝6px の 2×2 グリッド**。
  文字ピッチは168pxなので、**字送りも溝1本ぶん(6px)**。全文字同じ幅=**等幅**。
- 4つのセルに入るのは**たった3種類**:
  - `full` … 正方形をそのまま塗る
  - `q◇`  … 指定した角を、**セルの一辺**を半径にして丸く落とす(四半円)
  - `rr◇` … 帯の指定した端を、**セルの半分**を半径にして丸くする
  - `empty` … 空
- そして **セルとセルの間の溝(縦2本・横2本)は、繋がっている所だけ塗る**。
  これが字形を決める要。例:
  - **A** = 上段(左上を丸く / 右上を丸く)＋**縦の溝を塗る**→アーチ。
    下段は正方形2つで**溝を塗らない**→脚の間の隙間。
  - **O** = 四隅を丸めた4セルだが**縦の溝を塗らない**→円の真ん中に縦線。
  - **B と D は同じ「縦棒＋右のふくらみ」だが、B は右列の横の溝を塗らない**
    ので右のふくらみが上下に割れる。1色でも区別が付くのはこのため。

### 24.2 ★転写のやり方(目視で写してはいけない)

各セルを15種類のテンプレート(empty/full/四半円4方向/扇形4方向/半円4方向/
端丸帯4方向/半分の矩形)と **IoU で突き合わせて分類**した。全104セルが
**0.97〜1.00** で一致し、転写は機械的に確定した。

目視だと必ず取り違える。実際、最初に目で写したときは **C の右上を「丸い」と
誤読**していたし(実際は `full`)、そもそも「2×2のセル」という組み方自体に
気づけていなかった。**この手の作業は必ず画像解析で裏を取ること。**

### 24.3 実装(`components/GeoType.tsx` を全面書き直し)

- グリフのデータは `[TL, TR, BL, BR, "溝4桁"]` の5要素だけ。26文字ぶんが
  解析結果そのまま入っている。
- 塗り足しだけで済む(穴もmaskも要らない)ので、**1文字＝1本のパス**。
  §23 の mask 方式より軽い。
- **★部分パスはすべて時計回りで書くこと。** rect と逆向きの部分があると、
  溝と重ねた所の巻き数が 0 になり、nonzero塗りで**髪の毛のような穴**が開く。
  最初 `qTL` / `rrL` / `rrD` が逆向きで、実際に文字の中に細い筋が出た。
  ついでに `qBR` は最初**補集合**(角の欠けた側)を描いていた。
  どちらもレンダリングして見本と並べて初めて分かった。
- 溝を塗るときは両隣のセルへ `BLEED`(0.012)だけ食い込ませる。ちょうど接する
  だけだとアンチエイリアスで継ぎ目が残る。
- 数字0-9は見本に無いので、同じ規則で足したもの(その旨コードに明記)。

### 24.4 サイズ

正方形の書体なので、§23(高さ3ユニット)とは `size` の意味が変わった。
`size` = 正方形の一辺(px)。表示用の書体で小さいと潰れるため、タグは
少し大きめにしてある: 見出し30 / 棚の見出し16 / DONE・NOTES 15 /
KEEPバッジ 11。

`npx tsc --noEmit` / `npx eslint .`(既知の`<img>`警告3件のみ) /
`npm run build` すべて通過。
- **見本と自分の描画を上下に並べた比較画像**(scratchpad/cmp.png)を作り、

## 26. ★オーバーレイが画面外へ飛んでいた真因(transformされた祖先)・背景を
body直下へ・タグを本文の書体へ戻す・設定アイコン(2026-08-04)

実機のスクリーンショット3枚とともに4点。うち2つは**同じ1つの原因**だった。

### 26.1 ★★`position:fixed` が画面ではなくトラックを基準に解決されていた

報告は別々の2件だった:
- 「ブリーフのカードをタップしても画面が出てこない」
- 「ブラーの画面の時にタブ周りの表示がおかしい」

原因は1つ。**CSSの規則により、`transform` を持つ要素は、その子孫の
`position:fixed` の包含ブロックになる**(＝fixed がビューポートではなく
その要素を基準に解決される)。§13でアプリ切替の横スライドを入れた際、
シェルの中に `transform` を持つ `.app-track`(幅300%・translateされている)が
できたため、その中に描かれる `BottomSheet`(このアプリの全オーバーレイが
通る共通部品)の fixed が**トラック基準**になっていた。

実測(修正前 / 修正後):

| | ブラー(inset:0) | 中のパネル |
|---|---|---|
| 修正前 | `-780,0 1170x844` | `-385,298`(**画面外**) |
| 修正後 | `0,0 390x844` | `24,300 342x244` |

ブラーはトラック全体(1170x844)へ広がるので「一応それらしく暗くなる」が、
**中のパネルだけが画面の外へ飛んでいた**。だから「タップしても何も出ない」
ように見え、同時に「ブラーの効き方がタブの周りでおかしい」ようにも見えて
いた。`getComputedStyle` ではなく、**`offsetParent` を遡って transform を
持つ祖先を探す**ことで確定できた(`transformedAncestor: "app-track"`)。

**対応**: `components/BottomSheet.tsx` を `createPortal` で
`document.body` 直下へ描くようにした。このコードベースでは既に
Dashboard・MapFullscreenOverlay・ExecuteTabのバインドボタンが同じ手を
使っており(§7.5・§7.33)、定石に揃えただけ。

★**今後 `position:fixed` を新しく書くときは必ず portal を通すこと。**
`.app-track` がある限り、シェルの中に書いた fixed は例外なく壊れる。

### 26.2 背景も body 直下へ(タブ下部で途切れる件)

## 27. ★背景が丸ごと消えていた真因(bodyの背景が負のz-indexを塗りつぶす)・
歯車アイコン・ダッシュボードに慣性と右端の掴み代(2026-08-04)

### 27.1 ★★「背景のアニメーションがなくなった」の真因

§26.2 で背景(`AppBackdrop`)を body 直下のポータルへ移し `zIndex:-1` で敷いた
ところ、**背景が丸ごと見えなくなった**(パターンも、その入退場の
アニメーションも)。DOMにも要素はあり、`getAnimations()` も走っており、
図形の矩形も色も正しい——なのに画面は地の色一色。

原因は**CSSの描画順**。1つのスタッキングコンテキストの中では、
1. その要素自身の背景 → 2. **負のz-indexの子孫** → 3. in-flowの子孫の背景 →
… の順に描かれる。§22 で「画面の端が見える」対策として `body` にも
地の色を敷いていたため、**手順3のbodyの背景が、手順2の背景ポータルを
まるごと塗りつぶしていた**。

**対応**: 地の色は **`html` にだけ**敷く(htmlの背景はキャンバスへ伝播し、
すべてより先に描かれるので負のz-indexの下に正しく回る)。`app/globals.css`
で `body { background-color: transparent }` を明示し、`AppBackdrop` が
アプリごとに書き直すのも `documentElement` だけにした。
★**今後 body に background を足さないこと。** 足した瞬間に背景が消える。

検証: 切り替えの途中を `getAnimations()` で止めて0/200/420/700msの4コマを
撮り、円がはけて → 帯が上から伸びて → 三角が右から時間差で入ってくる、と
§21で作った3拍が実際に見えることを確認した。ピクセル値でも図形の色
(243,243,241)と地(236,236,234)が出ている。

### 27.2 設定アイコンを本物の歯車に

つまみ(円＋目盛り)は「設定っぽくない」と却下。**歯8つの歯車の輪郭**を、
外周R=11・内周r=8.2の多角形として**その場で1本のパスに組む**
(`GEAR_PATH`、`components/TabIcons.tsx`)。座標を手で並べると必ず順序を
取り違えるので、角度から計算して生成している。中心に濃い軸の円。
17pxでも輪郭のぎざぎざで歯車と読める。

### 27.3 ダッシュボード: 慣性・右端と上端の掴み代・段差の入場

**慣性**: 以前は速さに関わらず必ず340msで運んでいた(「ぎこちない・慣性が
ない」)。離した瞬間の指の速さから「残りの距離をその速さで運びきる時間」を
求めて `--dash-ms` に書き、CSSの transition-duration をそれにした
(190〜560msにクランプ、減速は指数のease-out `cubic-bezier(0.16,1,0.3,1)`)。
- ★**指を止めてから離したときは速さを0にする**。vx/vy は pointermove でしか
  更新されないので、止まっている間は最後に動いたときの速さが残り続ける。
  実測で「そっと置いたのに最短の190msで飛ぶ」状態になっていた。
  最後の move から70msを超えていたら0とみなす(AppShell・Dashboard両方)。

**掴み代を2つ足した**(`components/Dashboard.tsx`):
- **右端**(`EDGE_W`=22px、シートの全高) … ユーザー指定「取手を触らなくても
  画面右端側を下にスワイプすれば閉じれるように」。行の×ボタンは右端から
  12〜38pxにあるので、22pxなら重ならない。
- **シートの上端**(`TOP_GRAB_H`=46px) … 取手(`.dash-grip`)はシートの少し
  「上」に浮いているため、「シートの縁を掴んで下げる」という自然な操作が
  効いていなかった。この範囲は余白と日付しか無いので掴み代にしてよい。

**入場を段差に**: シートの中身に `dash-rise`(下から16px・420ms・
ease-out)を、日付→1つ目の節→2つ目の節→締めのボタンの順に60〜240msずらして
掛けた。1枚の板が出るのではなく、中身が組み上がって見える。

## 28. 背景の「去る」を払い始めと同時に走らせる(2026-08-04続報)

§21で組んだ3拍のうち、去る側も**アプリが確定してから**(＝指を離してから)
走っていた。ユーザー指定で、**払い始めた瞬間**に走り出すようにした。

**難しいのは「払い始めた時点では次がどのアプリか決まっていない」こと。**
去る側と来る側を、別々の合図で動かす作りに変えた
(`components/AppBackdrop.tsx`):

- `swiping`(新しいprop) … 横だと軸が決まった瞬間に true。ここで**いまの層を
  そのまま去る層へ移し**、逆再生を始める。同時に来る層(＝同じ図形が同じ
  位置に静止しているもの)は**描画をやめる**。残しておくと、その下で進んで
  いる逆再生が一切見えない。
- `appId`の変化 … スワイプが確定したとき。新しい層を入場させる。
  **去る層のkeyは据え置く**。振り直すと、走っている逆再生が最初から
  掛け直されてしまう。
- 払いかけてやめた場合(`swiping`がfalseに戻ったのに`appId`は同じ) …
  同じアプリで入場をやり直す(figureが戻ってくる)。

AppShell側は、軸が「横」と決まった瞬間に `setSwipingAway(true)`、
`finish()` で false。**1ジェスチャーにつき2回しかstateを更新しない**ので、
指を動かしている間のレンダーは従来どおり0回のまま。

あわせて、去りが速すぎて一瞬で消えていたので、逆再生を300→380ms・
図形ごとの遅れを40→52msにした(いちばん遅い図形が消えきるまで約700ms)。

検証: 払い始めから60ms/240ms/460ms、確定+150ms、落ち着いた後、の各時点で
去る層の有無と図形のtransformを実測。払い始め60msの時点で既に逆再生が
進んでおり(scale 0.997→0)、確定後に新しい層が入ってくること、
払いかけてやめると元に戻ることを数値で確認した。
`tsc`/`eslint`(既知の`<img>`警告3件のみ)/`build` 通過。性能(4倍
スロットリング)は横スワイプ 239ms・ストックの縦スクロール 0ms で、
§27と同水準。

## 29. ★去る合図をReactから外す・モーフ用ピルを本物と同寸に・どこでも下スワイプで閉じる(2026-08-04続報)

### 29.1 ★「スワイプが終わってからアニメーションが始まる」

§28で去りを払い始めに連動させたが、実機では**払い終わってから**始まると
報告された。原因は、その合図を**Reactのstate**(`swipingAway`)にしていた
こと。stateを1回更新するだけでもシェルは再レンダーされ、実機ではそれが
数百msかかる(タブのタップで実測している値がそのまま乗る)。その間に
スワイプが終わってしまい、アニメーションはあとから始まる。

**対応**: 合図からReactを完全に外した。払い始めた瞬間に、いま出ている
背景の層のDOM要素へ**直接クラスを付けるだけ**にする
(`beginBackdropExit()` / `cancelBackdropExit()`、`components/AppBackdrop.tsx`)。
このコードベースが `--drag` / `--dash` でやってきたのと同じ方針
(指の動きに関わる合図はDOMへ直接書く)に揃えた。

★**CSSは `animation-direction: reverse` では再生されない。**
既に再生し終わったアニメーションの direction だけを変えても、頭から
再生し直されるのではなく**その場で値が飛ぶ**だけになる。`animation-name`
が変わったときだけ確実に頭から再生される。そこで「去る」用の
キーフレームを別名で用意し(`bd-band-out` 等)、`.bd-out` が付いたら
名前ごと差し替えるようにした。クラスを外せば名前が入場用に戻るので、
「払うのをやめたら figure が戻ってくる」も同じ仕組みで済む。

去る層と来る層を2枚重ねる作りもやめた。層は常に1枚で、切り替わりの間だけ
ポータルの地に**ひとつ前のアプリの地の色**を敷いておく(新しい地が上から
下りてくる180msの間、そこが見えているだけなので、色さえ合っていればよい)。

### 29.2 ダッシュボードのピルが引き始めに一回り大きくなる

モーフ用のピルの箱が `left:50% / marginLeft:-210 / width:420` で、本物の
タブバーの箱(`padding:"0 16px"` の中に `maxWidth:388` の行、その中に
「ピル(flex:1) + gap10 + 書くボタン52」)と**別物**だった。引き始めた
瞬間に本物のnavが消えてこちらへ入れ替わるので、幅が56px広く・左へ9px
ずれた状態が一瞬見え、「元より大きくなる」ように見えていた。
本物と同じ箱に作り直し、ピルの幅も `行の幅 −(書くボタン52 + gap10)` から
始まるようにした。実測で本物 296x64、開き具合0のモーフ用も 296x64 で一致。

### 29.3 シートのどこを下へスワイプしても閉じる

取手・右端・上端だけでなく、シート全体で下スワイプを受けるようにした。
ただしここは**タップやスクロールと共存させる**必要があるので、掴んだ
瞬間には何もせず、(a)8px以上動いた (b)下向き (c)中身のスクロールが
一番上にある、の3つが揃って初めてドラッグとして引き取る。ボタンの
タップ(動かない)と、中身を上へスクロールする操作はこれまでどおり通る。

### 29.4 検証

## 30. ★背景の「去る」を指の移動量そのもので駆動する(2026-08-04続報・決着)

§28(Reactのstate)→§29(DOMへ直接クラス)と2回作り直したが、実機では
どちらも「スワイプしてから背景が動き出すまでタイムラグがある」と報告された。
ユーザーの指定はこう:

> アプリ遷移をし始めた時点で、背景が捌けるアニメーションが即座に流れ、
> 遷移する先が確定する判定が入った時点で、そのアプリの背景が入る
> アニメーションを流してください。左右スワイプの判定が入ると背景が捌け、
> アプリを切り替えなかったとしても、そのまま背景が戻ってくれば良い。

**時間で走らせる限り、「合図が届くまでの遅れ」は必ずどこかに残る。**
そこで、去りだけ **指の移動量そのもの(`--outp`)から算出**する形に変えた。
画面(トラック)を動かしているのと**同じ変数・同じフレーム**で動くので、
遅れが構造的に存在しない。払うのをやめれば `--outp` が0へ戻り、figure も
そのまま元の位置へ戻ってくる(ユーザーの指定どおり)。来る側は従来どおり
時間で組んだ入場アニメーション(確定してから)。

- `AppShell` の `setDragVar` が `--drag` と一緒に
  `--outp = min(1, |px| / (画面幅 * 0.22))` を書く(送る判定は18%なので、
  送ると決まる頃には figure がほぼ捌け切っている)。
- 図形ごとに `--o`(始まりのずれ、0.05刻み)を持たせ、
  `--lp: clamp(0, (--outp - --o) * 2.2, 1)` から transform を出す。
  上から順に畳まれる。
- ★`animation-fill-mode` を `both` → **`backwards`** に変えた。both のままだと
  入場が終わったあとも最後のコマの transform が永久に効き続け、この
  `--lp` から算出する transform を一切上書きしてしまう。backwards なら
  遅れている間だけ from のコマを見せ、終わった時点で普通のCSSの値へ戻る。
- 指を離すと `[data-dragging]` が外れ、`transition: transform 420ms` が
  figure を戻す(切り替えた場合は層ごと差し替わるので見えない)。

**★`will-change: transform` が必須**。半画面ぶんの図形13枚が毎フレーム
変形するので、合成レイヤーに上げないと毎フレーム塗り直しになる。
実測(4倍スロットリング・本番ビルド)で、横スワイプ1回の long task が
**435ms(8フレーム) → 0ms** になった。

検証: 指を6/14/30/50/80px動かしながら `--outp` と各図形のtransformを実測。
14pxで先頭が0.64、30pxで0.23/0.41/0.58(ずれている)、50pxで0、指を戻して
離すと1.00へ復帰、送ると新しい層が入場して1.00。ストックの縦スクロールは
引き続き0ms。

**なお §29 で入れた2件(モーフ用ピルを本物と同寸に・シートのどこでも下
スワイプで閉じる)は、この報告の時点ではまだデプロイが届いていなかった
可能性が高い**(「取手以外を下スワイプしても閉じない」という報告は、
その機能が入っている版では起こり得ない)。Chromiumでは本物のピル296x64と
引き始めのモーフ用ピルが一致し、シートの真ん中を下へ払うと閉じることを
再確認してある。

## 50. ★★タブバーをフローから外す — 「タブバー付近で表示が途切れる」の
構造的な解決(2026-08-12)

ユーザーからの指摘(要約):
> 背景や画面のものがタブバー付近にかかると、タブバーの上下で表示が途切れたり、
> 境目が見えたり、タブバーの周りだけ背景の色が途中まで残ったりする。それを
> 毎回私が直してくださいと言わないといけなくなっている。今後一切、タブバーが
> 他の画面や背景と干渉しないようにしてほしい。

**★根本原因**: タブバー(`nav.app-nav`)が**列の中の flex の兄弟**として置かれ、
`position: sticky` で**フローの高さを占めていた**。つまり本文の領域が
「画面の高さ − タブバーの高さ」で終わる構造だったため、

- 全面に敷きたい背景や大きな図形は必ずタブバーの手前で途切れる。
- 各タブが「タブバーの高さぶんの negative margin」を**自前で持って**
  食い込ませるしかない(RecordTab の `STUDIO_BLEED` がそれ)。
- その数字はタブバーの寸法・スクロールルートのパディングと厳密に一致して
  いないといけないので、どこかを触るたびにズレて「タブバーの上下に境目が
  出る」「背景が途中で切れる」が再発する。

**★構造を変えた(これが正)**:
1. **タブバーは `position: absolute; bottom: 0`(列の中)**。フローから外れる
   ので、本文の領域は**常に画面いっぱい**。中身はタブバーの下へそのまま
   continue し、タブバーはその上に浮く。
   ★`position: fixed` にはしないこと(iOS SafariのURLバー伸縮中に実際の
   ビューポートとズレて下に隙間が生まれる。過去に再発済み)。列はシェル
   (100svh)の中の普通の要素なので、その中の absolute なら安全。
2. **タブバーの高さを知っている場所は2つだけ**にした。
   `lib/constants.ts` の `NAV_H` / `TAB_PAD_TOP` → AppShell がシェルの
   style で CSS変数 `--nav-h` / `--pad-top` として配る。
3. **画面の四隅まで敷きたいタブは `.full-bleed`(app/globals.css)を付ける
   だけ**。中で `calc(-1 * var(--pad-top)) -16px calc(-1 * var(--nav-h))`
   を持つので、**タブ側は高さの計算を一切しない**。
   → `STUDIO_BLEED` は撤去。`VoiceStudio` の `bleed` prop も廃止。
4. **スクロールする中身の逃がし**は、タブの枠(`.tab-in`)の
   `padding-bottom: var(--nav-h)` で一元的に行う。

**★ここで踏んだ落とし穴(次に触る人へ)**:
- 逃がしを**スクロールコンテナ(`data-tab-scroll-root`)の padding-bottom**
  に置いてはいけない。flex の中身がはみ出したとき scrollHeight に正しく
  入らず、実測で最後の項目が 38px タブバーの裏へ潜って止まった。
- `.tab-in` は `flex: 1`(= basis 0)ではなく **`flex: 1 0 auto`**。basis 0 だと
  この枠が「空いている高さ」に固定され、中身が長いタブでは中身が枠から
  **はみ出す**。はみ出した分は枠の padding-bottom の外側なので、下の逃がしが
  効かない。basis:auto なら「中身が短ければ空きいっぱいに伸び、長ければ
  中身の高さになる」ので padding-bottom が必ず効く。

**検証**(Chromium 390x844・本番ビルド): 全タブでスクロールルートが 0..844
(画面いっぱい)、タブバーは 764..844 の `position: absolute`。
- RECORD(`.full-bleed`): `main` 0..844 = 画面いっぱい。円がタブバーの下へ
  そのまま続き、境目が無い。
- BRIEF / GOALS / STOCK / PLAN / TASK / ARCHIVE: `main` の下端が
  ちょうど 764(タブバーの上端)。
- STOCK を最下部までスクロール: 最後の項目の下端 722 < タブバーの上端 764
  (変更前は 802 で 38px 潜っていた)。
- 声の記録まわり(円の入場・タップ判定・波形・オーバーレイ)に回帰なし。
- 性能(4倍スロットリング): 横スワイプ **0ms** / 録音中 57ms /
  トリミングのドラッグ **0ms**。

**今後の約束**: タブバーの高さに合わせた negative margin を**タブごとに
書かない**。画面いっぱいに敷きたいときは `.full-bleed` を付ける。タブバーの
寸法を変えるときは `lib/constants.ts` の `NAV_H` だけを直す。

## 51. ★★アプリの地色を「列が持つ」ものにする — 遷移中の境目の構造的な解決
(2026-08-12続報)

§50 でタブバーをフローから外したあとも、**地色の違うアプリ(ジャーナル)へ
移る途中でタブバーの下に境目が見える**という報告が残った。

**★実測で原因を確定**。払っている最中〜離したあとの画面下部のピクセルを
サンプリングすると:
```
払っている間        : 全域 179 (=ジャーナルの地。まだ切り替わっていない)
離して 80ms         : 206  ← 混ざっている
離して 160ms        : 233
落ち着いた          : 236 (=タスクの地)
```
アプリの地色を**画面全体に1枚だけ敷いた帆布**(`AppBackdrop`)が塗っており、
アプリが切り替わるときにその1枚が**クロスフェード**していた。列は横へ
スライドするのに地色だけがその場で混ざるので、遷移中は「新しいアプリの
領域に古い地色が残っている」状態になる。中身が自分で地を塗っている所
(声の記録の器)との境目が、そこで見えていた。

**★構造を変えた(これが正)**: **アプリの地色は列(`AppColumn`)が持つ**。
- `AppColumn` の div に `background: groundOf(a.id)`。列は不透明になり、
  A の地が出ていって B の地が入ってくるだけになる。**混ざる瞬間そのものが
  無くなる**ので、地色を何色に変えても同じ理屈で成立する。
- `VoiceStudio` は**自分では地を塗らない**(列の色をそのまま透かす)。
  全画面のオーバーレイだけは列の外なので、自分で暗い地を塗る。
- `AppBackdrop` の帆布は普段は見えなくなった。役目は、シェル(100svh)の
  外側 — iOSのオーバースクロールやセーフエリアの帯 — に色を用意しておく
  ことだけ。`groundOf` を列・帆布・html の3つが同じ関数から引くので、
  色を変えてもズレようがない。

**今後の約束(★これを破ると必ず境目が出る)**:
- **アプリの地色を塗ってよいのは `AppColumn` だけ**。タブや中身の側で
  背景色を塗らないこと。出どころが2つあると、遷移中にどちらかがズレる。
- 地色を変えるときは `components/AppBackdrop.tsx` の `groundOf` だけを直す。

**検証**(Chromium 390x844・本番ビルド): 同じサンプリングで、払っている
最中の画面下部が `x=20,200,390 → 179` / `x=600,760 → 236` と、**2つの地色が
列の境目でくっきり分かれ、どちらも最終的な色のまま**であることを確認
(中間色が一度も出ない)。スクリーンショットでも、境目は列の縁の縦一本だけで、
タブバーの下に横向きの継ぎ目は無い。
§50 の検証項目(全タブの `main` の下端・STOCKの最下部)、声の記録まわり、
性能(横スワイプ 0ms / トリミングのドラッグ 0ms)にも回帰なし。

## 56. ★★★iOS ホーム画面アプリの「上下の帯」— 4巡かけて正しい理屈へ
(2026-08-19〜2026-08-23・第29〜36巡)

**結論**(現行仕様は `docs/project_knowledge.md` §3 が正): `statusBarStyle`
は`default`。タブバーの位置は`NAV_BOTTOM_GAP`が`env(safe-area-inset-bottom)`
を比率(2.382)で使って吸収する。ここには**そこへ至るまでに踏んだ間違いと、
なぜ間違いだったか**を残す。同じ手を二度試さないため。

### 29〜32巡: 行きつ戻りつ

- 第29巡: `default`にしたら下の帯は消えたが、上に黒い帯・タブバーが47px
  下がる副作用が出て、**原因を切り分けずに`black-translucent`へ即座に戻した**。
- 第30巡: 未確証の「WebKitの起動直後の高さグリッチ」説を立て、
  `lib/viewportKick.ts`を投機的に実装(★これは"未確証"と明記して出した点は
  正しかった)。
- 第31巡: 実機の実測データが2分間安定していて、第30巡の説を**否定**。
- 第32巡: 「web側では直せない、iOSのハード制約」と**誤って断定**して
  ドキュメントに"確定事実"として書いた。★★**これが一番の反省点**。
  ユーザーから「一度は解決していたはずだ」と名指しで訂正された
  (第29巡の実験ログを自分たちで見失っていた)。

### 34巡: `--screen-h`(誤ったCSSの前提)

「`position:fixed`の要素の`height`を`calc(100% + env(safe-area-inset-top))`
まで伸ばせば、ビューポートの外(下47px)まで描けるはず」という前提で実装。
**CSSの前提が誤り** — `position:fixed`要素はビューポートの実際の描画面の
外を絶対に描けない(heightをいくら指定しても)。実機写真の画素比較
(円の下端が796.7ptのまま1pxも動かず)で完全に反証され、撤去した。

### 35巡: `default` + 副作用の切り分け(ここでようやく正しい理屈に到達)

`black-translucent`は「web ビューは画面の上端(y=0)から始まるが、高さが
**画面の高さ − 上のセーフエリア**しか無い」モード。だから下47pxが
**どの要素からも塗れない帯**として残る。`default`は逆に「web ビューが
**画面の下端まで**与えられる」代わりに、上47pxをiOSが`theme-color`で
塗る**ネイティブ領域**になる。つまり第29巡で見えていた「副作用」は
2つとも**別々に直せるもの**であって、`default`自体の欠陥ではなかった。

- 副作用①(タブバーが47px下がる)→ `NAV_BOTTOM_GAP`に
  `+ env(safe-area-inset-top)`を足して戻す案。
- 副作用②(上47pxの黒い帯)→ 正体は`theme-color`の補間が`requestAnimationFrame`
  頼みで、rAFが止まる(画面が隠れる・iOSが絞る)と途中の色で固まっていた
  だけ。`setTimeout`で行き先を必ず書き込む保険を追加して解決。

### 36巡: `env(safe-area-inset-top)`は`default`で0という発覚

第35巡の副作用①の修正(`+ env(safe-area-inset-top)`)を、ユーザーが実機で
確認したところ**タブバーの位置が1pxも変わっていなかった**(新旧スクリーン
ショットのピル位置を画素比較して確定)。**`default`モードでは
`env(safe-area-inset-top)`が0になるらしい** — web ビューがそもそも
ステータスバーの下に描かれないモードなので、「不安全な領域」という概念自体が
無い、という理屈で説明はつく。

★**足し戻す信号が無いので、`env(safe-area-inset-bottom)`を比率で使う
ことにした**。これは実機でだけ非ゼロ(34pt)になる値で、Chromium・検証環境
では常に0なので、そこでの見た目・既存の検証は今までどおり4pxのまま保てる。
実機だけ、必要な47ptぶんを足す比率(2.382)を掛ける
(34 × 2.382 − 26 ＝ 55 ＝ 元の8px ＋ 47px)。この比率は**今の端末
(セーフエリア下34pt)専用の逆算値**で、別の端末では合わなくなる —
`docs/project_knowledge.md` §3に再計算の手順を明記した。

### 教訓

1. **実機の写真を画素で比較してから「直った」と言う。** 見た目の印象だけで
   判断すると(第29巡の即時ロールバック、第36巡の`+top`修正)、効いていない
   変更を「直った」ことにしてしまう。
2. **「web側では直せない」と断定する前に、過去の自分の実験ログを疑う**
   (第32巡)。
3. **CSSの前提を検証せずに実装しない**(第34巡の`--screen-h`)。
   `position:fixed`はビューポートの実描画面の外を描けない。
4. **`env(safe-area-inset-*)`はモード(`black-translucent`/`default`)ごとに
   挙動が変わりうる。** 決め打ちで使わず、実機で非ゼロになることを確認してから
   数式に組み込む。

## 65. ★★UI 規約の全数調査 — 「チェックが有る性質だけが揃っていた」

第65巡に `design.md` を作るため、全コンポーネントの CSS 的な性質を数えた。
**結論は語彙の質ではなく、強制の有無が品質を決めていた**である。

| 性質 | 機械チェック | 実測 |
|---|---|---|
| `fontSize` | **あり** | 生の数字は 224 箇所中 **1**（0.4%） |
| easing / duration | **あり** | 実際に動く 38 件が**全部**語彙 |
| `borderRadius` | 無し（結果的に無事） | 164 箇所中 153 が `RADIUS.*` |
| **`letterSpacing`** | **無し** | 85 箇所に **18 種類**（`0.2em` と `0.20em` の二重表記あり） |
| **`lineHeight`** | **無し** | **17 種類**。16px だけで 8 種類 |
| **`fontWeight`** | **無し** | 実効 5 段（400/500/600/700/800）。**無指定 93**（既定 400 へ落ちていた） |
| **余白** | **無し** | 457 箇所中、名前で書かれているのは **12**（2.6%） |
| **色** | **無し** | 16 進の直書きが **77 種類・135 箇所** |
| **横並び** | **無し** | `alignItems:"center"` 95 に対し `baseline` は **5** |

### 個々の症状（規約の各条がどこから来たか）
