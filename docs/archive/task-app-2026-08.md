## 52. ★タスクアプリを作り直す: 浮遊する柱体・展開図・重力(2026-08-12)

仮置きだった INBOX / TODAY / ALL を破棄し、§38 のデザイン言語(テクスチャを
排除した純粋幾何学ミニマリズム + 物理演算によるデジタルな手触り、Task の
担当メタファーは**落下と粉砕**)に沿って作り直した。

### 52.1 確定した設計(すべてユーザーと事前に合意)

| 論点 | 決定 |
|---|---|
| タブ構成 | **2タブ**。候補(DRIFT)=無重力で漂う / タスク(GRAVITY)=落ちて積む。日付での区切りは廃止 |
| 物理演算 | **matter.js**。計算だけに使い、描画は自前の canvas |
| 3D表現 | **CSS の 3D 変形は使わない**。投影を JS で計算して描く |
| 重要度 | Cowork の毎晩の仕分けが見立て、本人が展開図で上書き |
| 確定タスクのタップ | 候補と**同じ展開図**が開く |
| 完了 | **粉砕して消える**。上に乗っていたものは崩れて沈む |
| 候補の種類 | **タスクの候補だけ**。他3種はデータとして残るが表示しない(行先は未定) |
| ダッシュボード | 「今日のタスク」は従来どおり期日が今日のもの(`components/TaskRow.tsx`) |

### 52.2 立体は情報が増えるほど角ばる(柱体の一本道)

面の数 = 1(タイトル=なにを) + 面として置かれた5W1Hの数。最小3・最大6。

| 面 | 立体 | 底面 | 側面 |
|---|---|---|---|
| 3 | 円柱 | 円 ×2 | 曲面 ×1 |
| 4 | 半円柱 | 半円 ×2 | 曲面 ×1 + 平面 ×1 |
| 5 | 三角柱 | 三角 ×2 | 平面 ×3 |
| 6 | 四角柱 | 四角 ×2 | 平面 ×4 |

- 展開図は常に「底面 + 側面の帯 + 底面」の帯状。帯の端の「＋」を押すと
  **まだ乗っていない5W1Hだけ**が候補に出て、選ぶとその位置に面が増える。
  面の角の「×」で外すと丸くなる(3面より下へは減らない)。
- **面の数は「中身が入っている数」ではなく「面として置かれている数」で決める**
  (`keysOnNet`)。＋で足した直後はまだ空なので、中身で数えると面が生えてこない。

### 52.3 ★守ること(破ると壊れる)

- **CSS の 3D 変形(perspective / preserve-3d / rotateX)を使わない。**
  3D座標は `lib/prism.ts` が持ち、平行投影して多角形として描く。折り具合 t で
  投影も補間するので、t=1 では正面から見た本物の展開図に一致する。
- **展開図の折れている最中は canvas、開き切ったら DOM。** 円柱・半円柱の側面は
  曲面なので途中の姿は面ごとのアフィン変換では表せない。開き切った状態は
  完全に平らなので DOM で作れて文字入力もそのまま置ける。
- **側面は小片に割って描く**(`prismDraw`)。円柱の側面は全周を1枚で覆うため、
  1枚の多角形にすると自己交差した退化多角形になり、塗りが打ち消えて胴が
  消える(実際に消えた)。同じスロットの小片は同じ色なので見た目は1枚のまま。
  継ぎ目のアンチエイリアスは同色の細い縁取りで埋める。
- **明度は閉じた形から一度だけ決め、折りたたみの途中で変えない。** 光の向きは
  アイソメで同時に見える2つの側面に差が付くよう傾けてある(同じ明度だと稜線が
  消えて立体に見えない)。平らに開き切ったときだけ明度差を狭める(暗い面の上の
  文字が読めなくなるため。差はゼロにしない)。
- **底面の蝶番は周の真ん中の小辺**(`hingeIndex`)。端にすると展開図で底面が
  帯の左端に寄って絵が偏る。
- **落ちる物体を回転させない**(`inertia: Infinity`)。絵が平行投影なので body ごと
  回すと絵まで回り、同じ立体が別の形に見える。
- **落下位置の hash はそのまま使わない。** "t1","t2",… の連番は hash も連番に
  なり、剰余を取っても値がほとんど動かず全部が同じxに落ちて1本の塔になる
  (実際になった)。黄金比の定数を掛けて桁を混ぜる(`frac`)。
- **床の高さは CSS変数 `--nav-h` から読む**(数字を二重に持たない・§50)。
- 展開図は `createPortal` で body 直下へ(`.app-track` の中に position:fixed を
  書くと祖先の transform が包含ブロックになって画面外へ飛ぶ・§26.1)。

### 52.4 大きさ = 重要度 × 切迫度(`lib/taskSize.ts`)

期日なし/8日以上/3〜7日/1〜2日/今日以前 の5段の切迫度と、重要度(小中大)を
**0.55 : 0.45** で混ぜる。★半々にすると「どうでもいいが今日が期限」のものが
「重いが期日は先」のものより大きくなり、大事なものが山に埋もれる(単体テストで
実際に起きたので比率を変えた)。

### 52.5 性能

rAF は「このアプリが表示中」かつ「起きている物体がある」ときだけ回し、全部
寝たら止める(matter.js の `enableSleeping`)。matter.js は effect の中で
dynamic import(leaflet と同じ手)。毎フレームの値は ref と canvas だけで扱い、
React の state は動かさない。
実測(4倍スロットリング・本番ビルド): 横スワイプ6回 105ms / 落下中 535ms /
**静止後 0ms・他アプリで 0ms**。

### 52.8 見え方の作り直し(2026-08-12続報・ユーザー指定)

参考画像(Topple Towers / 円周上に配置されたカード)をもとに3点。

**重力タブ: 柱を倒して底面をこちらへ向けた姿にする。**
見えるのは**底面の形そのもの**(`baseOutline`)。円柱=円 / 半円柱=半円 /
三角柱=三角 / 四角柱=四角。バウハウスの基本図形が平らな色面として積み上がり、
面の数(=情報の揃い具合)も図形の違いとしてそのまま読める。
- **描画は body の実際の頂点から引く**(`body.vertices` / `circleRadius`)。
  自前の輪郭を別に持つと、`fromVertices` が重心へ寄せるぶん絵だけ浮く。
- **回転を許可した**(`inertia: Infinity` を外した)。絵が平面図形になったので
  body ごと回っても形が破綻しない。丸いものは転がり、角のあるものは止まる。
- 物理の形も底面の形。3面だけ `Bodies.circle`、他は `Bodies.fromVertices`
  (どれも凸なので poly-decomp は要らない)。
- 性能はむしろ軽くなった(落下中 535ms → **0ms**。面ごとの多角形を毎フレーム
  描いていたのが、1つの塗りで済むようになったため)。

**タグで色が付く。** 固定の6つ(仕事/買い物/暮らし/からだ/ひと/まなび)。
定義の正は `lib/taskTags.ts`、色は既存アクセント4色 + 同じ register の
PLUM/SLATE。展開図で選ぶ。★タグを変えたら山の色も変わるよう、同期のたびに
既存の piece の色を引き直している(作成時に固定しない)。

**候補タブ: 円環のカバーフロー。** 候補が輪に並んで奥へ広がり、手前の1つだけが
はっきり見える。左右に払うと回り、離すといちばん近いものへ寄る。
- CSS の 3D は使わない。円環上の位置と遠近の縮みを JS で計算し、
  **2Dの translate と scale だけ**を与える。
- ★**輪の角度を狭くしないこと**(`stepFor` の上限 1.15rad)。角度が小さいと
  cos がほとんど変わらず、隣の候補が同じ大きさ・同じ濃さで並んで「輪」では
  なく「団子」に見える(実際そうなった)。
- 手前の1つだけ `pointerEvents:auto`。題は輪を回すたび ref 経由で書き換える
  (毎フレームの再レンダーをしない)。追従は window に張る(§7.26)。
- これに伴い `components/FloatingBubble.tsx` は使われなくなったので削除した。

**動作確認用のダミー**(`lib/taskDemo.ts`)は、候補も山も4つの図形が揃うように
選んである。**完成時に撤去する**。＋ボタンは常時・右下(`TaskAddButton`)。

### 52.9 大きく・ふわふわ・惰性・色の自動割り振り(2026-08-12続報)

- **候補の輪を大きく**: 立体 132→186px、輪の半径 150→215。手前の1つが
  画面の主役になる。両隣は画面の端で切れるが、輪が画面の外へ続いている
  絵として読めるのでそのままにしてある。
- **ふわふわ浮かせる**: 輪の回転(JSが外側のdivのtransformを書く)とぶつからない
  よう、**内側のdiv**に CSS の keyframes(`.drift-bob`)を掛ける。毎フレームの
  計算はゼロ。速さと位相は id から決めるので、隣どうしが揃って動かない。
  ★**このアプリを見ていない間は `animation-play-state: paused`**。列は常に
  マウントされたままなので、放っておくと裏で合成し続ける(実測で他アプリに
  いる間も 118ms/1.5秒 の負荷が出ていた。止めて 0ms)。
- **払うと惰性が乗る**: ドラッグ中の速さ(index/ms)を平滑化して持ち、離した
  ときに `COAST_MS` ぶん流れた先から行き先を決める。速く払えばいくつも送られ、
  ゆっくり動かせば隣で止まる。★**指を止めてから離したときは惰性ゼロ**
  (最後に動いたときの速さが残り続けるのを防ぐ。声の記録のダイヤルで踏んだ
  のと同じ罠・§43)。流れている途中に掴むとその場で止まる(`glideRef`)。
- **山の図形も大きく**: `MIN_SIDE` 34→52 / `MAX_SIDE` 96→138。
- **タグ(色)をAIのデータが入った時点で自動で割り振る**: `lib/taskTags.ts` の
  `inferTag` が題と5W1Hの言葉から見立て、`parseCandidates` が取り込みのときに
  当てる。Coworkが `- タグ:` を書いてくればそちらが優先。本人は展開図で
  いつでも変えられる。語は部分一致で、上に置いたタグほど優先(からだ→仕事→
  ひと→まなび→買い物→暮らし)。

検証: タグの見立ての単体テスト9件PASS。性能(4倍スロットリング・本番ビルド):
横スワイプ **0ms** / 落下中 153ms / 静止後 **0ms** / 他アプリで **0ms**。

## 53. ★★タスクアプリ: 立面2枚のベタ塗り図形へ(2026-08-13)

§52 の版(5W1H・6タグ・折りたたむ展開図)を新仕様へ作り直し、さらに一度
アイソメの立体で作ったものを**立面2枚**へ作り直した。参照画像4枚(色面の円が
画面いっぱい / Topple Towers の積み木 / 1文字ごとに書体が違うステッカーの
ポスター / Strelka Institute のグリッド)で示された狙いに合わせてある。
**§52 の記述はこの節で上書きされる**(以下が正)。

### 53.1 確定した仕様(すべてユーザー確認済み)

| 論点 | 決定 |
|---|---|
| 投影 | **アイソメは使わない。真横から見た立面2枚だけ**。「システム的に3Dである必要はない」(ユーザー明言)ので、3D座標・投影・陰影・凸包はすべて持たない |
| FRONT | **長方形**(`len × 2r`)。スラブの切れ目入り。**タスクのタイトル**を図形いっぱいに |
| BOTTOM | **断面の形**(円/半円/三角/四角)。**形は正しいまま**(円は正円)足あとの中央へ。**タグの英字**を図形いっぱいに。長方形は描かない |
| 色 | **タグの色を図形の全面に** |
| 側面の情報 | Title / When / Context / Belongings の4つ。文字として出るのは**タイトルとタグ名だけ**で、他は「埋まっている数=断面の形」としてだけ効く |
| タグ | **5つ**(WORK / LIFE / WELLNESS / SOCIAL / GROWTH)。旧 `shopping`→LIFE。英字のみ |
| スラブ | サブタスク n 個 = n 枚。**済ませるたびに1枚消え、短く・軽くなる** |
| 文字 | 白か黒(下地の輝度で選ぶ)。できるだけ大きく。**1文字ごとにランダムな書体** |
| 大きさ | 図形の基本サイズは `UNIT` = **64**(2026-08-13に2倍へ) |
| 設定画面 | 画像4のような**方眼の強調**。**明るいグレー地＋RUST の細い罫線**。地は他の画面と揃える |

**寸法の対応**:
```
横幅   len    = タイトルの文字数 × 手順の残り     lib/taskSize.ts の lenOf/specOf
高さ   2r     = 重要度(小/中/大)。物理の重さも    radiusOf / massOf
断面の形      = 埋まっている側面の数(1..4)        sidesOf / lib/solid.ts の section
スラブ        = 残っている手順                    slabsOf / slabRects
色            = タグ                              lib/taskTags.ts
落ちてくる順  = 切迫度(期日)                      dropOrder
```

- `lib/textFit.ts`(新) … 1文字ごとの書体割り当て・箱に最大で収める・白黒判定・

- `components/tabs/GravityTab.tsx` / `DriftTab.tsx`。
- `app/layout.tsx` … 書体を追加。`lib/constants.ts` … `FONT_FACES`。
- 削除済み: `lib/prism.ts` / `components/tasks/PrismSolid.tsx` / `TaskNet.tsx`。
- 移行は `lib/dataStore.ts` の `migrate()`(旧5W1H→`context`/`note`、旧タグ→新タグ)。

### 53.3 設定画面(`TaskSheet.tsx`)

立方体の展開図(4×3の階段型)を巨大なオン/オフのマスにし、**画面いっぱいの方眼**
(`repeating-linear-gradient`、RUST 1px)の上に乗せる。

```
[WEIGHT] [        いまの図形(FRONT のプレビュー)        ]
[TITLE ] [WHEN] [CONTEXT] [BELONGINGS]
[      ] [    ] [       ] [   TAG    ]
```
- 未入力 = 方眼のまま(地)＋RUST の細い枠 / 入力済み = ベタ塗りの色面。
- WEIGHT はタップ/縦スワイプで循環、TAG はタップで5つを循環しマスの色が変わる。
- 中央4マスはタップで画面いっぱいに開いて入力。SUBTASKS と FREE TEXT は外。
- **方眼の目盛りはグリッドの実測値を CSS変数 `--cell` として配って一致させる**
  (`NetGrid` が ResizeObserver で書く)。★`--cell`/`--gx`/`--gy` の既定値を
  ルート(`data-task-sheet`)に持たせておくこと。無いと `var()` が不正になり
  罫線ごと描かれない(実際に一度そうなった)。

### 53.4 ★守ること(破ると壊れる)

- **CSS の 3D 変形は使わない**(§5・§7.9・§7.14・§7.32・§7.35 で Safari の
  描画崩れを5回踏んでいる)。いまは3Dの概念そのものが無いので該当箇所も無い。
- **canvas の `ctx.font` は CSS変数を解決できない。** `var(--font-…)` を含む
  文字列を代入すると黙って失敗し、既定の 10px サンセリフのままになる(実際に
  そうなって文字が豆粒になった)。`lib/textFit.ts` の `resolveFamily` が
  `getComputedStyle(document.documentElement)` で一度だけ解決してキャッシュする。
- **★文字はグリフのアトラス経由で描く。** 和文のWebフォントは unicode-range で
  数百の @font-face に分割されており、`fillText`/`measureText` は
  **(書体, 文字) の組ごとに初回 5〜10ms** かかる。1文字ずつ書体を替えるこの
  設計で素直に描くと、7個を落とすだけで **fillText 合計 2.4秒**(実測)。
  同じ (書体, 文字, 色) は一度だけ小さな canvas へ描き、以後は `drawImage` で
  使い回す。アトラスに入れるのは **1フレームに `GLYPH_BUDGET`(1)枚**だけで、
  揃うまでその図形はタグ色のベタ塗りで置いておく。
- **`document.fonts.load()` の Promise は必ず `.catch()` する。**
  読めない書体があると unhandled rejection になり pageerror が飛ぶ。
- **書体が届いたら(`onFontsReady`)アトラスとビットマップを捨てて描き直す。**
  最初の数フレームは fallback の書体で焼かれている。
- **和文のGoogleフォントはウェイトを増やすとビルドが落ちる。** 1書体につき
  100以上の断片を取りに行くため、3書体×3ウェイトで turbopack が
  `Module not found` を出した(実測)。**各1ウェイトに留め、太字・斜体は
  ブラウザの合成に任せる**(`app/layout.tsx`)。`.next/static/media` は 12MB。
- **物理の形は FRONT の長方形1つだけ。ビュー切替では body を作り直さない**
  (作り直すと山が崩れる)。形が変わったとき(手順を済ませて短くなった等)だけ、
  位置と速度を引き継いで差し替える(`sameShape` で判定)。
- 検証スクリプト: 3アプリの列と nav は常にマウントされている。
  `getBoundingClientRect().x ≈ 0` で見えている列を特定し、その中に限定して探す。
  タブの `aria-label` は日本語。**`migrate()` は `wishes` が無い状態を「最古の
  形式」とみなして全部捨てる**ので、localStorage に状態を差し込むテストでは
  必ず `wishes` を置く。

### 53.5 検証

`npx tsc --noEmit` / `npx eslint .`(既知の `<img>` 3件のみ)/ `npm run build` 通過。

## 54. ★★★入力画面とキーボード: `--vvtop` を14巡かけて捨てるまで(2026-08-19・第24巡)

第10〜23巡は**タスク入力画面（`TaskComposer`）だけ**を直し続けた。実機（iPhone の
ホーム画面に追加した PWA）でキーボードを出すとレイアウトが崩れる、という一点。
現行の結論は `docs/project_knowledge.md` §4 が正。ここには**外し方の記録**を残す。

### 何が起きていたか（第24巡に確定）

キーボードを出すと、入力画面の中身が画面の半分ほど**下へ落ちる**。上のバー
（DELETE / CONFIRM）が画面の真ん中に来て、名前の帯と図形がキーボードの裏に隠れる。

原因は `[data-fit]`（中身を包む1枚）に掛けていた
`transform: translateY(var(--vvtop))`。`--vvtop` の出どころは
`visualViewport.offsetTop` ただ1つだった。持ち上げ量を `--kb = K` とすると:

| 部品 | 補正ありの位置 | 正しい位置 |
|---|---|---|
| 上のバー | `y = --vvtop` | `y = 0` |
| 帯の下端 | `y = 100lvh + --vvtop − K` | `y = 100lvh − K` |
| 図形の中心 | `y = --vvtop + (100lvh − K)/2` | `y = (100lvh − K)/2` |

`--vvtop ≒ K` を入れると、報告された崩れ方が**3か所とも一致する**。つまり
**iPhone は `offsetTop` にキーボードの高さを返すが、`position: fixed` の器は
ずれていない**。補正がまるごと余分だった。

### なぜ14巡も外し続けたのか（★ここが教訓）

1. **確かめられない読みを式に足した**。第21巡の `window.scrollY`、第18巡の
   `offsetTop` — どちらも「iOS はこう振る舞うはずだ」という読み。この環境で
   WebKit を動かせない以上、式は永久に確かめられない。
2. **第22巡の「測って直す」は、物差しが循環していた**。残りを
   `印の rect.top − vv.offsetTop` で測っていたので、`--vvtop = offsetTop` を
   当てた瞬間に**必ず 0** になる。**疑っている値そのものを物差しにしていた**ので、
   「`offsetTop` が当てにならない」という誤りだけは構造的に検出できない。
   第23巡が `SHIFT_CAP` について同じ循環に気づいていたが（「基準が `offsetTop`
   自身なので疑っている値が大きいときは素通りする」）、それが**補正の本体にも
   効いている**ことまでは繋がっていなかった。
3. **自動検証が崩れを一度も再現していなかった**。Chromium は素で
   `visualViewport.offsetTop` に 0 しか返さない。だから「Chromium では全部通るのに
   実機だけ崩れる」が14巡続いた。

### どう決着したか

★**`visualViewport.offsetTop` を偽装すれば、実機と同じ条件を Chromium で作れる**
（値は返るが `fixed` の器は動かない）。第24巡でこれを入れたら、上の3か所が
そのまま落ちた ＝ **初めて実機の崩れを開発環境で再現できた**。
`scratchpad/vvtop24.mjs` と `scratchpad/fix24.mjs`。

直しは**補正の削除**。キーボードは `--kb`（＝ `器の offsetHeight − vv.height`。
`offsetTop` が一切混ざらない式・第18巡で確定）**だけ**が運ぶ。

★第18巡の「上のバーが画面の外へ出る」は `--vvtop` が直したことになっていたが、
**同じ巡で `--kb` の式も直している**。あの崩れは `--kb` の式にずれが紛れ込んで
いたのが原因で、`--vvtop` は最初から要らなかった可能性が高い。
**1つの巡で2つ直すと、どちらが効いたか永久に分からなくなる。**

### 開発用に残したもの（★次巡で撤去する）

- `components/tasks/legacyShift.ts` … 旧方式ひとそろい。設定の
  「ずれの補正を試す（旧方式）」で呼び戻せる。実機で見比べるためだけ。
- `components/tasks/ViewportProbe.tsx` … 数値表示。第24巡で
  **物差しが循環していない値**へ入れ替えた（`shl` = 器の rect.top /
  `doc` = html の rect.top / `bar` = 上のバーの rect.top をそのまま）。
  `shl` が 0 なら器は見えている領域に貼り付いている ＝ 補正は不要。

## 55. ★★デザインシステムの正規化 — 「語彙はあったのに守られていなかった」(2026-08-23・第33巡)

「スペーシング・ボタン・タイポが不規則」という体感の**真因は、新しい仕組みが
足りないことではなく、第26巡で作った語彙が守られていなかったこと**だった。
実測すると次のとおり。

| 項目 | 第33巡の直前 |
|---|---|
| `fontSize` | 約25種類（8 / 8.5 / 9 / 9.5 / 10 / 10.5 / 11 / 11.5 / 12 / 12.5 / 13 / 15 / 15.5 / 16 / 17 / 18 / 19 / 20 / 22 / 24 / 26 …） |
| `gap` | 2〜12 の連番がほぼ全部 ＋ 16 / 22 / 24 |
| `borderRadius`（角のある方） | 2 / 6 / 8 / 9 / 10 / 12 / 14 / 16 / 18 / 20 / 22 / 26 / 28 |
| 直書き `cubic-bezier` | 17箇所 |
| 直書きの時間 | `globals.css` だけで約20種類。`var(--t-*)` は14箇所しか使われていない |
| 共通ボタン部品 | **存在しない**（`<button>` が20ファイルに散在） |

### 教訓1 — **語彙は「作った」だけでは効かない。機械で検査できる形にして初めて効く。**
第26巡で曲線を8→4本に統合したが、その後の7巡で 17箇所の直書きが積み上がった。
今回は `CLAUDE.md` に **grep のチェックコマンドを載せた**。数字が0件でないと
終われない形にしないと、また同じ速度で腐る。

### 教訓2 — **自分の規約に反する数字は、規約を読める人でも足してしまう。**
`globals.css` の冒頭に「対称な ease-in-out は使わない」と書いてあるのに、
`cubic-bezier(0.34,1.56,0.64,1)`（**跳ね返る**曲線）が `common.tsx` と
`BottomSheet.tsx` に入っていた。跳ね返りは「気持ちいい」ので手が伸びる。
**規約は、破った瞬間に見える場所（＝共通部品）へ実装を寄せることでしか守れない。**

### 教訓3 — **二重定義は「後勝ち」で静かに規約を無効化する。**
`@keyframes tab-in` が2つあり、後にある方が `translateY(7px)` を持っていた。
先にある方には「**transform を乗せると、下部固定バーがこの祖先を
containing block と見なしてガクつく**」という理由付きのコメントがあったのに、
それが丸ごと上書きされていた。opacity のみの側へ一本化した。

### `--t-out` を 350ms → 600ms へ戻した（ユーザー確定）
第27巡に「閉じるのはきびきび」として 600 → 350 にした判断を、**シネマティックな
手ざわりを優先して戻した**。開く 700 / 閉じる 600 の非対称は残る。
★これが第33巡でいちばん体感の変わる数字。**戻すときは `app/globals.css` の
`--t-out` と `lib/motion.ts` の `T_OUT` の2つを必ず同時に直す。**
なお `.tc-lamp`（現 `.press`）のコメントは「離すと上の 600ms で戻る」と書いて
あったので、350ms だった間は**押下の戻りだけが道連れで短くなっていた**。
600 に戻したことでコメントと実装が一致した。

### 入力欄の自動ズーム（ついでに直った実バグ）
`input` / `textarea` の文字が 12 / 12.5 / 13 / 15 のまま残っている欄が7つあった。
**iOS Safari は 15 以下の入力欄にフォーカスすると画面を勝手に拡大し、以後
レイアウトが崩れたまま戻らない。** 目盛りの `lead` を 16 に置いたのはこの閾値に
合わせるためで、全部 16 以上にした。入力画面（TaskComposer）の行も 15 → 16。

### shadcn/ui を入れなかった理由
ユーザーへ提示して確定（2026-08-23）。shadcn は Tailwind + Radix が前提で、
このプロジェクトの「全インライン style」と真っ向から衝突する。加えて中身の
大半は canvas と自作 SVG（`GeoType` / `SolidCanvas` / matter.js / Leaflet）で、
汎用キットの効く面が少ない。**汎用キットで平均へ寄せるより、目盛りと共通
ボタンを自前で持つ方が、揃う度も個性も上がる。**

## 56. ★候補の円環カバーフローと、それをやめた理由 (2026-08-18〜第12巡 / 第38巡に撤去)

第38巡に DRIFT を**散らして浮かべる**形へ作り直したので、円環はもう無い。
ここは「なぜ作り、なぜやめたか」と、**円環で3回踏んだ切れ目の罠**の記録。

### やめた理由
縦の空間（`components/tasks/TaskSpace.tsx`）を作ったことで、DRIFT は
「GRAVITY の**真上**にある浮遊層」という位置を持った。輪は「手前の1つを選ぶ」
ための形で、奥行き方向の物語しか語れない。層として見下ろせる場所になった
以上、**漂っているものが漂っているように見える**方が正しく、「確定すると
その場から真下へ落ちる」という筋も通る。

### ★★「左右が見切れる」の正体 — 直しを2回外している
2026-08-18・第12巡でようやく特定。**輪の面が画面より 16px 内側だった**。
列の左右パディング（`padding: … 16px`）が効いていたので、隣の図形が
**画面の端ではなく 16px 手前で直線に切れて**いた。

外した直し … ①図形と半径を縮めて収める（第10巡）②`mask` で端を薄れさせる
（第11巡）。どちらも**切れ目の位置**を見ていなかった。

**教訓 — 「はみ出しが汚い」と見えたら、まず切れ目が**どこ**にあるかを測る。
見た目を弱める（縮める・ぼかす）のは、切れ目の位置が正しいと確かめた後。**

### ★`overflow` は `hidden` ではなく `clip`
`hidden` は**送れる箱**を作るので、はみ出したぶんを iOS が横に送れてしまう
（入力画面でも同じ罠を踏んだ）。`clip` は箱を作らずに切るだけ。
**この教訓は円環をやめた後も生きている。**

### 数字（参考）
`SOLID_W 300 / SOLID_H 190 / SPREAD 300 / FOCAL 1.9 / DRAG_PER_ITEM 150`。
輪は一周し、並びの差を `wrap(i - pos, n)` で輪の長さに折り返してから角度に
していた。端の抵抗も上限も持たない。
