## 0. このアプリは何か

ユーザー本人 1 人のための PWA。タスク管理アプリではなく、
**「やりたいこと」を集め・実行し・記録として綴じる**ための道具。

**絶対に守るユーザーの設計思想**
- タスク化しない（義務や TODO の消化にしない）
- 設定画面を増やさない（`ProfileTab` が唯一の設定で、これ以上増やさない）
- 説明文を置かない（本人専用アプリなので、使い方の案内は不要）
- OS 標準のフォーム UI（ドロップダウン・標準テキストボックス・チェックボックス）を
  使わない。**純粋な幾何学図形・ベタ塗り・太いタイポグラフィだけ**で画面を構成する。
  ★**角丸と円は使ってよい**（2026-08-16 にユーザー指定で改訂）。むしろ
  アプリの語彙は「丸」— タブバーのピル、丸ボタン、`borderRadius: 22` の
  カード。ここから外れた「角の立った矩形だけの画面」は他から浮くので不可。
  使ってよい丸みは **22（板）/ 999（ピル）/ 50%（丸）** の 3 つだけ。
  影は `SOFT_SHADOW` / `SOFT_SHADOW_LG`。
  ★ただし**タスクの図形そのもの**（円・半円・三角・四角）は角を立てたまま。

## 1. アプリの構造

3 つのアプリを、**タブバーの帯を横に払って**行き来する（`lib/apps.ts` が正）。

| 順 | アプリ | `en` | タブ |
|---|---|---|---|
| 0 | ジャーナル `journal` | JOURNAL | レコード `journal-record` / 今日 `journal-today` / アーカイブ `journal-archive` |
| 1 | タスク `tasks` | TASK | 候補 `tasks-drift` / タスク `tasks-gravity` |
| 2 | ブリーフ `life` | EXPLORE | ブリーフ `brief` / ゴール `goals` / ストック `stock` / プラン `execute` |

- 右端からさらに右へ払うと先頭へ**回り込む**（一周ループ）。位置は 0〜2 に
  丸めない**通し番号 `pos`** で持つ。丸めると端で位置が飛ぶ。
- **3 つの列は常にマウントされたまま**。初回描画後に `requestIdleCallback` で
  残り 2 つを先読みし、以後アンマウントしない。
- アプリごとに最後に見ていたタブを覚える（`tabByApp`）。
- 画面左上（`Masthead`）は**アプリ名**（EXPLORE / TASK / JOURNAL）を
  幾何アルファベットで。タブ名はタブバーのアイコンの下に小さく出す。

### ダッシュボード
画面下から引き上げる共通の引き出し（`components/Dashboard.tsx`）。
どのアプリからでも開ける。中身は「選んでいるカード」と「今日のタスク」、
下端に **「今日を終える」**。これで選んだカードは `done` になりアーカイブへ移る。
開き具合は 0〜1 の連続値 `--dash` で、指の位置と 1 対 1。

**メタファー（§38 で確定した体験の構造）**
- Journal … 音声の抽出（テープを巻き、切り出す）
- Task … 落下と粉砕
- Explore … 立体の展開と結合
- 1 日の終わりに 3 要素が 1 枚の幾何学ポスターへプレスされる（**未実装**）

## 2. データモデル（`lib/types.ts` が正）

- `Item` … ストック／プラン／アーカイブに出る「願望の対象物」。
  `kind`（place/exhibition/live/activity/food/movie/book/album/info/thing）×
  `area`（場所の有無は種類と独立の直交軸）。
  `status: candidate → planned → done`、`origin: brief | manual | wish | info`、
  `lat/lng/placeId`、`goalId?`、`expiresAt?`。
  分類の入口は `domainOf(item)`（`lib/helpers.ts`）ただ 1 つ。
  4 ドメイン `ItemDomain = place | experience | info | thing`
  （バショ／タイケン／ジョウホウ／モノ）。
- `Wish` … ✨で書く受信箱。`category: ItemDomain`。KEEP されて初めて Item になる。
- `Goal` / `CheckIn` … ゴールのバインダーと記録。
- `Task extends TaskSides` … §4 参照。面は `SIDE_KEYS = title / due / context /
  belongings` の 4 つで、埋まった数がそのまま図形になる。
  ★2 番目は **`dueDate`（YYYY-MM-DD）**。自由文の `when` は 2026-08-16 に廃止し、
  `migrate()` が「日付なら `dueDate` へ / それ以外は `context` の先頭へ」畳んだ。
  同じ「いつ」が自由文と期日の 2 箇所にあると、大きさ（切迫度）に効くのが
  どちらか読めなくなるため。
- `InboxCandidate extends TaskSides` … Cowork が声のメモから作った候補。
  `dueDate` を持ち、確定するとそのままタスクの期日になる。
- `JournalEntry` / `VoiceNote` … ジャーナルと声のメモ。
- `BriefCard` / `GrowthCard` … ブリーフのデッキのカード。
- `AppState` … 上記すべての入れ物。
  - `generatedDecks: Record<"YYYY-MM-DD", BriefCard[]>` と `cronStatus` は
    **サーバー（夜間 Cron）が所有**する（`lib/dataStore.ts` の
    `SERVER_OWNED_KEYS`）。クライアントは読むが上書きしない。
  - `magazine` / `weekendMeta` / `shelfOrder` は**もう更新されない**
    （それを使っていた UI が廃止済み）。型は互換のために残してある。

**永続化** … `lib/dataStore.ts`。3 モード（cloud / persistent / memory）。
Supabase の環境変数があり、かつログイン済みのときだけ cloud。
localStorage のキーは `qol-app-state-v1`。

★`migrate()` は `wishes` が無い state を**最古の形式とみなして全部捨てる**。
テストで localStorage に state を差し込むときは必ず `wishes` を置くこと。

## 3. デザイン言語

**テクスチャを排除し、ベタ塗りの色面・直線・円などの純粋幾何学**（§38 で確定）。
角度は 0 / 45 / 90 / 180 度のみ。

### ★★★質感 ── **平均 128 を `soft-light`**（第76巡に根治／第77巡にしわ紙へ）

**券も図形も同じ 1 枚**（`public/crumple.webp`）。違うのは**乗せ方**だけ …
券は DOM なので CSS の面（`lib/printGrain.ts`）、図形は canvas に焼き込む
（`lib/paperTexture.ts`）。第75巡までの「券は板紙・図形は切った紙。混ぜない」は撤回済み。

★★★**テクスチャは明暗だけを足すもので、色を変えるものではない。**
乗せたあとの**平均の色が動いていたら、それは質感ではなく色の変更**である。

#### 何が「濁って」いたか（第76巡に実測で特定した2つのバグ）

- **図形** … `paperTexture.ts` が **赤チャンネル**（`d[i]`）を読みながら、**輝度**の
  中央値（`PAPER_MID = 161/255`）と比べていた。クラフト紙の写真は赤の平均が **175**
  なので、ほぼ全画素が「明るい側」＝**白**へ倒れた（実測で**白側 0.287 ／ 黒側 0.012
  ＝ 96% 白**）。凹凸ではなく**白の薄塗り**。`PAPER_GAIN 5.0` の飽和で**純白の斑点**
  にもなり、点の1つ1つは彩度ゼロだった。★★**読む量と比べる量を揃えていなかった**、
  それだけのこと。1行のバグ。
- **券** … `Ticket.tsx` が**茶色いカラー写真**を `multiply` 0.42 で敷いていた
  （実効 R×0.868 / G×0.840 / B×0.809 ＝ 13〜19% 暗く、青だけ 6pt 余計に落ちる）。
- ★★**色相は動いていなかったので気づきにくかった。動いていたのは彩度。**

#### 直し方（規則）

- タイルは **平均 128 の無彩色**。**128 は `soft-light` の恒等点**なので地の色は
  **原理的に**動かない。生成物は平均を合わせ込む（頭打ちで逃げるので、書いてから
  測って戻す。実測 127.99）。
- ★★**`multiply` を使わない。** 原理的に**暗くしかできない**ので、質感だけを乗せる
  ことができない。実測 … `multiply` は **ΔE 0.135・彩度 −20%**、`soft-light` は
  **ΔE 0.001・彩度そのまま**（142,884 画素）。しわ紙でも **ΔE 0〜0.005**（262,144 画素）。
- ★★canvas のブレンドは Porter-Duff の `source-over` で合成されるので、**透明な地にも
  乗る**。焼く前の絵を控えて、`soft-light` のあと `destination-in` で**元の α に切り抜く**。
- ★★★**しわは低い刻みなので拡大縮小してよい。網点は高い刻みなのでいけない。**
  **どちらの規則を当てるかは、テクスチャの刻みで決まる。**
  ・しわ（`crumple.webp`・512px角）… ばらつきの **73%** が低い刻み（全体 sd 9.54 に
    対し 8px でぼかしても 7.00 残る）。だから**繰り返さず**、面いっぱいへ伸ばす
    ―― **継ぎ目もタイルの周期も存在しない**。図形は絵ごとに
    **向き4つ × 切り出す場所 × 切り出す大きさ**で散らす。
  ・網点（`halftone.webp`・126px角。第76巡。**戻せるように残してある**）…
    **1画像画素 = 1デバイス画素**で敷く（伸ばすと点が太って「水玉」になる）。
    継ぎ目は**整数周期（9px × 14 = 126）で切って**構造として消す。
- ★写真から作るときは**照明のかたよりだけを抜く**（半径 96 のぼかしを引く）。
  実測でこの写真は四隅 220〜235 の傾きがあり、そのまま敷くと図形の片側が必ず暗くなる。
  ★★★第64巡の教訓「**写真を加工するな**」は、**粒を増幅し低い刻みを削った**話。
  ここで抜くのは**照明**で質感ではない ―― **同じ「ハイパス」でも半径が2桁ちがえば
  別の操作になる。** 取り違えないこと。
- 強さの目盛りは **`PAPER_ALPHA`（図形 0.5）と `GRAIN_ALPHA`（券 0.55）の2つだけ**。
  ★平均が 128 に固定されているので、**ここをいくつにしても地の色は動かない**。
- ★`paper-kraft.webp` / `make-paper.py` / `print-grain.webp` / `make-grain.mjs` /
  `halftone.webp` / `make-halftone.mjs` は**まだ消していない**（テクスチャを
  試している最中）。決まったらまとめて消す。

### ★★基本のUIフォント（`lib/constants.ts`）— 2026-08-24・第53巡にユーザー確定

**欧文は Archivo、和文は Noto Sans JP。**「ブルータリズム/スイスに合う、太めで
幅が少し詰まった、洗練された書体」というユーザー指定に対して **Archivo**（可変
フォント）を選んだ。適用範囲は**アプリ全体の欧文**（3アプリで声を1つにする）。

- **幅** … Archivo は `wdth`(62〜125) の軸を持つ。`app/globals.css` の `body` に
  `font-variation-settings: "wdth" 88` を置き、**全体を少し詰める**。和文の Noto は
  この軸を持たないので無視される。`ctx.font`（canvas の図形の文字）にも掛からない。
- **太さ** … 使う場所で `fontWeight`（見出しは 700〜800）。★★★`app/layout.tsx` で
  **`weight` を固定で渡さないこと**。渡すと可変でなくなる。
  ★第73巡に踏んだ … `Noto Sans JP` を `["400","500","700"]` の固定3本で読んでいて、
  **`WEIGHT.heavy`(800) が和文で出ていなかった**（13箇所が影響）。
  ★★**確かめ方**：`document.fonts.check` は**近い太さへ落ちても true** を返すので
  使えない。**描いたインクの量**（canvas に描いて α を合計）を測る。
  和文は幅では測れない（どの字も 1em 幅）。実測 …
  直す前 400=841 / 500=1055 / **700=800=900=1319**（3段）→
  直した後 841 / 1055 / 1319 / **1450** / **1587**（5段）。
  ★第74巡に再測して 5/5 段が別値のまま（欧文 Archivo も 758/877/1117/1293/1531）。
- ★★**`WEIGHT.black`(900) は券の題だけ**（2026-08-31・第74巡にユーザー指定）。
  `design.md` §5-2 の「太さは2値。中間を作らない」に反しないのは、900 が
  **中間ではなく上の端**だから。`heavy`(800) が数字の主役専用なのと同じ扱いで、
  **増やさない**。上の可変フォントの直しが先に入っていたから使えた段。
- **並び順が「欧文だけ Archivo」を作っている** … 和文は Archivo にグリフが無いので
  自動的に次点の Noto Sans JP へ落ちる。
- ★★**`Noto Sans JP` ＝ 源ノ角ゴシック**（Adobe 名 Source Han Sans と同じ書体。
  Google 名が Noto Sans CJK JP → Noto Sans JP）。**和文はすでに源ノ角**で、
  源ノ角でないのは**欧文だけ**。
- ★第73巡に **`SERIF` / `DISPLAY` という別名を消した**（中身はどちらも `SANS`
  だった。12箇所を直した）。**`--font-anton` も撤去**（使い手 0 件）。
```
export const SANS  = 'var(--font-archivo), "Archivo", var(--font-noto-sans-jp), "Noto Sans JP", sans-serif';
export const LATIN = 'var(--font-archivo), "Archivo", "Helvetica Neue", Arial, sans-serif';  // 欧文だけ(旧 HELV)
```
`LATIN`（旧 `HELV`）は**和文フォールバックを含めない**並び。数字・曜日・#タグの
ように、ラテン文字だけをスイス・スタイルで置く場所で使う（和文が混じると数字の
骨格が Noto の字面に寄ってグリッドが崩れる）。

#### ★★★メイン5色の選び方 ―― 目で選ばない

ユーザー指定は「**単純な濃さとかではなく**、このカラーパレットの雰囲気を作る上で
**理論的に重要**なカラーとし、できるだけ**バランス**をとってください」。
**4つの尺度**で全ての組を採点して決める:

| 尺度 | 第77巡 | 第76巡 | 意味 |
|---|---|---|---|
| 色相の最小隔たり | **28.0°** | 6.2° | 円を均等に覆うか |
| 明度の幅 | 0.671 | 0.671 | 暗・中・明がそろうか |
| 彩度の幅 | **0.182** | 0.152 | 鮮やかと淡いがそろうか |
| 見分け（最小 ΔE） | 0.144 | 0.216 | 山の中で別の色に見えるか |

★★★**見分けだけを最大化しないこと。** 第76巡はそれで解いた結果、**赤が2つ**
（朱 34.9° と深紅 28.7° で 6.2° しか離れていない）になり、藤も水も入らなかった ――
**盤の雰囲気が図形に出ない**という形で跳ね返った。見分けは4つのうちの1つでしかない。
★**多いタグ（work / life / growth）は先に離す**。
★★★ただし**第78巡にユーザー指定で役だけ入れ替えた**（wellness 水→杏／
social 杏→黒桜／growth 黒桜→水）結果、**多い3つの見分けは 0.34 → 0.169 に落ちた**。
色の集合は変わっていないので5色の 0.144 は据え置き。**次に色を触るときは、

### ★寸法の語彙（`lib/tokens.ts`）— 持ち主はここだけ

★**UI の規約と目盛りの段は `design.md` が正**（文字の対・余白・配色・動きの表と、
機械チェック13本）。ここが持つのは**なぜその段なのか**と、**目盛りの外に居てよいもの**。

**余白・文字・角丸も名前で持つ**（2026-08-23・第33巡）。動きの語彙が
`lib/motion.ts` にあるのと同じ考え方。第33巡の実測で、`fontSize` が約25種類、
`gap` が 2〜12 の連番ほぼ全部、角のある `borderRadius` が13種類と、
**一点物の数字**で埋まっていた。画面ごとに手ざわりが違う直接の原因だった。

★**段の値は `design.md`（§1 の表と §2）が正**。ここには写さない
（二重に持つと必ず片方が腐る）。以下はその段を決めた理由と、外に居てよいもの。

- `hair`(2) は**罫と光学的な詰め**だけ。それ以外の余白は必ず4の倍数。
- ★**入力欄（`input` / `textarea`）は必ず `TYPE.lead`(16) 以上**。15 以下だと
  iOS Safari がフォーカス時に画面を勝手に拡大し、以後レイアウトが崩れたまま
  戻らない。`lead` を 16 に置いたのはこの閾値に合わせるため。
- `nano`(7) は**小さな操作部品に焼き付いたラベル**（NAME / TAG / 物理キーの名前）
  専用。文章には使わない。使いたくなったら、まず器が小さすぎないかを疑う。

**目盛りの外に居てよいもの**（ここ以外に例外を作らない）
1. `env(safe-area-inset-*)` を含む式 … `TAB_PAD_TOP` / `NAV_BOTTOM_GAP` /
   `NAV_H` / `NAV_OFFSET`。端末が決める値なのでこちらの目盛りには乗らない。
2. **図形の座標系** … `GeoType` / `SolidCanvas` / matter.js / Leaflet /
   `TabIcons` のアイコン内部。これは「UIの余白」ではなく絵の寸法。
3. 噛み合って高さが決まっている部品寸法 … `TAB_MARK`(52) / `NAV_PILL_PAD`(6) /
   `HEADER_CHIP_SIZE`(40)。★タブバーの目印の行（丸 5 + 余白 8 = 13）は
   `NAV_H`(77px) に**組み込まれている**ので、動かすなら両方直す。
4. **スイス見出し**（表示専用の大きな欧文）… `SWISS_XL`(72) / `SWISS_MD`(28)。
   `TYPE` は本文の目盛りなので `display`(26) 止まりで、ブルータリズム／スイスの
   大きな見出しはその外に居る。使うのは GRAVITY の ALIGN と TIMELINE だけ。
   ★**この2つから増やさない。** 第53巡は 72/44/28 の三段だったが、第56巡に
   ALIGN の焦点が 72 へ上がって 44 の使い手が居なくなったので捨てた
   （**使わない段は残さない**）。

### ★ボタン（`components/Button.tsx`）— 押せる面はここだけ

第33巡まで押下の作法が3流派に分かれていた（`useState`＋跳ね返りカーブ /
`data-pressed` を DOM へ直に書く / CSS の `:active` 頼み）。1ファイルへ集めた。

**使い分けは1行で言える … 入力画面（キーボードを出したまま触る面）＝ `Press`
／ それ以外＝ `Button`。**

- `Press` … `<div>`。**`pointerdown` で即座に走る**。`touchstart` の既定動作を
  素の listener（`{ passive: false }`）で止めてフォーカス移動を防ぐ。
  `<button>` を使わないのは、iOS が `<button>` のタップで入力欄を blur するため。
  ★離上を待たないので、**取り返しのつかない操作（削除など）には使わない**。
- `Button` … `<button>`。離上で走る。`variant`（`primary` / `secondary` /
  `ghost` / `icon`）× `size`（`sm` 28 / `md` 36 / `lg` 48）。寸法は `lib/tokens.ts`
  から引く。**輪郭は「文字と同じ色の 45%」**（`color-mix`。以前は BLUE=そのまま /
  RUST=45% / INK=30% とバラバラだった）。1画面に `primary` は1つまで。

4 種を置き、**繋がっているところだけ溝を塗る**。等幅。A–Z と 0–9。

### ★画面の地色（`lib/ground.ts`）— 持ち主はここだけ

**背景が途切れたら、まずここを見る。**

- `html` の `background-color` と **`<meta name="theme-color">` を必ずセットで**
  書く。ホーム画面へ追加した PWA では、**iOS が自分で塗る領域**
  （キーボードの手前の帯・画面のいちばん下・セーフエリア）に theme-color を
  使うので、片方だけ合わせても帯が残る（2026-08-17 に
  `themeColor: "#1A1A18"` の固定値のままだったのが原因で、
  「キーボードのところで背景が途切れる」「全タブの下端で途切れる」の両方が出た）。
- ★★**積み木は「後勝ち」ではなく「高い層が勝つ」**（2026-08-19・第26巡）。
  `pushGround(color, level)` の `level` は `"app"`（アプリの地）か
  `"overlay"`（全画面の面＝入力画面・録音）。**いちばん高い層**が地色を持ち、
  同じ高さなら後から積んだ方。返り値を呼ぶと外れる（`useEffect` の後始末で必ず）。
  以前は素直に「最後に積んだ層が勝つ」だったが、**積む順は重なり順とは無関係**
  なので、入力画面が開いている最中にアプリ側が積み直すと**アプリが地色を
  奪った**。「画面の一番下だけ背景が適応されない」が何度も再発した正体はこれ。
  **書き手を2つにしないこと**（以前 `AppBackdrop` と `TaskComposer` が両方
  `html` を書いていて、閉じても戻らないことがあった）。
- ★★★**塗る人は3人いるが、色を決める人は1人**（2026-08-19・第27巡）。
  第26巡は「時間」だけ揃えて**色そのものが2つある**まま放置していた。
  帆布（`AppBackdrop`）だけが `groundOf(appId)` を直に見ていたので、
  **入力画面が開いているあいだ `html` は暗いのに帆布はアプリの明るい色**
  という状態になる。帆布は `zIndex: -1` で html の上にあるから、
  **html の色は帆布の外側 — 画面のいちばん下 — にしか出られない**。
  これが「一番下だけ背景が適応されない」の残り半分だった。
  いまは `onGround(cb)` で**勝っている色を購読**し、帆布はそれを塗る。
  ★**全画面に色を塗る面は、自分でアプリの色を決めないこと。**
- ★★**帆布の寸法は `position: fixed; inset: 0`**（同巡）。
  `width: 100vw; height: 100lvh` をやめた。iOS のスタンドアロン（ホーム画面へ
  追加した PWA）では `lvh` が下のセーフエリアを含まないことがあり、そのぶん
  **帆布が画面の下まで届かない**。届かない所は端末が manifest の色で塗る。
  `viewport-fit=cover` の固定要素の `inset: 0` は**セーフエリアを含む画面全体**
  なので、`lvh` がどう計算されようと届かない場所が無くなる。
- ★★★★**`apple-mobile-web-app-capable` を自分で出す**（2026-08-19・第29巡）。
  **これが「画面の下端だけ別の扱い」の正体だった。**
  Next は `appleWebApp.capable` から **`mobile-web-app-capable`（Android 用の
  名前）しか出さない**。iOS はそちらを見ないので、ホーム画面から起動した
  アプリが「マニフェスト方式のスタンドアロン」になり、**web ビューが画面の
  下端まで届かない**。実測（実機の写真を画素で解析）… 円が **y=796.7pt で
  どの x でもまっすぐ**切れ、その下 **47pt** はページが一切塗れない領域で、
  そこは **iOS が `theme-color` で塗っていた**。
  だから「コンポーネントが途切れる」「色の変化がそこだけ遅い」「一応色には
  連動する」が全部同時に出ていた。`app/layout.tsx` の `other` で明示する。
  ★**この値はホーム画面へ追加した時点で端末に焼き込まれる。** 反映するには
  一度ホーム画面から消して、追加し直すこと。
- ★★★★**`statusBarStyle` は `black-translucent` のまま**（2026-08-19・
  第29巡・一度 `default` を試して差し戻した）。`default`/`black` は
  「ステータスバーの見た目だけ変える設定」ではなかった —
  **iOS はステータスバーぶんを web ビューの外(OS が別に確保する帯)として
  扱うようになり**、そこが黒い帯として残り、しかも中身全体がそのぶん下へ
  押し出されて**タブバーの位置までずれた**（実機で「上に変な黒い帯」
  「タブバーが下寄りすぎ」と報告）。`black-translucent` は中身が画面の裏側
  まで1枚で伸び、ステータスバーはその上に透けて重なるだけなので、帯もずれも
  起きない。時計とアイコンが白くなって明るい地色の上で読みにくいのは
  **既知のトレードオフ**（iOS の3択にこれ以外の選択肢が無い。第26巡の写真で
  実際に白く潰れていた）。★**この値を変えて試すこと自体を今後もしないこと** —
  `apple-mobile-web-app-capable` だけで下端の問題は解決している。
- ★★★**`theme-color` は毎フレーム自分で混ぜる**（同巡）。CSS では補間できない
  が、**iOS が画面のいちばん下を塗るのはこの値**なので、1回だけ差し替えると
  そこだけ遅れてパッと切り替わる（第26〜28巡は `GROUND_MS / 2` で1回だけ
  書いていた ＝「そこだけ遅い」の直因）。`lib/ground.ts` が `requestAnimationFrame`
  で `GROUND_EASE` と同じ曲線を数値で解き、`GROUND_MS` かけて混ぜる。
  実測 … 動き出しのずれ 0ms・途中 16 色・html と同じころ終わる。
- ★**`app/manifest.ts` の `theme_color` / `background_color` もアプリの地色
  （`BD_GREY` `#ECECEA`）に揃える**（同巡）。この2つは**ホーム画面へ追加した
  時点で端末に焼き込まれ**、iOS が自分で塗る領域に使われる。`#1A1A18` のまま
  食い違っていた。★変えても既にホーム画面にあるアプリには反映されない —
  一度消して追加し直すこと。
- ★★**塗る人は3人いる。時間を必ず揃える**（同巡）。
  ①列（`AppColumn` の地色。`.app-track` の横スライド **380ms**）
  ②帆布（`AppBackdrop`。シェルの外側＝オーバースクロールとセーフエリア）
  ③`html` ＋ `theme-color`（iOS が自分で塗る領域）。
  以前は 380ms / 420ms / **即座** だったので、**画面の一番下だけ先に切り替わった**。
  いまは `GROUND_MS = 380` / `GROUND_EASE`（`--ease-sheet` と同値）を
  `lib/ground.ts` の1か所から配り、①②③が同じ合図で動く。
  ★`theme-color` は CSS で補間できないので、**滑りの折り返し（190ms 後）に
  1回だけ**差し替える。即座だと「下だけ先に」、終わりだと「下だけ遅れて」変わる。
  折り返しならずれは最大でも半分。
  **検証は `scratchpad/ground26.mjs`**（①②③の**動き出した時刻**を毎フレーム採り、
  ばらつき ≦60ms・theme は +100〜300ms を見る。実測 16ms / 182ms）。
  ★★あわせて**画面のいちばん下 1px の色 ==「html の色」==「帆布の色」**を、
  閉じている状態と**入力画面を開いた状態の両方で**見る。
  「開いた状態」が第26巡で抜けていて、そこが帯の正体だった。
- ★新しく全画面の面を作るときは必ず `pushGround` を呼ぶ。
- ★★**積む色は「その画面のいちばん下に見えている面の色」**（2026-08-17）。
  入力画面は地が `CHARCOAL` でも**下端に見えているのは帯（`LIFT`）**なので、
  `pushGround(LIFT)` を積む。`CHARCOAL` を積んでいた頃は、キーボードの手前
  （次候補の帯のあたり）と画面の下端に色の違う帯が出て「境目が見える」と
  報告された。下敷き（全画面のオーバーレイ）も同じ色にする。
  **検証は「画面の最下 1px の色 == `html` の色」**（Playwright で
  `elementFromPoint` の背景を辿る。全タブ＋入力画面で一致することを確認済み）。

### ★モーションの語彙（`app/globals.css` の `:root` ＋ `lib/motion.ts`）

**曲線は4本、時間は5つだけ。増やさないこと**（2026-08-19・第26巡にユーザー確定）。
以前は曲線が 8 種類バラバラに散っていて、画面ごとに手ざわりが違った。

考え方 … **初速を高く、終点へ向けて長く滑らかに収束させる（非対称な減速）**。
対称な ease-in-out は使わない（動き出しと止まりに機械的な硬さが出る）。

| 名前 | 値 | 何に使うか |
|---|---|---|
| `--ease-settle` | `cubic-bezier(0.16, 1, 0.3, 1)` | 主役。定位置への吸着 |
| `--ease-sheet` | `cubic-bezier(0.32, 0.72, 0, 1)` | 面が出入りする（iOS のシート）。**地色もこれ** |
| `--ease-press` | `cubic-bezier(0.4, 0, 1, 1)` | 押し込み。速く沈む |
| `--ease-exit` | `cubic-bezier(0.4, 0, 0.2, 1)` | 去る |

| 名前 | 値 | 何に使うか |
|---|---|---|
| `--t-press` | 90ms | 押した瞬間（指の反応は 0.1s 以内） |
| `--t-in` | 700ms | 大きな面が開く |
| `--t-out` | **600ms** | 閉じる（2026-08-23・第33巡にユーザー確定。第27巡の 350ms を戻した） |
| `--t-item` | 420ms | 中の要素ひとつ |
| `--t-step` | 50ms | 時間差（視線誘導） |

#### カメラ専用の2つ（`--t-cam` / `--ease-cam`）は第52巡に撤去

第38〜43巡は縦のカメラのために `--t-cam`(1400ms) と対称の `--ease-cam` を語彙の
例外として持っていたが、**第52巡にカメラごと撤去**（TOP/UNDER を破棄し GRAVITY の
物理モードへ作り替えた）。曲線4本・時間5つに戻る。★**対称な ease-in-out は環境
ループ以外で使わない**という決めごとは、例外が無くなってなお**そのまま生きている**。

JS 側は `lib/motion.ts` が同じ数字を**秒**で持つ（`T_IN` = 0.7 など）。

#### ★canvas の図形だけは「バネ」（`lib/spring.ts`）— 第55巡

CSS の語彙は**時間とカーブ**で刻む。これは面の出入りには合うが、**たくさんの図形が
それぞれの都合で動く**場面（ALIGN の出入り・TIMELINE の寄せ）に使うと、全部が同時に
始まって同時に止まり、動きが安っぽくなる。canvas と物理の座標系に限って
**バネ（位置と速度の減衰振動）**を使う（`lib/tokens.ts` の「図形の座標系」と同じ扱い）。

- 係数は `K_TRAVEL`/`D_TRAVEL`（遠くへ運ぶ）と `K_SETTLE`/`D_SETTLE`（近くへ寄せる）の
  **4つだけ**。画面ごとに書き散らさない。
- ★**CSS の transition / animation はこれまでどおり曲線4本・時間5つから引く。**
  バネは DOM のスタイルには使わない。
**CSS と JS で数字がずれたら、どちらかを直すのではなく両方をここへ合わせる。**
JS のタイマー（「閉じ終わってからアンマウントする」等）は `ms(T_OUT)` のように
`lib/motion.ts` から引くこと。**数字を書き写さない** — 片方だけ変えると
閉じ切る前に消える。`BottomSheet` の閉じ待ち・`LEAVE_MS`・`POP_OUT_MS`・
`GROUND_MS`・`DIAL_OUT_MS`・`MAP_FULLSCREEN_MS`・`SLIDE_MS`・`DASH_MS` が該当。

★**環境の動き**（止まらずに回り続けるもの）は上の5つの対象外。状態の遷移では
ないので「開く/閉じる/押す」の語彙に乗らない。`--t-amb-load`(3.6s) /
`--t-amb-reel`(3.2s) / `--t-amb-tape`(260ms) / `--t-amb-blink`(1.15s) /
`--t-amb-bob`(5.4s) の5つ。**対称な `ease-in-out` を許すのはここだけ。**

曲線の例外は2つだけで、理由を CSS にその場で書いてある …
読み込み中のループ（対称な in-out。同じ形が延々と行き来するので行きと帰りの
手ざわりが違うと目に付く）と、ダイヤルを画面の外へ捨てる動き（もっと深く沈める）。

これは theme-color の補間に**数値として**必要なため（CSS 変数は JS で解けない）。

### ★★★★iOS のホーム画面アプリ「上下の帯」— **第35〜36巡で解決**

**結論だけ先に。** `apple-mobile-web-app-status-bar-style` は **`default`**。
`black-translucent` に戻さないこと。タブバーの位置は `NAV_BOTTOM_GAP` が
`env(safe-area-inset-bottom)` を**比率(2.382)で使って**吸収している
（`env(safe-area-inset-top)` ではない。理由は下の「2つの副作用」参照）。

#### 実測（実機の写真を画素で解析。すべて 390×844 の端末）

| | web ビューの高さ | 画面の下 47px | 画面の上 47px |
|---|---|---|---|
| `black-translucent` | **797**（画面 − 上のセーフエリア） | **どの要素も塗れない帯** | 中身が描かれる |
| `default` | **797**（同じ）だが**画面の下端まで**置かれる | 中身が描かれる ✓ | iOSが**固定の**白背景+黒文字（★下記） |

★★★**第37巡で訂正: `default`/`black`の上47pxは`theme-color`を見ない。**
Appleは`apple-mobile-web-app-status-bar-style`に`default`(白地に黒文字・
固定)/`black`(黒地に白文字・固定)/`black-translucent`(中身の背景色が
そのまま透ける)の3値しか公開しておらず、**`default`/`black`はどちらも
静的固定で、`theme-color`を一切読まない**(Web App Manifestの`theme_color`
もiOSでは無視される。Apple公式フォーラムでも既知の制限として言及されている)。
動的に色を追従させたい場合に使えるのは**`black-translucent`だけ**
(中身がその領域まで描かれ、そこに置いた背景色がそのまま見える)。
つまり「`default`で下の帯を消す」と「状態に応じて上の帯の色を変える」は
**両立しない**(iOSの制約であり、CSS/JSでは回避できない)。
第35巡で「入力画面を開くと上47pxも`theme-color`で暗くなるはず」として
実装した`lib/ground.ts`の`setTimeout`保険は、DOM上の`<meta name="theme-color">`
の値そのものは正しく追従させる(Android PWA・Safariのタブ色には効く)ので
無駄ではないが、**iOSのホーム画面アプリの状態バーには効かない**。
実機で「入力画面を開くと上に白い帯が残る」という報告はこれが原因
（コードの不具合ではなく、iOSの仕様上の制約）。

- `black-translucent` … 中身は y=0 から始まるのに高さが 47px 足りないので、
  **下 47px が誰も塗れない帯**になる。実測: 円の下端が **796.7pt**（どの x でも
  同じ y でまっすぐ）。★**`position: fixed` の面を伸ばしても描かれない** —
  ビューポートの外は要素では塗れない（第34巡に `--screen-h:
  calc(100% + env(safe-area-inset-top))` で試し、実機で**1pxも動かず**撤回）。
  **同じ手を二度試さないこと。**
- `default` … web ビューが**画面の下端まで**置かれる。実測（第29巡の写真）:
  最下部まで地色 `#ECECEA` で**帯が無い**。

#### `default` にすると出る2つの副作用と、その直し方

1. **タブバーが 47px 下がる**（web ビューが下へ伸びたぶん、下端に貼り付く
   ものが下がる）。実測: ピルの下端 783.0pt → 830.0pt、画面下までの余白
   60.7pt → 13.7pt でホームインジケーターに乗っていた。
   → 第35巡は `NAV_BOTTOM_GAP` に **`+ env(safe-area-inset-top)`** を
   足して戻そうとしたが、**`default` ではこの値が 0 になるらしく**
   実機で足した前後のピル位置が 0.1pt も動かなかった（第36巡に実機写真の
   画素比較で発覚）。`default` は「web ビューが物理的にステータスバーの
   下に無い」モードなので、そこに「不安全な領域」という概念自体が無い、
   という理屈で説明はつく。
   ★★**足し戻す信号が無いので、代わりに `env(safe-area-inset-bottom)` を
   比率で使う**（第36巡）。これは実機でだけ非ゼロ(34pt)になる値で、
   Chromium・検証環境では常に0なので、そこでの見た目・既存の検証は
   **今までどおり4px**のまま。実機だけ、必要な47ptぶんを足す比率(2.382)を
   掛ける（34 × 2.382 − 26 ＝ 55 ＝ 元の8px ＋ 47px）。
   ```
   export const NAV_BOTTOM_GAP =
     "max(4px, calc(env(safe-area-inset-bottom) * 2.382 - 26px))";
   ```
   ★★★**この比率は今の端末(セーフエリア下34pt)専用の逆算値。** 別の端末
   （例: 下34pt・上59ptのような機種）では比が変わるので合わなくなる。
   ずれたら「画面の数値を出す」の`safe`の値と実機の写真を見比べて、
   `目標(旧の55px相当) ÷ 実測のsafe-bottom` へこの数字を計算し直すこと。
2. **上 47px が `theme-color` の帯になる**。これは**うちの色**なので、
   地色に合っていれば見えない（`lib/ground.ts` が同期させている）。
   第29巡に「黒い帯」と報告されたのは iOS の仕様ではなく、
   **入力画面の色 `#33332E` が残っていた**もの（写真の実測で判明）。
   → 原因は `theme-color` の補間が `requestAnimationFrame` 頼みだったこと。
   **rAF は画面が隠れている間や iOS が絞っている間は止まる**ので、止まった
   ところの色で固まっていた。`GROUND_MS + 40` の `setTimeout` で
   **行き先を必ず書き込む保険**を置いた。

**検証は `scratchpad/chin35.mjs`。** メタが `default` か／`--screen-h` が
復活していないか／`lib/constants.ts` の実際の式を読んで、セーフエリア0で
4pxのまま・実機相当(下34pt)で目標55pxに一致するか／
★**rAF を殺した状態で入力画面を閉じても `theme-color` が地色へ着地するか**。

### ★長押しで iOS の選択メニューを出さない（第55巡）

### ★★★DRIFT は「触れたら止まる」（2026-08-26・第65巡）

**動いている相手は掴めない。** DRIFT は無重力で、`reseed()` が表に出るたび全部に
初速を与え、減速は `frictionAir = 0.016` だけなので**2〜3秒**漂い続ける。
ユーザーが最初に触るのはちょうどその間で、こうなっていた:

| 症状 | 仕掛け |
|---|---|
| 掴めない | 当たり判定は `pointerdown` の瞬間、掴みの成立は **150ms 後**。その間に相手が指の下から逃げる |
| 掴めない(2) | 逃げる図形を指で追うと **8px（`TAP_MOVE`）で掴みが捨てられる** |
| **上へ飛ばされる** | 捨てられたあとは払いの分岐に落ち、上に 44px で `enterGravity()` |
| 掴むとすっ飛ぶ | `ox/oy` を `pointerdown` で凍結。body はその後 150ms 動くので、成立後の最初の move で `(tx - b.position.x)·GRAB_K`（上限 34px/step）が一気に効く |
| 指の下で回り続ける | DRIFT だけ**角速度を 0 にしていなかった** |

直し（**すべて GRAVITY に揃える方向**）:

1. ★★**`onDown` で当たった図形の速度と角速度を 0 にする。** 指を置いたら止まる、は
   物理的にも自然で、**逃げる相手を追わなくてよくなる**ので上の3つが根元から消える。
2. `enterHold` で **`ox/oy` を取り直す**（`grab.px/py` に canvas ローカルの最新の指の位置を持つ）。
3. `enterHold` で **`moved` を再確認**し、**角速度を 0** にする。
   ★起動直後は焼きでメインスレッドが詰まり、150ms のタイマーが**遅れて発火する**。
4. `onDown` に**門番**（`live` / `size.w` / 図形が1つ以上）。GRAVITY の
   `if (!visibleRef.current) return;` に当たるものが DRIFT だけ無かった。

★★**DRIFT は第60・61・63・65巡と4回続けて壊れた。毎回「DRIFT だけが GRAVITY と
違うことをしていた」**（既定タブゆえの初期化順 → 画面座標の場 → 二重 bleed → 動く世界）。
**同じ器に居るのに片方だけ壊れるときは、片方だけ違うことをしていないかを最初に疑う。**

### ★★変形中の要素を当たり判定に測らない（第65巡）

`components/tasks/DropTargets.tsx` の `inRect` / `aimTargets` が
`getBoundingClientRect()` を読んでいたが、`.drift-target` は

### ★★★列は「画面の外」でマウントされる（第58巡・DRIFT が初回に壊れた）

`AppShell` の `mountedApps` は **`["life"]` から始まり**、ほかのアプリの列は
`requestIdleCallback` で**あとから**組まれる。そのとき列は `translateX(±100%)` で

見ない**ので、あとで列が入ってきても直らない。

1. 画面の座標に依存して測るものは、**見えるまで測らない／置かない**

2. それでも動いたときのために、**原点が動いたぶんだけ中身を運ぶ**

3. `sizeRef`（`offsetWidth/offsetHeight`）は位置に依らないので安全。
   **位置を含む測り方だけ**が危ない。

### ★性能の作法
- **毎フレーム変わる値を React の state に入れない。** ref と、CSS カスタム
  プロパティ（`--drag` / `--dash`）への直接書き込み、canvas で扱う。
  ドラッグ中の React のレンダーは 0 回が正しい。
- **`@property` は使わない**（Safari 16.4 未満に無い）。トランジションは
  カスタムプロパティ自身ではなく、そこから `calc()` で導かれる
  transform / width / opacity の側に掛ける。
- **重いものは合成レイヤーへ上げる**（`will-change: transform`）。巨大な図形の
  隣で canvas を毎フレーム描くと、同じレイヤーを汚して図形ごと塗り直される。
- **`animation-direction: reverse` では再生し直されない。** 逆再生させたい
  ときは**別名のキーフレーム**を用意して `animation-name` ごと差し替える。
- **`animation-fill-mode`** … `both` にすると最後のコマの transform が
  残り続け、JS が書く値を上書きする。遅延の間だけ見せたいなら `backwards`。

## 4. タスクアプリ（§53 で確定）

### ★★GRAVITY の物理モード（2026-08-24・第52巡にユーザー確定。TOP/UNDER と縦のカメラを破棄）

**タスク図形は常に GRAVITY 空間にだけ在る。** 以前は DRIFT / GRAVITY / TOP / UNDER の
4層をカメラで上下していたが、「図形が GRAVITY に積まれているのに同時に別画面
（TOP/UNDER）にも在る」のは**物理演算ベースの UI としてメタファーが破綻**している
（ユーザー指摘）。TOP（カレンダー）と UNDER（リスト）の画面遷移を**完全に破棄**し、
別画面へ遷移せず、スワイプで**GRAVITY の物理法則を一時的に変える**ことで詳細リストと
俯瞰を見せる。

- タブは **DRIFT（候補の無重力の場）＋ GRAVITY** の2つ（末は GRAVITY 1画面へ集約。
  DRIFT の扱いは別途相談）。
- `components/tasks/TaskSpace.tsx` は**薄い器**に。GRAVITY を常時マウント（山を保つ）、
  DRIFT タブのときだけ上に重ね、画面固定の `Masthead`（TASK）を持つだけ。
- 中身は `components/tabs/GravityTab.tsx` の**物理モードの状態機械** `modeRef`:

| モード | 入口 | 何をする |
|---|---|---|
| `pile` | 既定 | 重力 1.4 で落ちて積まれる（従来の山） |
| `align` | 画面**左端→右**スワイプ | 磁場で**面積の降順の一列**に整列＋右に詳細リスト |
| `timeline` | **下→上**スワイプ | 巨大な曜日が仕切りに立ち、図形が**日付レーン**へ吸着 |

各モードの逆方向スワイプで `pile` へ戻る。

#### ★★描き方（第53巡に作り直し）— スロットへ「絵の中心」を置く

**align / timeline では matter の body の位置で描かない。** レイアウトが決めた
**スロット `{x, y, s, a, o}`（位置・倍率・角度・濃さ）へ、焼いた絵の中心をそのまま
置く**。第52巡はここが原因で実機のレイアウトが破綻した:

| 第52巡の作り | 何が起きたか |
|---|---|
| body の**重心**へ寄せ、`ox/oy`（重心と絵の中心のズレ）で補正 | `ox` の大きい形（半円・三角）が行から外れ、**画面の左端で切れた** |
| `unit` を変えて**焼き直す** | 焼き上がるまで fallback が**実寸の多角形**を描き、位置も大きさも合わない |
| 全図形で `unit` が1つ | 焦点だけ大きくできない |

いまの作り:
- **絵の中心＝スロット**（`ox/oy` を使わない）。どの形でも必ず行に揃う。
- **大小は `ctx.scale`**。焼くのは**1つの unit だけ**（`bakeUnitRef`）で、焦点が
  ちょうど等倍になるように焼く（＝焦点がいちばん綺麗）。
- 焼き上がる前は**山の絵**を倍率だけ合わせて流用する（空白にしない）。どちらも
  無い1〜2フレームだけ、スロットの大きさの薄い矩形を置く。
- **当たり判定もスロットの矩形**で見る（body は画面上に居ないため）。
- **濃さ `o`** … 円弧の端では切り落とさず**淡くして消す**（縁で図形が真っ二つに
  切れると事故に見える）。
- ★**align/timeline は「未完了の全タスク」が対象**。`pileOf` は山が読めるように
  間引くが、一覧・俯瞰は全部見えないと用を成さない（`buildItems`）。
- `pile` は従来どおり body の位置・角度で描く（山の物理はそのまま）。

#### モードの出入り

- モードに居る間は**物理を止める**（`frozenRef`＝`Engine.update` を呼ばない・重力0）。
  止めるので、入る時に控えた**山の位置のスナップショット**（`fromRef`）が腐らない。
- 入り具合 `enterRef`(0..1) で `from → slot` を補間する（`ease` は初速の高い減速）。
  **TIMELINE だけは指が `enterRef` を直に進める**（下記）。
- **山へ戻すとき**は、いま見えている位置を body へ**書き戻して**から重力を返す。
  だから図形は「いま居るところから」落ちる（テレポートしない）。
- ジェスチャーは GravityTab の器で認識（左端 `EDGE_PX`=30・`SWIPE_PX`=44・軸ロック）。
  タップ（`TAP_MOVE` 未満）はどのモードでも `TaskComposer` を開く。DRIFT タブが
  上にいる間（`active=false`）はループもジェスチャーも止める（`visibleRef`）。
- ★★**縦のスワイプは「向き」で行き先が決まる**（第61巡にユーザー確定）。
  | 層 | 指 | 行き先 | 図形 |
  |---|---|---|---|
  | GRAVITY（山） | **上** | TIMELINE | 床が抜けて落ちる |
  | GRAVITY（山） | **下** | **DRIFT** | 効果線を伴って**下へ**吹き飛ぶ |
  | DRIFT | **上** | **GRAVITY** | 効果線を伴って**上へ**吹き飛ぶ |
  ★候補の層（DRIFT）は山の**上**に在る ― 指で世界を下へ送るとそこへ上がる。
  ★第60巡は上を「地面際=TIMELINE / それ以外=DRIFT」と割ったが、**向き自体が逆**
  だった（ユーザー指摘）。切り分けは要らないので `TL_GRAB_H` ごと撤去した。
  上スワイプは**どこからでも TIMELINE**。
- ★★★**山が使える左右の内寸は `PILE_INSET`（＝画面の端から 16px）**（第62巡に
  ユーザー指定「箱の左右の幅を狭めて、タブバーや他のレイアウトと統一して」）。
  タブバーは `left:0; right:0; padding: 0 16px`（`AppShell`）。canvas は `full-bleed`
  で左右 16px ずつ広いので、**canvas 座標では 32px**。
  ★**左右の出どころはここだけ** — 壁も、湧く x も、`pileOf` に渡す幅も全部これを通す
  （`pileWOf(w)`）。壁と湧く場所がずれると、壁際で図形が押し合う。
- ★★★**山を小さくするとき、下げるのは `SCALE_MAX` と `FIT_*`（1つの図形の大きさの
  上限）であって `FILL` ではない。** `FILL` は「何個ぶんの面積を置けるか」なので、
  下げると `pileOf` が `SCALE_MIN` に当たって**タスクを間引いてしまう** ―
  小さくなるのではなく**減る**（第62巡に踏んだ。0.58→0.46 で 7個が 3個になった）。
  間引きを増やさずに小さくするには **`SCALE_MIN` も一緒に下げる**こと。
- ★★**GRAVITY が表に出るたびに山を落とし直す**（第60巡にユーザー指定「開いたりする
  たびに毎回ランダムに図形が落ちるように」）。ALIGN / TIMELINE を開いたまま離れて
  いても、戻ってきたら**山からやり直す**（開いたままの層に戻されると「開いたら落ちる」
  が起きないうえ、前に見ていた状態が置き去りになっていることに気づけない）。
  ばらつきは `makePiece` に渡す**その回の種**で作る（`frac(t.id + seed)`）―
  `frac(t.id)` だけだと**同じタスクは毎回まったく同じ所へ落ち**、山の形が寸分違わず
  再現されていた。★傾きと回りは**控えめに**（±0.25rad / ±0.025）。強くすると転げて
  逆さまに積まれ、**名前が読めなくなる**。ばらつきは主に「どこへ・どの高さから」で作る。

#### ★★★カメラのパン（地上 ↔ 上空。2026-08-25・第62巡に作り直し）

  合計の移動は画面 1.6 枚ぶん ＝「遠くまで上がった」が出る。
- `--cam` は**いまのタブから決まるだけ**（指には追従しない・ユーザー確定
  「払ったらグワーっとパン」）。払いは各層が `goTab` を呼ぶだけ。
- ★★**曲線は `--ease-exit`**(0.4,0,0.2,1)。語彙の4本のうち**加速してから減速する**
  形はこれだけで、長い距離を運ぶ「乗り物」に合う。

#### ★★★ALIGN の出入り（第64巡に作り直し）

- **入りの `from` は「見た目の中心」を控える**（`snapshot`）。山は
  `translate(位置) → rotate(角) → drawImage(ox - w/2, oy - h/2)` で描くので、絵の中心は
  **`位置 + rotate(ox, oy, 角)`**。`ox/oy` を足さないと、ALIGN の判定が入った瞬間に
  そのぶんだけ**図形が飛ぶ**（第63巡のユーザー指摘）。
- ★★★**緩急は「加速しっぱなし」の1本だけ**（`flow(t) = t^2.4`）。
  第57〜63巡の `cine`（遅→速→遅）は**終わりで必ず傾きが 0** になるので、
  **全員が出口で減速して右上に溜まる**。第63巡は「後ろほど `t²` を混ぜる」で誤魔化したが、
  混ぜ具合が図形ごとに違うぶん**進みと時刻の対応が図形ごとにずれ**、次の項の引き渡しが
  合わなくなった ― **対症療法が次のバグを産んだ典型**。
  加速しかしない曲線なら:
  - 出口で減速しないので**溜まらない**。
  - **等間隔**（`STREAM_STEP` = 64ms）に出発した図形は、傾きが増えるぶん
    **進むほど間隔が開く** ― 重なりが**構造として起きない**。
    第63巡までの `LEAD_GAP · GAP_DECAY^i` は等比級数で収束し、**7番目以降が数ミリ秒差**
    でしか出発しなかった（`streamQ` の頭打ちと重なって「後半が右上でぐちゃぐちゃ」）。
  - 速さの山が終盤に来るので、速さ由来のスクイーズが**勝手に後半だけ強くなる**
    （`SQUASH_MAX` 0.09 は「見える所まで出す」ためだけの数字）。
  - ★揃えるための仕掛け（`span` / `conv` / `line` / `streamQ` / `STREAM_GAP`）が
    **まるごと要らなくなった**。
- ★★★**引き渡し（円弧へ上がる合図）は「進み」で決める。時刻で決めない。**
  `HANDOFF_N = 0.96`。第63巡までは時刻（`STREAM_MS · 0.72`）で切っていて、これは
  `cine(0.72) ≒ 0.94`（ほぼ画面外）を前提にした数字だった。緩急を `t²` 寄りに変えた
  とたん同じ時刻の進みが **0.52 ＝ まだ画面の真ん中**になり、
  「**図形が画面から出る前に消える**」（第64巡のユーザー指摘）になった。
  進みで決めれば、曲線をどう変えても**必ず道の終点＝画面の外**で渡る。
- ★★**位置は「筋の形をそのまま持ち、自分のズレだけを減衰させる」。**
  `p = streamAt(n)` に `(fr - streamAt(0)) * keep`（`keep = (1 - n/MERGE)²`、`MERGE`=0.45）を
  足す。第63巡の `lerp(fr, p, join)`（動く点へ直線で寄せる）だと**筋の曲がりが打ち消され**、
  まっすぐ吸い込まれるように見えた。こうすると
  「あった場所からそのまま曲線を描いて、筋に合流」（ユーザー指定）になる。
  ★`n` の出発の傾きが 0 なので、**山に置かれた姿からなめらかに動き出す**。
- ★入口の番号は `ENTRY_QUEUE * Math.min(i, ENTRY_Q_MAX)`。素の `i` だと後ろの
  図形ほど円弧のはるか下から入るので、**大きく回り込んで**見える。
- ★長さ … `STREAM_MS` = `ms(T_IN)` / `STREAM_STEP` 64ms。
  **閉じはさらに素早く** `OUT_MS` = `ms(T_ITEM)`、遅れは `startAt(i) * OUT_LEAD`(0.5)。
- ★★**閉じでは山を前倒しに落とす**（`OUT_DROP` = 0.55・第64巡にユーザー指定
  「落ち始めるのも早めて」）。そこまで来れば図形は `homeAt(0.55)` ＝ 画面の左の外に居る。
  ★★このとき**モードは変えない** — `mode === "align"` は右の文字（DOM）を出す条件でもあり、
  先に変えると**薄まりきる前に文字がぱっと消える**。代わりに `draw` が `outDroppedRef` を見て、
  そのあいだだけ**山と出ていく図形の両方**を描く（山を先、図形を上）。
  ★`outDroppedRef` は align-out が終わったら **false へ戻す**（戻し忘れると次の入りで
  山まで描いてしまう）。

#### ★★★ALIGN の並び（2026-08-26・第65巡に作り直し）

##### 道は「縦はまっすぐ、横だけほんのり弓なり」

```
y = mid + L                                   ← 縦は**道のりそのもの**
x = ARC_APEX_X - ARC_SWING · clamp(L/reach, ±1)²   ← 横は放物線。膨らみは頭打ち
```

- ★★★**本物の円をやめた**（ユーザー指定「円弧の部分はほとんど見えなくても良いので、
  図形を左に寄せて右側に文字の場所を作る」）。円だと必ず2つ起きる:
  1. 端へ行くほど**縦が詰まる**（`dy/dL = cos θ`）ので**行が重なる**
  2. 遠い行ほど横に流れて**画面の外へ逃げる**

  縦を道のりそのものにすれば、行の間隔は常に一定で、**指と 1:1** が素直に出る。
  浅い放物線は浅い円弧と見分けがつかないので、狙いの「気配」はそのまま残る。
- ★★**二次関数は必ず頭打ちにする**（`clamp(±1)`）。基準の外では暴れるので、
  膨らみが `ARC_SWING`(32) を超えないよう止める。基準 `reach` は**場の半分**
  — `mid` を基準にすると上下で基準が食い違い、下の行が際限なく左へ逃げた。
- ★★★**`mid` は画面と目盛りだけで決まる固定値**。
  **レイアウトの原点を、レイアウトの中身から決めてはいけない。**
  第65巡の1回目はここを `scrollRef.current.p` の関数にして（上下の空きを釣り合わせる
  つもりで）**スクロールを壊した** ― 指を動かす → 原点が動く → **場ぜんぶが動く** →
  その動く的をバネが追いかける、という輪ができて行がガクガク揺れた。

##### 寸法は互いに縛り合っている（どれか1つだけ動かせない）

| | 値 | 誰に縛られるか |
|---|---|---|
| `PITCH_TIGHT` | 88 | ★**行の高さ（題＋帯 ≒ 50px）より大きく**／★**図形の高さ×0.75 より大きく** |
| `PITCH_SPREAD` | 40 | 焦点↔隣が 116px。ユーザー指定で**広げた**（1回目の 81px は詰めすぎ） |
| `ALIGN_MAX_H` | 104 | `H × 0.75 ≤ PITCH_TIGHT` でないと**図形どうしが重なる** |
| `ALIGN_MAX_W` | 116 | 小さいほど題が長く入る。`ARC_APEX_X` と `TEXT_GAP` の親 |
| `ARC_APEX_X` | `SPACE.lg + W/2` = 74 | 画面の左端から `SPACE.lg` |
| `TEXT_GAP` | `W/2 + SPACE.lg` = 74 | これより小さいと**文字が図形に重なる** |

→ 文字の幅 **226px**（第64巡は 194px、第65巡の1回目は 166px）。

★★第65巡の1回目は `ALIGN_MAX_H = 176` / `PITCH_TIGHT = 64` で、**図形が派手に重なった**。
第64巡までは `PITCH_TIGHT = 44` で遠い行が必ず重なっていたが、**霧がそれを隠していた**
だけだった。**霧を消すと、詰めすぎが全部見える。**

##### 行の組み（タイトルが主、残り日数とタグが従）

- 題 `TYPE.display`(26)／非焦点 `TYPE.head`(20)・焦点は2行まで。
- その下に**同じ大きさ**（`TYPE.small`）で、残り日数（`MUTED`）と**タグのピル**
  （`RADIUS.pill` ＋ タグ色 ＋ `tagInk`。入力画面と同じ意匠＝画面で唯一の色）。
- ★★**横のラインを揃える** … 残り日数とタグを**同じ高さの箱**（`SPACE.xl`=24）に入れ、
  中で上下中央に置く。片方だけ padding で膨らませると高さが食い違って下端が揃わない。
- ★題と帯のすき間は `SPACE.hair`(2)。箱の中で中央に置いてあるので、これで光学的に足りる。
- ★題の左端と残り日数の左端は**インクで一致**する（実測 0px）。どちらも行の左端から
  始まる素直な積み方にしておけば、側面ベアリングの差は出ない。

##### 指と 1:1（`layoutAlign` のバネ）

```ts
k = max(K_TRAVEL, CHAIN_K · CHAIN^min(CHAIN_MAX, |d|))   // 0.34 → 0.12 → 0.044 → 0.016
d = min(D_CHAIN_MAX, 2√k · D_CHAIN)                      // 臨界の 86%（わずかに行き過ぎる）
```

- ★★★**焦点は硬く、遠い行ほど柔らかい。** 第64巡までは全部が `K_TRAVEL`(0.016) の
  同じやわらかさで、**焦点の行ですら指の3割しか付いてこなかった**。
  「連鎖」は遠い行が遅れることで出るのだから、**触っている行まで遅らせる必要は無い**。
- 実測（焦点の行）… 120px 払って**116px = ちょうど1行ぶん**に収まる／
  払っている最中も **112/120px** 付いてくる／毎コマの動きは
  `0.9 1.5 2.0 … 3.9 4.1 … 5.3 5.4`（**単調に増えて指の速さを超え、遅れを取り戻す**）。

##### ★★測り方の罠（第65巡に3つ踏んだ）

1. **dispatch の直後に DOM を読まない** … rAF 前の値が返る。ページの中で
   `requestAnimationFrame` ごとに測ること。
2. **遠い行を測らない** … 遅れるのは設計どおり。**焦点の行**を測る。
3. **固定間隔でポーリングしない** … `waitForTimeout(40)` は 60fps に対して 2.4 コマなので、
   **測り方のせいで**ばらついて見える（アプリは揺れていなかった）。

- 並びは `areaOf` の降順。左へ払うと山へ。
- **★★スクロールは「連鎖」**（第58巡にユーザー指定）。**指は 1:1**（スクロールそのもの
  をバネにすると「操作が重い」だけで連鎖が見えない — 第57巡の失敗）。richness は
  **行ごとの弧長のバネ**が持つ … 硬さを焦点からの距離で落とす
  `k_i = K_TRAVEL × CHAIN^min(|d|,6)`。**中央と隣の間隔がまず縮み、それに次が追い、
  さらに次が追う**。文字も**同じバネ**を読む（文字だけ先に着くと連鎖が壊れる）。
- ★★★**スクロールの語彙は `lib/scroll.ts` だけ**（第59巡）。指の 1:1 ＋ 投げ ＋ 減衰 ＋
  最寄りへ吸着を1つにまとめてある。**強さを触るのは `SCROLL_GAIN` と `FLICK_K` の
  2つだけ**。第58巡は効きが強すぎて「少し払っただけで画面の下まで行く」「慣性で
  全部潰れる」になったので第59巡に 0.2 倍へ。★★第60巡はその逆の指摘 ―
  「指のスクロールに追従しなさすぎる。わざと遅くしすぎている。もう少し普通の動きに
  寄せて」。**指の効き（`SCROLL_GAIN`）だけを普通(1.0)へ寄せ、投げ（`FLICK_K`）は

  勝手に伸びる。第61巡「まだ重い」でもう一段、第62巡「100パーセントで指に追従させて」で
  **`SCROLL_GAIN` = 1.0 ＝完全な 1:1** に到達（`FLICK_K` は 0.08）。
  ★★**投げの速さには上限（`V_MAX` = 1フレームに1つ弱）を置く**（第62巡）。上限が
  無いと、強く払ったとき1フレームで端まで飛び、**呼ぶ側の連鎖のバネが巨大な目標差を
  一度に受けて暴れる**（ユーザー報告「勢いをつけ過ぎてスクロールすると画面がバグる」）。
  連鎖ばねは触っていない（潰れて見えたのは**入力が強すぎた**からで、連鎖そのものは
  指定どおり）。★TIMELINE の横送りも次はここへ寄せる。

#### ★★MAGNETIC TIMELINE（下→上）— **アニメーションではなく本物の落下**（第55巡）

指の動きに落下を1:1で対応させない。**指は合図で、あとは物理**。

1. 下から上へ払うと、**地面でぺたんこの曜日が指に追従して伸びる**
   （`.tl-band span { transform: scaleY(var(--tl)) }`）。★指との対応はここだけ。
2. 伸びが `TL_TRIGGER`(0.45) を超えたら合図 … **GRAVITY の床が抜ける**
   （`rebuildWalls(..., withFloor=false)`）。山は**そのまま重力で落ちる**。
3. 画面の下（`h + 120`）へ出た図形を、**その日の列の真上（`-RECYCLE_Y`）へ引き上げて
   離す**（`recycle`）。出ていった順に上から降ってくるので、「落ちながら、すでに落ちた
   図形が上から順番に振り分けられる」がそのまま出る。
4. **レーンの器**（`buildLanes`）… 曜日の帯の上端に**レーンごとの床**、境目に**縦の壁**。
   図形はスロットに置かず、**物理で下から積み上がる**。

- ★★**当たり判定の層**（`CAT_*` / `setFilter`）… **落下中の図形はレーンの器を
  すり抜ける**。そうしないと床を抜いた瞬間に山がその場で受け止められ、振り分けが
  起きない。`FILTER_FALL`（落下中）→ `recycle` で `FILTER_HELD`（列に収まった）。
  ★`Bodies.fromVertices` の複合 body は**各 `part` の `collisionFilter`** を見るので、
  親だけ書き換えても効かない（`setFilter` が `parts` にも入れる）。
- ★★**画面の左右の壁は「列に収まった図形」を通す**（第56巡）。レーンは画面の外まで
  続いていて、**3日目より先の列は右の壁の中に居る**。壁が効くとそこへ落ちた図形が
  押し戻され、隣のレーンへ紛れ込む（実機の写真で発覚）。壁は山（既定の分類）と
  落下中（`CAT_FALL`）にだけ効かせる。
- ★★**図形はレーンの「内寸」に収める**（`laneInner = laneW - WALL_T`）。壁は境目の
  **上に**置くので、レーン幅いっぱいに作ると壁に挟まって**宙に浮く**（第56巡）。
- ★★**回転を止めないこと**（第57巡にユーザー確定「ちゃんと GRAVITY と同様に」）。
  第55〜56巡は `setInertia(Infinity)` で回転を禁じていたが、それだと落下が
  **アニメーションに見える**。図形は落ちながら転がり、ぶつかって**傾いたまま
  積まれる**。曜日の列はきっちり整わなくなるが、それが物理として正しい姿。
- ★★**投入をばらす**。全部を同じ高さ・速度 0・角度 0 で入れると、隣同士が寸分違わず
  同じ速さで落ちて**アニメーションに見える**（第57巡のユーザー指摘の正体はこれ）。
  id の `frac` から**高さ・初速・角度・角速度**を散らす。
- **★日付の無いタスクは「消さずに落とす」**（第56巡にユーザー指摘）。世界から
  `remove` すると**その場で瞬間に消えて**事故に見える。`lane = -1` ＋ `FILTER_FALL` で
  一緒に落とし、画面の外（`h + 120`）へ出たところで畳む。
- **大きさ** … レーンの内寸の `TL_FILL`(0.94)、高さは `LANE_HEAD_H × 2`。落ちて画面の
  外にいる間に `swapUnit` で入れ替えるので、継ぎ目は見えない。
- **左右** … 器と乗っている図形を**同じ `dx` だけ平行移動**する（`syncLanes`）ので
  積んだ山が崩れない。★★離した瞬間に `Math.round(world/laneW)` で**最寄りへ吸着させ
  ないこと** — 半レーンぶんの払いが**必ず元へ戻る**（第57巡のユーザー指摘「引き
  戻される」）。**投げを先に伸ばしてから**レーンを決める
  （`proj = p + v · WORLD_FLING`）。速い払いは `ceil`/`floor` で**最低1レーンは送る**。
  速さは DRIFT と同じく**時間で割って1ステップぶんへ**そろえる。
- ★**曜日は黒**（`INK`。今日だけ `RUST`）。第55〜56巡は画面での位置で薄墨の階調を
  付けていたが、第57巡にユーザー指定で**階調をやめた**（`gradeInk` は削除）。
  毎フレーム CSS 変数 `--wd` に入れる。
- ★★**曜日をたたくと**（第55巡の指定）… **たたいた曜日が画面の左端（`PAD_L`=20 ぶん
  内側。端ぴったりにしない）へ来て、曜日の文字の間隔が空き、その隙間に詳細が出る**。
  隙間 `GAP_W` と横スクロールは**どちらもバネ**で、`laneLeft(i)` が
  「器・図形・曜日の札・詳細」の**唯一の出どころ**。★CSS の transition で札だけ別に
  動かすと器とズレる（第55巡に作って捨てた）。パネルは**読むだけなので指を通す**
  （`pointerEvents: none`）— 受け取ると上から払っても閉じられない。

#### ★★★曜日の詳細の開閉は「隙間」ひとつが動かす（第68巡に根治）

**詳細パネルの見え幅は、レーンの隙間 `gapRef` そのもの。** 開きも閉じも
`advance()` が毎フレーム `clip-path: inset(0 N% 0 0)` に入れる（CSS は持たない）。

    見え幅 = clamp((gapRef.p − SPACE.lg×2) ÷ DETAIL_W, 0, 1)

パネルの左端はレーンの右＋`SPACE.lg` に在るので、この式は
**パネルの見えている右端と、戻ってくる隣のレーンの左端の距離を常に `SPACE.lg` に保つ**
（実測：閉じの全フレームで 16.0±0.1px）。

★★**`laneLeft(i)` の `sel` は `expandedRef ?? closingRef`。** ここを `expandedRef`
だけにしていたのが第62〜67巡の症状の正体で、閉じ始めた**その1フレーム**で
縦線・曜日の札・図形から隙間が消え、パネルだけが 600ms かけて拭かれていた
（ユーザーの言葉で「縦の列だけ閉じるのが早すぎる／下の横線と合っていない」）。

★片づけは**隙間が 0 に落ち着いたとき**（`settled(gapRef, 0)`）。第67巡までの
`setTimeout(ms(T_OUT))` は、バネの実際の長さと必ずズレる。
★片づけの経路（層を離れる・TIMELINE を開き直す）は演出せず、`closingRef` も消す。

#### ★横に送っている間だけ出る日付の目盛り（第58〜59巡にユーザー確定）

レーンの境目に 1px の縦線、線の**上端**に `8/28` の日付（**`TYPE.head`**(20)）。
**土日はレーンいっぱいに淡い地色**（`color-mix(INK 5%, transparent)`）を敷き、
日付も `INK` にする。出るのは**横に動かしている間だけ** … `--pan`（0/1）を
`move`/`up` が書き、`opacity` を語彙の時間で出し入れする。
★**離してもすぐには消さない** — `ms(T_OUT)` 待ってから 0 にする（送り終わった位置を
読む間だけ残す。第59巡にユーザー指定）。位置は `laneLeft(i)` から毎フレーム
（**器・図形・曜日の札と同じ出どころ**）。

#### ★★TIMELINE を閉じる（第58〜59巡）— 開くときの鏡

第57巡までは `dropAll()` で山を作り直していたので、**timeline の図形が消えて別の
図形が降ってくる**（＝閉じるアニメーションが無い）。開くときと同じ段取りにする:

1. 下へ払うと**曜日が指に追従して潰れる**（`pullTo(1 - dy / TL_SPAN)`。開くときの
   `pullTo` をそのまま使う）。潰れが `1 - TL_TRIGGER` を切ったら合図。
2. **レーンの器を外し**（`clearLanes`）、床は**抜いたまま**、全部を落下の層
   （`FILTER_FALL`）へ戻して落とす。
3. 画面の下へ出たものから**山の上へ引き上げて離す**（`recycleToPile`）。
   大きさは `swapUnit` で山の単位へ戻し、高さ・初速・角度を `frac` で散らす。
   「自由」の板は**タスクではない**ので、ここで畳む（山へは戻さない）。
4. 全部そろったら、**timeline に居なかったタスク**（日付なし・間引かれたぶん）を
   足し、**床を戻して** `mode = pile` へ。

★★**`mode` を先に `pile` にしないこと**（第59巡に踏んだ）。React が帯（`.tl-band`）も
縦線（`.tl-rules`）も**即座にアンマウント**するので、「下へ払った判定が入った瞬間に
自由と曜日が消える」＝閉じるアニメーションが無い、に見える。**潰れ切って全部が山へ
戻ってから**切り替える。同じ理由で「自由」の板もその場で world から外さない。
★`dropAll()` を使わないこと ―**同じ物体が落ち続ける**のが繋がって見える理由。

#### ★★曜日の見た目と引き上げ（第56巡にユーザー指定）

- **引っ張れる** … 指の引き上げは 1 で頭打ちにせず、**1 を超えたぶんは重くなって**
  `TL_STRETCH`(1.9) へ漸近する（`rubberRise`。1 の所で傾き 1 なので継ぎ目が無い）。
  **離すと規定(1)へバネで戻る**（`riseSRef` ＋ `K_SETTLE`/`D_SETTLE`）。
  ★瞬間で 1 に飛ばさないこと（第55巡までの `up` はそうだった）。
- ★★**`--tl` は `move` の中で直接書く**（`pullTo`）。rAF の中でだけ書くと1フレーム
  遅れ、**速く払うと指に置いていかれる**（第57巡のユーザー指摘）。離すときは
  **指の速さをバネの初速に渡す**ので、速い払いは少し行き過ぎてから収まる。
  ★モードが `timeline` になった直後の1〜2フレームは帯がまだ無いので、
  そこだけ rAF 側が埋める（`bandRef` が null なら書かない）。
- ★`.tl-band` は **`overflow: visible`**。伸びた文字を切ってしまうと引きが見えない。
  画面外へは外側の `main.full-bleed`（`overflow: clip`）が抑える。
- **規定の曜日を少し縦長に** … `scaleY` で変形させるのではなく、**Archivo の幅の軸を
  細くする**（**`"wdth" 58`**。第56巡 75 → 第59巡 58）。細いぶん**同じレーン幅でより
  大きく**でき（`laneFs` の1文字あたりの送りを `WD_ADV`(0.54) で計算 → `SWISS_XL`(72)
  に届く）、書体が歪まない。★`body` の `wdth 88` は触らない。

#### ★★タスクが無い日は「自由」のブロックを落とす（第56巡にユーザー確定）

空白のままだと、俯瞰したときに**空いている理由**が読めない。タスクの図形が
「色の面＋載った文字」なのに対して、これは**文字そのものが図形**。

- 文言は10語（`FREE_WORDS`）… `FREE / 自由 / LIBRE / FREI / LIBERO / LIVRE / VRIJ /
  FRI / VAPAA / VOLNY`。**日付から選ぶ**ので同じ日はいつも同じ語になる。
- ★**字の大きさは語によらず1つ**（`freeGeom`。第57巡にユーザー指定）。語ごとに
  幅から出すと `FRI` だけ巨大になる。書体は `SANS`（`自由` は Archivo にグリフが無い）。
- ★★**箱は「文字の塗り」そのもの**（第61巡。下の「文字ブロック」を見よ）。
- ★★★**字面と詰め先は「対角」から決める**（`freeGeom`・第62巡）。板は回るので、
  条件は `√(板の幅² + 板の高さ²) ≤ レーンの内寸 − FREE_MARGIN`。
  - ★**詰める先を「対角の予算」そのものにしないこと。** 板の幅は
    `詰めた塗り + FREE_PAD*2` なので、塗りを予算いっぱいまで許すと**幅だけで
    予算を超える**（＝どんなに小さくしても収まらず、字がどんどん縮む。最初の
    実装で 24px まで落ちた）。正しくは高さから**幅の予算を逆算**する:
    `幅の上限 = √(予算² − 高さ²)`。
  - ★★**`FREE_WORDS` の全部**で確かめること。**いちばん対角が長いのは `自由`** —
    CJK は塗りが**ほぼ正方形**（高さ ≒ 1em。Latin の大文字は 0.72em）だから。
    ユーザーの「なぜか日本語の自由だけ当たり判定が無いように見える」は、実際には
    **自由がいちばん先にはみ出していた**ということだった。
  - **縦の遊びは横の半分**（`FREE_PAD_Y`）。板を平たくするほど「寝る」のが安定な
    姿勢になり、短い辺で立ったまま止まりにくい。
  - **回り慣性を重くする**（`setInertia(×5)`）。板は薄いので、横送りでレーンの壁が
    動くたびに小突かれて立ってしまう。質量が両端に寄った板だと思えば物理的にも
    素直で、落ちるあいだは変わらず回る（空中では小突かれない）。
- ★★★**当たり判定は図形とまったく同じ**（`FILTER_HELD`）。第61巡は板だけ
  「仕切りをすり抜けて床とだけ当たる」層に逃がして大きさを取ったが、**隣の板とも
  仕切りとも当たらなくなり、境界を越えて転がった**（第62巡のユーザーの写真）。
  「内寸に収める」と「大きく組む」は同時には満たせない ― ユーザー確定で
  **小さくしてでも必ず収める**（第56巡は押し出され、第59巡は回転を殺して
  「物体に見えない」になり、第61巡は層を分けて境界を越えた。4巡目で決着）。
- ★`recycle()` が下へ出た図形を引き上げるとき、**板に `swapUnit` を掛けないこと** —
  `swapUnit` は `paint` から**図形の** body を作り直すので、板が図形に化ける。
- `Piece.word` を持つ図形は … 色の面を敷かず `fillText` で `wordInk`（既定 `MUTED`）に
  描く／**たたいても入力画面を開かない**／**掴めない**（完了も削除もできないため）。
  物体は測った文字の箱ぶんの矩形。後始末は `dropAll()` が world ごと組み直すので不要。
  ★`makeWordPiece(M, word, id, room, fs, x, y, ink, fam)` は **TIMELINE の「自由」と
  GRAVITY の日付・曜日で共用**する（下記）。

#### ★図形どうしに髪の毛ほどの隙間（`HAIR`・第63巡）

当たり判定だけを**見た目より `HAIR`(1.5px) 外側**にする（絵は変えない）。図形どうしが
隣り合って止まったとき、色面が直に接していると境目が潰れて見える ― 髪の毛ほどの
地色が挟まると、面の連なりが読める（ユーザー指定「ほんの 0.1 ミリくらい外側に」）。

- 円は半径 ＋ `HAIR`。多角形は `Body.scale`（**重心まわり**に拡大するので、
  重心と絵の中心の差 `ox/oy` はそのまま使える）。
- ★`setMass` は拡大の**後**に呼ぶ（`Body.scale` が質量と慣性を書き換えるため）。

#### ★★山へ「その日の日付」と「曜日の英語」を落とす（2026-08-25・第60巡にユーザー指定）

「自由」と**同じ枠の無い文字だけの板**で、色は **`INK`（黒）**。GRAVITY の山に
タスクと一緒に転がり、積まれる。

- 語は2つ … `${月}/${日}`（例 `8/25`）と **綴りのままの曜日**（`WD_FULL`。例 `TUESDAY`）。
  TIMELINE の見出しが3文字（`WD3`）なのは**列の見出しだから**で、こちらは山に転がる
  一枚の板 ― 役が違うので長さも違ってよい。
- 字の大きさは「**塗りの幅**が山の内寸 × `PILE_WORD_W`(**0.66**) に収まる」で決める。
  ★★**日付と曜日で別々**（第63巡）。2枚で1つにすると、長い `WEDNESDAY` に引きずられて
  曜日が小さくなる（ユーザー指摘「落ちてくる曜日をもう少し大きく」）。
  「語によらず1つ」は TIMELINE の「自由」の約束であって、役の違う2枚には効かせない。
  日付は `PILE_DATE_W`(0.62) ぶん控えめの幅で組む。
- ★板の遊びは**「自由」より小さく**（`PILE_WORD_PAD` 4 / `PILE_WORD_PAD_Y` 2）。
  `8/26` のような短い語では、`FREE_PAD`(8) だと塗りに対して箱が目に見えて大きい
  （ユーザー指摘「日付の図形の当たり判定が文字に対して少しだけ大きい」）。太さは `WORD_WEIGHT`(**900**)、
  書体は `LATIN`（日付・曜日は欧文。`自由` だけは `SANS` — Archivo にグリフが無い）。
- ★★★**物体は「文字の塗り」そのもの**（第61巡にユーザー指摘「当たり判定が文字の
  塗りから離れすぎ」）。`measureText` の
  `actualBoundingBoxLeft/Right/Ascent/Descent` から**インクの矩形**を出し、
  `FREE_PAD` だけ遊びを足したものを物体にする（`inkBoxOf`）。
  第60巡までは「画面幅の 46% × その 40%」の決め打ちだったので、`8/25` のような
  短い語では**箱が塗りよりずっと大きく**、何も無い所で当たっていた。
  ★`textBaseline:"middle"` の原点と塗りの中心は**一致しない**（大文字や数字は em の
  中で上に寄る）。ずれを `wordDx/wordDy` に持ち、描くときに引く ―
  **これをしないと物体の中心と字の中心がずれる**。
- ★★これは**タスクではない**ので、タスクの増減で消してはいけない。山を組み直す

#### ★★山（pile）でも図形を掴める（第54巡にユーザー指定）

- **長押し（`HOLD_MS`=150）してから動かす**と図形を運べる。**すぐ動かす**と空間の
  スワイプ（モードの出入り）になる。
  ★★**掴みは `setVelocity` で運ぶ**（第55巡）。`setStatic` ＋ `setPosition` で瞬間移動
  させると**他の図形をすり抜ける**（実機で発覚）。動く物体のまま毎フレーム
  「指へ向かう速度」を与えると、周りを**押しのけて**山が崩れ、離した勢いもそのまま
  投げに残る。掴んでいる間は `engine.enableSleeping = false`（眠っている物体は
  当たり判定が起きない）。離したら戻す。
  ★図形に触れただけでスワイプを塞ぐと、山が埋まっているとき TIMELINE を開けない。
  ★重いフレームで最初の `move` が 150ms 以上遅れることがあるので、`beginHold` は
  **すでに指が動いていたら掴まない**。
- ★★**掴んでいる間は無重力**（`engine.gravity.y = 0`。第58巡にユーザー指定）。
  重力があると運んでいる図形が下へ引かれ続けて、口やブラックホールへ寄せにくい。
  離したら `GRAVITY_Y` へ戻す（掴みが流れた経路でも戻すこと）。
- 掴んでいるあいだ、右下から**口とゴミ箱**が出る（`components/tasks/DropTargets.tsx`。
  DRIFT と共通の部品）。**口＝完了**（`done` にして粉砕の破片を飛ばす）、
  **ゴミ箱＝削除**。どこでもない所で離せば、その速さで投げられて落ちる（`FLING`）。
- ★左端（`EDGE_PX`）から始めた指だけは掴まない（ALIGN の入口を優先）。

#### ★★DRIFT（`components/tabs/DriftTab.tsx`）— 無重力の場と口/ゴミ箱（第44巡）

2026-08-24 にユーザー指定で**規定の格子をやめ**、候補を**無重力で漂わせる**形へ
作り直した。per-item の DOM（旧 `.drift-bob`）ではなく、**1枚の canvas に matter.js
の図形を描く**（`engine.gravity=0`・`enableSleeping=false`・四方に反発 1 の壁）。
一律の幅で湧かせ、微速をランダムに与えて漂わせる。

**掴む・捨てる・食べる:**
- **タップ**（動かさず離す・`HOLD_MS`=150 未満）… `TaskComposer` を開く（候補の編集）。
- **ホールド**（150ms 押さえる／`TAP_MOVE`=8px 動かす）… 図形が `static` になり
  自由に運べる。同時に**右下の黒い丸から口（上）とゴミ箱（下）が滑り出す**
  （`.drift-target.in`）。
- **口の上で離す＝完了**（`accept`＝候補を GRAVITY のタスクへ）、**ゴミ箱の上で
  離す＝削除**（`reject`）。当たり判定は的の実測 `getBoundingClientRect`（14px の
  遊び）。離すと図形は的の中心へ吸われて縮んで消える（`gone`）。
- **どこでもない所で離す**… 指の速度で放り投げる（`FLING`=1.0）。無重力なので
  そのまま滑っていき、空気抵抗でやがて止まる。
- ホバー中は的が `.hot`（口は開き＝`scaleY`、ゴミ箱は震える。色でも応える）。
  離した瞬間は `[data-fire]`（噛む／落ちる）。CSS は `app/globals.css` の
  `.drift-target`。時間・曲線は語彙から（`--t-item`／`--t-press`／`--ease-settle`）。
- ★★**投げたら減速して止まる**（第54巡にユーザー指定）。第44巡は速さの**下限**を
  保って永久に漂わせていたが、下限をやめ**空気抵抗**（`DRIFT_AIR`=0.016）で静かに
  止める。止まったらループも止める。
- ★★★**速さの上限を投げの速さより低く置かないこと**（第56巡・「投げても慣性が
  かからない」の正体）。第54巡に下限を外したとき `clampDrift` の**上限 1.0 が
  そのまま残っていた**。1.0 は**毎秒 60px** なので、投げは生まれた次のフレームで
  毎回潰されていた。上限は**壁抜け止め**としてだけ持つ（壁の厚み 80px に対して 26）。
- ★★**掴んでいる間も `setStatic` にしない**（第56巡。GRAVITY と同じ作り）。静止物に
  すると当たり判定が消えて他の図形をすり抜けるうえ、離した瞬間の速度が**物理には
  無い**ので投げが死ぬ。毎フレーム指へ向かう速度を与える。
- ★★**投げの速さは時間で割って1ステップぶんへ揃える**。1イベントの差をそのまま
  使うと、120Hz の端末では 60fps の物理に対して半分になり、離す直前に指が止まると
  0 になって投げが消える。**直近に動いていた値**を持ち、古ければ「置いた」扱いにする。
- ★★**器は `full-bleed`** なので canvas は画面より上下左右へはみ出している
  （実測 422×894 @ -16,-16）。`size.h` をそのまま床にすると**タブバーの裏まで**
  器が広がり図形が潜り込む。**画面の座標を canvas の座標へ変換してから**壁を置く
  （`fieldOf()`）。第54巡のユーザー指摘「図形がタブの下に潜り込む」の原因はこれ。
- ★湧く位置は**画面の真ん中あたり**。ただし同じ点に重ねると、大きな図形が押し合って
  壁をすり抜け画面の外へ飛ぶ（実測）。**ひまわり配置**（黄金角）で中心に寄せつつ
  均等にばらす。件数が多いときは `FIT_N` を基準に**平方根で縮める**。
- ★図形の上での `pointerdown` は `stopPropagation`（空きを掴んだときだけ外へ任せる）。
- ★`active`（そのタブが画面に居るか）で rAF を止める（`ctrlRef.setActive`）。
  DRIFT タブから離れたら物理を回さない。
- ★★★**器の bleed は `TaskSpace` の `<main>` だけが持つ**（第63巡に根治）。
  `DriftTab` の `wrapRef` にも `className="full-bleed"` が**二重に**掛かっていた。
  `position:absolute; inset:0` に負のマージン（`-pad-top / -16px / -nav-h`）が乗ると
  **箱が外へ広がる**ので、canvas は「幅＋64px / 高さ＋pad-top＋nav-h」になる。
  その寸法で `fieldOf()` を出すと、場の下端が**ちょうどタブバーのぶん低く**なり、
  候補がタブの裏へ潜る（実機の写真で2度報告）。
  ★**GravityTab の器には付いていない** ―**同じ器に居るのに片方だけ壊れるときは、
  片方だけ違うことをしていないか**を最初に疑う（第61巡とまったく同じ教訓）。
- ★★**表に出るたびに置き直す**（`reseed()`。第63巡にユーザー指定「開くたびに
  真ん中ら辺でランダムに」）。DRIFT は第62巡から**出しっぱなし**なので、再マウントでは
  起きない ― `setActive(true)` の**立ち上がり**でだけ呼ぶ。物体は作り直さず、
  位置・角度・初速だけ入れ直す（作り直すと焼いた絵のキャッシュまで捨てることになる）。
- ★★★**場は「自分の寸法」だけで決める。画面の座標を測ってはいけない**（第61巡に根治）。
  `fieldOf()` は `size`（`wrap.offsetWidth/Height`）から
  `left = (w - innerWidth)/2`（`full-bleed` の -16px ぶん）／`right = w - left`／
  `top = FIELD_TOP`／`bottom = h - navHeightPx()` を出す。**`getBoundingClientRect` を
  読まない。**
  - **なぜ** … `AppShell` の列は**一周ループのために `translateX(±300%)` がアプリを
    切り替えた瞬間に飛ぶ**し、`mountedApps` はアイドルで後から増える。画面の座標を
    canvas の座標へ変換すると、**測った瞬間と実際に見えている瞬間がずれる**。
  - **第58巡**は「原点が動いたぶん図形を運ぶ」（`lastField`）、**第60巡**は「流すのを
    matter が来てから」（`flush()`）と**タイミングを合わせにいった**が、どちらも
    対症療法で実機では直らなかった（写真つきで2度報告された）。
  - ★**GRAVITY はこの症状が一度も出ていない** ― `sizeRef` しか見ていないから。
    **同じ器に居るのに片方だけ壊れるときは、座標の出どころを疑う。**
  - 指の座標は `cv.getBoundingClientRect()` を**イベントのたびに**読むので、
    列がどこに居ても正しい（ここは変えなくてよい）。
  - 図形の大きさも**場の幅**から出す（`window.innerWidth` を混ぜない ―
    場と大きさの出どころは1つにしておく）。
- 溜めた列を流すのは「matter が来ていて、見えていて、**寸法が来ている**とき」だけ。
  条件は `flush()` 1か所に集め、`setActive` と matter の読み込み完了と
  `ResizeObserver`（最初に有効な寸法を拾ったところ）の**3つ**から同じ関数を呼ぶ。
- ★★**縦の払いはどこから始めてもよい**（第61巡）。図形の上でも、掴む前に動き出したら
  払いに変わる ― DRIFT は図形で埋まっているので、空きからしか払えないと上スワイプ
  （GRAVITY へ）が実質使えない。GRAVITY と同じ作法に揃えた:
  **長押ししてから動かす＝運ぶ / すぐ動かす＝空間の払い**。

#### DRIFT の散らし方

**ゆらいだ格子**。件数から列（1/2/3）と行を決め、マスの真ん中へ置いてから
id 由来の値でずらす。★ずらす量は**マス1つの寸法**に掛けること — 器の幅に
掛けると3列のとき器の12%（=44px）動き、右端の候補が画面の外へ出た。
ずらした後も中心±半分が器に収まるよう `clamp` する。
揺れは環境ループ `--t-amb-bob`（5.4s）で、始まりを id からずらす。

**候補の大きさは揃える**。重さ（重要度 × 切迫度）を持つのは確定してからで、
漂っているうちはまだ量られていない、という区別を形で示す。

### 寸法の対応
```
塗られる面積 = 重要度 … weightArea(小1.6/中3.6/大8.0) × 期限の倍率
  期限の倍率 … 今日・過ぎ 2.2 / 1〜2日 1.6 / 3〜7日 1.1
               8〜30日 0.7 / 31日〜 0.45 / 期日なし 0.55
  → 面積の幅 24.4:1（辺の比 4.9:1）。★大きさに効くのはこれだけ
  形ごとの塗り率(inkRatio)で外接箱を広げるので、**形が違っても同じ重要度なら
  色の量が同じ**（円/半円 0.78・三角 0.50・四角 1.00）
縦横比 … **四角だけ**題の長さのはしご 1:2 / 3:4 / 1:1 / 3:2 / 5:2 / 4:1
        円 1:1・半円 2:1・三角 1.155:1 は**必ずその比を保つ**
形     … 埋まっている側面の数（1..4）      lib/solid.ts
        題だけ=円 / ＋日付=半円 / ＋メモ=三角 / ＋持ち物=四角
        ★2 番目の面は **dueDate**（自由文の `when` は 2026-08-16 に廃止）
スラブ … 残っている手順（大きさには効かない）
色・書体 … タグ                            lib/taskTags.ts
落ちる順 … 切迫度（期日）
```
★**幅に上限を置かないこと**。以前は `LEN_MAX 4.0` で頭打ちにして余りを高さへ
回していたため、本来 2:1 の半円が **1.06:1 のドームに潰れていた**。画面に
収める役目は一括スケールが持つ。
★`sectionOutline` は**縦横とも −0.5〜0.5** に正規化。`(w, h)` を掛けた外接箱が
ちょうど `w × h` になり、「箱の面積 × 塗り率 ＝ 塗られる面積」が形によらず
成立する。その形の本来の比は `naturalRatio()` が別に持つ。

### タイトルの組み方
`layoutInShape()` が **`max(16px, 0.34 × √面積 × unit)`**（上限 64px）から始め、
折り返し、それでも入らなければ縮める（最大 3 行）。
★基準に √面積 を使うのは**縦横比に左右されないため**。

★**折り返す幅は行ごとに違う**（2026-08-16 確定）。断面のその高さでの半幅を
`halfWidthAt(sides, y)` から引き、行の**狭い方の端**で測る。矩形 1 つ
（`innerBox`）に収めていた頃は三角が外接箱の 23% しか使えず（四角は 79%）、
同じ面積でも**三角だけ文字が半分以下**になっていた。いまは 1.5 倍。
縦の置き場所も形で決める — **三角は下寄せ**（広い方へ寄せる）、他は中央。
`innerBox` はタグビュー（`fitText` で英字を図形いっぱい）だけが使う。

  html の地色が同じ色になっているので、覆わなくても継ぎ目は出ない。

  と書いた。**`VoiceOverlay` には入力欄が 1 つも無い** — キーボードが出ない

  |---|---|---|

  （実機で「アイコンとタイトルのウィンドウがスクロールして動く」と報告）。
- ★★★**全画面のオーバーレイは「送れる箱を減らす」ではなく「動かせるものを
  名指しで許す」側から書く**（2026-08-18・第14巡。「まだスクロールできる」が
  3 巡続いた）。器の中を `clip` にしても消えなかったのは、**送っているのが器では
  なかった**から。iOS は指の下に送れる箱が見つからないと、**その先（後ろのタブの
  列・ページ・見えている矩形そのもの）を送りにいく**。だから 2 段構えで止める:

  1. `document.documentElement.dataset.overlay = "1"` を立て、CSS で
     **後ろのタブの列を止める**（`[data-overlay] [data-tab-scroll-root] { overflow: hidden !important; }`）。
  2. **`touchmove` を素の非 passive で受け、本当に送れる箱の中でなければ
     その場で `preventDefault()`**。「本当に送れる箱」＝ 祖先をたどって
     `overflow-y/x: auto|scroll` かつ**実際にはみ出している**もの
     （行の並び・カレンダー・ダイアル・タイムライン）。二本指も止める。

  流れ続ける。カレンダーの横払いも時刻のダイアルも生きたままである（実測済み）。
- ★**器の中に「はみ出し」を作らないこと**（2026-08-18）。
  `overflow: hidden` の箱は**送れる箱**なので、iOS はキャレットを見せるために
  そこを送ってくるし、右端にスクロールバーも出す。**`overflow: clip`** は
  箱そのものを作らないので、構造的に送れない。
  **器（`[data-composer-shell]`）自身も `clip`**。図形の canvas のように
  器より大きいものを置く面も `clip`。行の並びだけは `auto`（手順は増える）だが、
  `scrollbar-width: none` でバーは出さない。
  検証は「器と、その中のどの箱も `scrollTop` を書いても 0 のまま」
  （`scrollHeight` の大小ではない — `clip` ははみ出しても送れない）。

### 一括スケールと間引き（`pileOf`）
「小さすぎるものは出さない」と「混雑しても大きい図形を残す」を同じ仕組みで解く。
面積の降順に並べ、先頭 N 件だけで縮尺を出しながら N を増やし、次のどちらかで止める。

- **これ以上入れると `SCALE_MIN 0.70` より縮めないと収まらない**
  → 縮めるのではなく**間引く**
- **その 1 件自身が `CULL_PX 30` を割る** → どうせ読めないので入れない

★最後に、**いちばん大きい 1 枚が画面に収まる**ところまで縮める
（幅 `FIT_W 0.86` / 高さ `FIT_H 0.62`）。面積の合計だけで決めていた頃は、
数件しか無いと縮尺が上限に張り付き、重要度の高い 1 枚が画面より大きくなって
壁に挟まったまま宙に浮いていた。渡す高さからは**見出しのぶん**
（`MASTHEAD_H 108`）も引く — 引かないと山が見出しに重なる。

含める数を増やすほど縮尺は単調に下がるので、この走査は一意に決まる。
実測: 4 件→4 件表示・最大 278px / 16 件→16 件・146px / 40 件→10 件・137px /
80 件→9 件・137px。★**間引かれたタスクは画面から触れなくなる**（ユーザー了承済み）。

LOD は代表寸法 `s = √面積 × unit` で決める。`>=48` 3 行 / `30〜48` 1 行 /
`<30` 文字なし / `<16` 切れ目なし。

### ★★書体が揃ったときの捨て方（2026-08-18・第17巡）

**`onFontsReady` は「購読しただけ」で呼び返してはいけない。**
以前は `document.fonts.ready.then(cb)` を置いていた。これは**もう揃っていれば
即座に解決する**ので、`SolidCanvas` が 1 枚マウントされるたびにコールバックが
走っていた。そのコールバックは `clearSolidBitmaps()` ＝ **みんなで使っている
焼き上がりの全消し**なので、

- 入力画面を開くだけで**山の絵が全部消え**、閉じたあとに焼き直されて
  **文字が点滅**する（実機で報告。Chromium でも閉じた 350ms 後に
  色数 241→51 と再現できた）。
- タブを行き来するたびに焼き直しが走る ＝「全体的に処理が間に合っていない」。

揃っていない面は `requestGlyphs` の `load().then` が拾うので、これは要らない。
`loadingdone` の安全網も、**面の顔ぶれ（`document.fonts.check` の並び）が実際に
変わったときだけ**動かす。

### ★守ること
- **`ctx.font` は CSS 変数を解決できない。** `var(--font-…)` を含む文字列を
  代入すると黙って失敗し、既定の 10px サンセリフのままになる。
  `resolveFamily()` で `getComputedStyle(document.documentElement)` から
  一度だけ解決する。
- **文字はグリフのアトラス経由で描く。** 和文の Web フォントは unicode-range で
  数百の `@font-face` に分割されており、`fillText`/`measureText` は
  **(書体, 文字) の組ごとに初回 5〜10ms** かかる。素直に描くと落下中に
  `fillText` だけで 2.4 秒。同じ (書体, 文字, 色) は一度だけ焼いて
  `drawImage` で使い回し、**1 フレームに数枚だけ**焼く（`GLYPH_BUDGET = 4`）。
  ★1 枚では足りない — 16 個 × 8 文字 ≒ 130 枚を 1 枚/フレームで焼くと 2 秒以上
  かかり、そのあいだに断片が届いて振り出しに戻るため文字が一度も出なかった。
  ★**焼く大きさをバケツ `[32, 64, 96]` に丸める**。常に 128px で焼いて
  13px へ縮めていた頃は 9.5 倍の縮小になり、`drawImage` が標本を落として
  文字がジャギーになっていた。ただし**段を増やしすぎない** — 同じ文字が段の
  数だけ焼き直されるので、7 段にしたら落下中の `fillText` が 868ms へ増えた。
  図形の絵は `bakeDpr = min(dpr, 1.5)` で焼く（1.25 では画面へ 1.6 倍に
  拡大されて滲み、2.0 では画素が 2.56 倍になって 800ms 級のひっかかりが出た）。
- **和文の送り幅は測らない。** 全角（かな・漢字・全角記号）の `advance` は
  必ず 1em なので、`measureText` を飛ばす。題の文字数ぶんが 1 フレームに
  まとまって走ると 666ms 止まった。
- **欧文（タグの英字）の送り幅は暇な時間に先に測っておく**
  （`primeAdvances` を `requestIdleCallback` で数組ずつ）。BOTTOM へ
  切り替えた瞬間に 5 書体ぶんがまとめて走ると 328ms 止まる。
- 実測（4× CPU 絞り・本番ビルド、16 個）… 落下 合計 1300ms 前後 / 最大 190ms、
  ビュー切替 最大 130ms、積み終わったあとと横スワイプは 0ms。
- **和文の Google フォントは 1 書体につき 1 ウェイトまで。** 3 書体 × 3
  ウェイトで turbopack が `Module not found` を出す。太字・斜体はブラウザの
  合成に任せる（`app/layout.tsx`）。
- **`document.fonts.load()` の Promise は必ず `.catch()` する**
  （unhandled rejection で pageerror が飛ぶ）。書体が届いたら
  `onFontsReady` でアトラスとビットマップを捨てて描き直す。
- ★★**「書体が届くまで文字を描かない」は必ず時間で門を開けること**
  （2026-08-17。実機で「文字が表示されない・アプリ全体が不安定」）。
  `textDrawable(face, text)` は「届いた **または** 頼んでから 600ms 過ぎた」で真。
  待つだけにしていたら、次の 3 つのどれか 1 つで**文字が永久に出なかった**:
  - **WebKit の `document.fonts.check()` が偽を返し続ける**
    （unicode-range で分割された和文の family に対し Blink と挙動が違う）。
    → `computeTextPlan` が `null` を返し、その `null` が `planCache` に載る。
  - **判定結果のキャッシュに「取りに行く前の偽」が焼き付く** →
    届いたあとの再判定も偽を読むので、**焼き直しの通知が一度も飛ばない**。
    取りに行く前後の比較は**キャッシュを通さない生の `check()`** で行う。
  - **`loadingdone` のたびにアトラスを全消し**していた → 断片は 100 以上
    あるので、1 フレーム数枚しか焼けないアトラスが焼き切る前に振り出しへ
    戻る。`pendingBake` が立ち続けて **rAF も止まらない**。
  → 捨てるのは **400ms にまとめて、届いた面のぶんだけ**（`dropFace`）。
  安全網の `loadingdone` は **`document.fonts.status === "loaded"`（＝読み込みが
  落ち着いた）ときだけ**動かす。
  ★**「何も出ない」より「一度 fallback で出てから本物に差し替わる」**方がまし。
  検証は `document.fonts.check` を偽で固定して実機を再現し、山の画素の色数を
  数える（修正前 125 色・文字の画素 19 → 修正後 336 色・6779）。
- **当たり判定は描く形そのもの**。断面の多角形
  （`Bodies.fromVertices`）。長方形で当てていた頃は、形の周りの見えない余白
  どうしがぶつかって図形が宙に浮いて見えた。**丸だけは `Bodies.circle`**
  （36角形は衝突判定が重く、転がりもカクつく）。物理の頂点は 12 点まで
  間引く — 半円の 37 点を 16 個ぶんまとめて `fromVertices` に通すと、
  凸包の計算で 400ms 級のひっかかりが出た。
  ★`fromVertices` は**重心**を `body.position` に置くが、絵は図形の原点を
  中心に焼いてある。三角形のように両者がずれる形では、そのズレ（`ox`/`oy`）を
  描画側で戻すこと。戻さないと絵と当たり判定が食い違う。
- 手順を済ませて形が変わったときは、位置と速度を引き継いで body を差し替える
  （ビュー切替は全部作り直すので、こちらは編集のときだけ）。
- **落下位置の hash に連番をそのまま使わない。** `"t1","t2",…` は hash も
  連番になり、全部が同じ x に落ちて 1 本の塔になる。黄金比の定数を掛けて混ぜる。
- ★★**`document.fonts` には「先頭の family だけ」を渡す。**
  `next/font` は `--font-dela-gothic-one` を
  `"Dela Gothic One", "Dela Gothic One Fallback"` に展開する。後ろの
  *Fallback* は**端末のフォントに寸法だけ合わせた `local()`** なので
  **常に読み込み済み**。スタックごと `load()` に渡すと、それで即 resolve して
  **本物の断片を取りに行かない**。実測（2026-08-17）:
  スタックで load → 塗り率 **17%**（素のサンセリフ）のまま /
  先頭だけで load → **37.9%**（本物の Dela）。
  ★これを間違えていたため、**和文のディスプレイ書体は一度も表示されて
  いなかった**（それまでの「書体の違い」は太さと斜体の合成だけ。だから
  「赤と黄が同じに見える」ことになった）。`primaryFamily()` / `checkFace()` /
  `textDrawable()` / `ensureGlyphs()` が唯一の窓口。`ctx.font` の方はスタックのままでよい
  （届いていない間は fallback で描くため）。
- **書体は待たずに「取りに行く」。** 断片の取得が始まるのは**その文字を
  初めて描いた瞬間**なので、`document.fonts.ready` も `loadingdone` も
  「鳴る前に焼いてしまった絵」は救えない。焼く直前に `ensureGlyphs()` を
  呼び、**まだ使えないときだけ**、届いた時点でアトラスと割り付けを捨てて
  購読者へ知らせる。
- ★**書体が届くまで文字を描かない**（`computeTextPlan` が `textDrawable` で
  門番をする）。グリフは 1 フレームに数枚しか焼かない（落下のガクつき対策）
  ので、焼いている途中で書体が届くと**前半 fallback・後半 本物**の絵になる
  （実機で「1 つの図形に 2 書体」として報告された）。
  **fallback で焼かなければ混ざった絵は存在し得ない。**
  ★★ただし**門は必ず時間で開ける**（600ms）。理由と再現手順は上の
  「性能の作法」の節に書いた — 待つだけにしたら実機で文字が永久に出なかった。
- **入力画面のプレビューは倍率を固定する**（`SolidCanvas` の `unit`）。
  器いっぱいに拡大すると、重要度や期限を変えても絵の大きさが変わらず
  「大きさ ＝ 重要度」が読めなくなる。

## 6. ブリーフ生成（運用ポリシー）

パイプラインの詳細は `SYSTEM-DESIGN.md`、実装は `lib/briefPipeline.ts`。
**ここに書くのはユーザーが明言した「これを正とする」運用だけ。**

### 情報源とカードの関係（§8.15）
- **情報源の本体は、雑多で高品質なネットマガジン**（カルチャー・技術・生活・
  音楽・ファッション）。淘汰・入れ替えでゆっくり好みに追従する。
  ここから、興味に合致する＝**提案カード**、合致しない新着＝**情報カード**。
  **カルチャー誌の「記事」を第一級で扱う**のが中核の体験。
- 展覧会・映画・イベントの集約サイトは、**情報が集約されているから固定に
  しているだけ**で、他の情報源と完全に平等。**抽出・分類・枚数配分のどこにも
  「展覧会を優先する」構造を作らない。**

### 更新と枚数（§8.18）
- **1 日 2 回**（朝 06:30 JST / 夕 13:30 JST の Cron）、各 **10 枚くらい**。
  事前に生成してストックし、アプリを開いたら即出る。
- 未消化カードの保持は **3 日**。ストック上限 **40 枚**（超えている間は追加生成
  しない）。キーは**日付だけ**（`YYYY-MM-DD`。朝刊／夕刊の概念は撤去済みで、
  Cron は置き換えではなく **id 重複を除いた積み増し**）。
- **「今すぐ生成」はテスト用**。完成時に削除する。

### 構造（§8.19）
2 層＋コード検証。**AI に「落とす」判断をさせない**ので、候補が 1 件でもあれば
構造的に 0 枚にならない。
- 層 1（サイトごと・並列）… 抽出と関連度付け（0〜100）を 1 回で。
- 選抜（コードのみ）… 出典 URL の実在検証・終了済み／圏外／重複の除外の後、
  関連度順にサイト横断ラウンドロビン。`>=80` ストレート／`50〜79` 派生／
  `<50` 情報カード。**trigger もコードが関連度から決める。**
- 層 2 … 採用分だけ個別ページを取得して本文を詳細化。

### ★絶対の原則
- **LLM に URL を抽出させない。** 抽出のつもりが推測創作になる（§8.12.5 で
  実在しない展覧会を丸ごと捏造した）。URL は必ず**コードが実 HTML／Markdown
  から機械的に取り出した集合**で照合し、外れたカードは機械的に捨てる。
- **retrieval は Jina Reader を第一に**（`r.jina.ai`・**鍵なし**）。生 fetch は IP ブロック・
  JS 描画・正規表現依存で繰り返し失敗した（§8.12.13）ので**主にはしない**。
  ★★ただし第64巡から**保険として直接取得を持つ**（下の項）。

### ★★★取得は2段。そして「失敗は必ず理由ごと残す」（2026-08-26・第64巡）

**6日間、提案カードが1枚も作られていなかった。** 原因は `r.jina.ai` が
2026-08-21 からすべての要求に 4xx を返しはじめたこと（鍵切れ・無料枠の締め付け）。
夜間 Cron は**毎日「緑」で成功**していた。カード本体は 3日で消えるので、
3日後にプールが空になり、画面が「今日はここまで」になった。

**なぜ気づけなかったか** … `SiteTrace` が `fetched: false` しか持たず、
**HTTP コードもエラーも残らなかった**。ジョブの成功／失敗も HTTP 200 だけを見ていた
（生成 0 枚は 200 で返る）。唯一の手がかりは**実行時間**（60秒前後 → 13秒前後）で、
これは 4xx が待たずに返っていた形跡だった。

守ること:

0. ★★★**Jina には鍵を送らない**（第64巡にユーザー確定「ずっと無料で」）。
   料金の当たり方が**2つ**あり、**どちらに乗るかで寿命が決まる**:

   | | RPM | 課金 | 寿命 |
   |---|---|---|---|
   | 鍵を送る | 100 | **読んだぶんトークンを消費** | 無料枠1000万トークンは1日2回×20〜26ページで**約50日**で尽き、以後 402 で**全滅** |
   | 鍵を送らない | **20（IPごと）** | **トークンは減らない** | 1分あたりの本数さえ守れば**永久に無料** |

   実際に 2026-08-21 07:02 に残高が **-249,999** になって6日間止まった。
   **尽きる仕組みに乗っている限り必ずまた止まる**ので、既定を鍵なしにした。
   - 鍵を使いたいときだけ **`JINA_USE_KEY=1`**（`JINA_API_KEY` があるだけでは送らない）。
   - ★**鍵が 401/402 を返したら、その場で鍵を捨てて撃ち直す**（`jinaKeyDead`）。
     枠切れの日に全滅せず、レート制限側へ移る。
   - ★鍵なしのときは**全体で 18 RPM**（`KEYLESS_RPM`・20 に1割の余裕）に絞る。
     `jinaSlot()` が順番を配る。**同時実行数は絞らなくてよい** — 単スレッドなので
     順番の予約は await の前に同期で終わり、取り合いにならない。
   - ★★間引きには**締切**がある（`JINA_PACE_BUDGET_MS` = 210秒）。過ぎたら待つのを
     やめる ― 待ち続けて関数ごと打ち切られる（＝0枚。いま直している失敗そのもの）より、
     429 覚悟で撃つ方がまし。
   - ★★**`s.jina.ai`（検索）は鍵なしでは使えない。** 補充検索は「候補が少ない日だけ」の
     おまけなので、鍵なしのときは**静かに諦める**（エラーにしない）。
   - 単体で確かめる … `npx tsx tools/jina-check.mjs`（fetch を差し替えて3つの約束を検査）。

1. **取得は `fetchViaJina` → `fetchDirect` の2段。** 直接取得は `OG_UA` を名乗り、
   `htmlToMarkdownish()` で HTML を**Jina と同じ形**（`[文字](絶対URL)` を含むテキスト）へ
   均す。★ここを合わせておけば**下流は1行も変えなくていい** ―
   `stripMarkdownNoise` → `markdownUrlMap` がそのまま効き、実在URL集合も同じに作れる。
   ★これは**保険**で置き換えではない（サイトによっては直接取得も弾かれる）。
2. **`SiteTrace` に `via` / `jina` / `direct` を必ず入れる**（HTTPコード・`timeout` 等）。
   `cronStatus.fetchFail` に `"jina 401×10 ／ 直接 403×10"` の形でまとめ、
   設定タブ「ブリーフ生成の状況」に**取得できなかった理由**として出す。
3. ★**「0枚」と「失敗」を混同しない。** `ok: true, cardCount: 0` は正常応答なので、
   ジョブは緑のまま。**枚数ではなく取得の内訳を見ること。**
- **機械的な処理はコードで、LLM に投機させない**（日付の期限切れ判定、距離の
  計算、枚数の配分、重複の統合）。

### ★★育成カード（チェックイン／マイルストーン）の約束（第64巡に確定）

育成カードの id は `` `${kind}-${goalId}` `` で**日付を含まない＝日をまたいで同じ**。
プールのカード（生成ごとに一意な id）とは性質が違うので、**扱いを混ぜない**。

- ★★**差し込みの判定と、進行度の数え方は「同じ入れ物」を見る。**
  どちらも**今日の号**（`briefs[todayKey()].decisions`）。第63巡までは差し込みが今日の号、
  数える方が**全号マージ**で、昨日の決定が「今日も消化済み」に数えられていた。
  結果、プールが空なら `deck.length === 1 / index === 1` でいきなり「今日はここまで」、
  プールがあっても**先頭の1枚が黙って飛ばされて**いた。
  ```ts
  const decidedOf = (c: DeckCard) => (isGrowthCard(c) ? decisions[c.id] : allDecisions[c.id]);
  ```
- ★**「あとで」＝ 次の間隔まで出さない**（ユーザー確定）。skip したら
  `Goal.snoozedAt.{checkin,milestone}` に時刻を残し、`dueCandidate` は
  **最後の記録と `snoozedAt` の遅い方**から日数を数える。
  ★`checkIns` に空の記録を積む手は採らない（ゴールのバインダーに中身の無い記録が並ぶ）。
  ★移行 … 第63巡までに skip した人は `snoozedAt` を持たないので**1度だけまた届く**。
  そこで「あとで」を押せば記録が入り、次の間隔まで静かになる。

### 情報源の淘汰（§8.20）
個別のスキップは記録しないので、打率は**集計値として別に持つ**。
`lib/sourceStats.ts` が `generatedDecks` と `briefs` からドメインごとの
`shown / kept / flagged` を積算し（`countedIds` で二重計上を防ぐ）、
my-brain の `sources/stats.md` へ書く。Cowork の発掘タスクはこの数字だけを
見て並べ替え・淘汰する。

### ★★入力画面は「4 通りの型」で見る（第18巡・`scratchpad/geo4.mjs`）

**これまでの検証には「ずれた場合」が無かった。だから 3 巡続けて同じ所を壊した。**
キーボードの出方は端末で 3 通りあり、さらに**見えている矩形がずれる**型がある。

| 型 | 作り方 |
|---|---|
| A キーボード無し | そのまま |
| B レイアウトごと縮む | `setViewportSize` で縮める |
| C `visualViewport` だけ縮む | `vv.height` だけ差し替える |
| **D ずれる** | `vv.height` を縮め、さらに `vv.offsetTop` を 156 にする |

**どの型でも次の 3 つが成り立つこと**（入力画面の不変条件・第24巡で改訂）:

1. **器の上端 == 見えている上端**（`vv.offsetTop`）
2. **器の下端 == 見えている下端**（`vv.offsetTop + vv.height`）
3. 上のバーの上端が見えている上端のすぐ下（＋セーフエリア上）
4. **帯の下端 == 見えている下端**
5. 図形の中心が見えている範囲の中
6. 日程シートの下端 == 見えている下端

★★★**期待値は「見えている矩形」だけで書く**（第24巡）。第18〜23巡の判定は
`--kb` や `--vvtop` という**代用品の値**を見ていたので、代用品が壊れていても
「正しい」と判定できてしまった。実機の崩れを 14 巡ぶん通した直接の原因。
**位置だけを見ること。**
