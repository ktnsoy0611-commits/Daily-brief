## 0. このアプリは何か

ユーザー本人 1 人のための PWA。タスク管理アプリではなく、
**「やりたいこと」を集め・実行し・記録として綴じる**ための道具。

**絶対に守るユーザーの設計思想**
- タスク化しない（義務や TODO の消化にしない）
- 設定画面を増やさない（`ProfileTab` が唯一の設定で、これ以上増やさない）
- 説明文を置かない（本人専用アプリなので、使い方の案内は不要）
- OS 標準のフォーム UI（ドロップダウン・標準テキストボックス・チェックボックス）を
  使わない。**純粋な幾何学図形・ベタ塗り・太いタイポグラフィだけ**で画面を構成する。
  ★**角丸と円は使ってよい**（2026-08-16 にユーザー指定で改訂）。むしろ
  アプリの語彙は「丸」— タブバーのピル、丸ボタン、`borderRadius: 22` の
  カード。ここから外れた「角の立った矩形だけの画面」は他から浮くので不可。
  使ってよい丸みは **22（板）/ 999（ピル）/ 50%（丸）** の 3 つだけ。
  影は `SOFT_SHADOW` / `SOFT_SHADOW_LG`。
  ★ただし**タスクの図形そのもの**（円・半円・三角・四角）は角を立てたまま。

## 1. アプリの構造

3 つのアプリを、**タブバーの帯を横に払って**行き来する（`lib/apps.ts` が正）。

| 順 | アプリ | `en` | タブ |
|---|---|---|---|
| 0 | ジャーナル `journal` | JOURNAL | レコード `journal-record` / 今日 `journal-today` / アーカイブ `journal-archive` |
| 1 | タスク `tasks` | TASK | 候補 `tasks-drift` / タスク `tasks-gravity` |
| 2 | ブリーフ `life` | EXPLORE | ブリーフ `brief` / ゴール `goals` / ストック `stock` / プラン `execute` |

- 右端からさらに右へ払うと先頭へ**回り込む**（一周ループ）。位置は 0〜2 に
  丸めない**通し番号 `pos`** で持つ。丸めると端で位置が飛ぶ。
- **3 つの列は常にマウントされたまま**。初回描画後に `requestIdleCallback` で
  残り 2 つを先読みし、以後アンマウントしない。
- アプリごとに最後に見ていたタブを覚える（`tabByApp`）。
- 画面左上（`Masthead`）は**アプリ名**（EXPLORE / TASK / JOURNAL）を
  幾何アルファベットで。タブ名はタブバーのアイコンの下に小さく出す。

### ダッシュボード
画面下から引き上げる共通の引き出し（`components/Dashboard.tsx`）。
どのアプリからでも開ける。中身は「選んでいるカード」と「今日のタスク」、
下端に **「今日を終える」**。これで選んだカードは `done` になりアーカイブへ移る。
開き具合は 0〜1 の連続値 `--dash` で、指の位置と 1 対 1。

**メタファー（§38 で確定した体験の構造）**
- Journal … 音声の抽出（テープを巻き、切り出す）
- Task … 落下と粉砕
- Explore … 立体の展開と結合
- 1 日の終わりに 3 要素が 1 枚の幾何学ポスターへプレスされる（**未実装**）

## 2. データモデル（`lib/types.ts` が正）

- `Item` … ストック／プラン／アーカイブに出る「願望の対象物」。
  `kind`（place/exhibition/live/activity/food/movie/book/album/info/thing）×
  `area`（場所の有無は種類と独立の直交軸）。
  `status: candidate → planned → done`、`origin: brief | manual | wish | info`、
  `lat/lng/placeId`、`goalId?`、`expiresAt?`。
  分類の入口は `domainOf(item)`（`lib/helpers.ts`）ただ 1 つ。
  4 ドメイン `ItemDomain = place | experience | info | thing`
  （バショ／タイケン／ジョウホウ／モノ）。
- `Wish` … ✨で書く受信箱。`category: ItemDomain`。KEEP されて初めて Item になる。
- `Goal` / `CheckIn` … ゴールのバインダーと記録。
- `Task extends TaskSides` … §4 参照。面は `SIDE_KEYS = title / due / context /
  belongings` の 4 つで、埋まった数がそのまま図形になる。
  ★2 番目は **`dueDate`（YYYY-MM-DD）**。自由文の `when` は 2026-08-16 に廃止し、
  `migrate()` が「日付なら `dueDate` へ / それ以外は `context` の先頭へ」畳んだ。
  同じ「いつ」が自由文と期日の 2 箇所にあると、大きさ（切迫度）に効くのが
  どちらか読めなくなるため。
- `InboxCandidate extends TaskSides` … Cowork が声のメモから作った候補。
  `dueDate` を持ち、確定するとそのままタスクの期日になる。
- `JournalEntry` / `VoiceNote` … ジャーナルと声のメモ。
- `BriefCard` / `GrowthCard` … ブリーフのデッキのカード。
- `AppState` … 上記すべての入れ物。
  - `generatedDecks: Record<"YYYY-MM-DD", BriefCard[]>` と `cronStatus` は
    **サーバー（夜間 Cron）が所有**する（`lib/dataStore.ts` の
    `SERVER_OWNED_KEYS`）。クライアントは読むが上書きしない。
  - `magazine` / `weekendMeta` / `shelfOrder` は**もう更新されない**
    （それを使っていた UI が廃止済み）。型は互換のために残してある。

**永続化** … `lib/dataStore.ts`。3 モード（cloud / persistent / memory）。
Supabase の環境変数があり、かつログイン済みのときだけ cloud。
localStorage のキーは `qol-app-state-v1`。

★`migrate()` は `wishes` が無い state を**最古の形式とみなして全部捨てる**。
テストで localStorage に state を差し込むときは必ず `wishes` を置くこと。

## 3. デザイン言語

**テクスチャを排除し、ベタ塗りの色面・直線・円などの純粋幾何学**（§38 で確定）。
角度は 0 / 45 / 90 / 180 度のみ。

### 基本のUIフォント（`lib/constants.ts` の `SANS`）— 2026-08-23・第36巡確定

**Helvetica + Noto Sans。** `SANS`（`SERIF`/`DISPLAY`も同じ実体）が
アプリ全体のUI文字の出どころ。Helveticaは端末のシステム書体（読み込み
不要）で欧文・数字を描き、和文はグリフを持たないので次点の
Noto Sans JP（`app/layout.tsx` で`next/font/google`から読み込み、CSS変数
`--font-noto-sans-jp`）へ自動的に委ねられる。
```
export const SANS = '"Helvetica Neue", Helvetica, var(--font-noto-sans-jp), "Noto Sans JP", sans-serif';
```
★**タスクの図形に載る文字(`FONT_FACES`)はこの対象外**（ユーザー確定）。
そちらは骨格の違う5書体を保つ（上の「書体はタグごとに1つ」を参照）。

### 色（`lib/constants.ts`）

**無彩色**（地とタイトル）— ここは色を持たない。カラースキームの対象外。
| 用途 | 定数 | 値 |
|---|---|---|
| 地（EXPLORE / TASK） | `BD_GREY` | `#ECECEA` |
| 地（JOURNAL） | `JOURNAL_BG` | `#B3B3AE` |
| 紙 | `PAPER` | `#FAFAF9` |
| 墨 | `INK` | `#1A1A18` |
| 控えめな字 | `MUTED` | `#8E8E88` |

**カラースキーム `SCHEME`**（2026-08-16 確定・参照画像＝Spotify の配色見本）
— **色の出どころはここ 1 つ**。9 つの「地の色 × その上に載る文字の色」の組で、
使うのは**地の色**の方。文字の色は、その地の上に何かを載せるときの相方。

| 名前 | 地 | 相方の文字 |
|---|---|---|
| `pink` | `#F76FA1` | `#4B2438` |
| `orange` | `#FA6E31` | `#1B2B4F` |
| `sky` | `#509BF5` | `#C4F0C5` |
| `red` | `#EE1B33` | `#F9C3C9` |
| `violet` | `#4100F5` | `#FFFFFF` |
| `yellow` | `#F5E837` | `#EF3E23` |
| `navy` | `#1E3264` | `#F573A0` |
| `wine` | `#8C1932` | `#A3E3C8` |
| `forest` | `#04624A` | `#F7D6D3` |

前からある 6 つのアクセントは**名前を変えずに中身を差し替えて**ある
（`BLUE`=violet / `RUST`=red / `GREEN`=forest / `GOLD`=orange /
`PLUM`=wine / `SLATE`=navy）。呼び出し側は数十箇所あるので、名前は動かさない。
★`GOLD` に黄ではなく橙を当てているのは、その面に**白い ✓ が載る**ため
（黄だと白が消える）。

★**新しい色を hex で直書きしない。** 必ず `SCHEME` から取る。地と字面は
**必ず同じ組から**取ること（片方だけ差し替えると、明るい地に明るい字が
乗る事故が起きる）。

### ★寸法の語彙（`lib/tokens.ts`）— 持ち主はここだけ

**余白・文字・角丸も名前で持つ**（2026-08-23・第33巡）。動きの語彙が
`lib/motion.ts` にあるのと同じ考え方。第33巡の実測で、`fontSize` が約25種類、
`gap` が 2〜12 の連番ほぼ全部、角のある `borderRadius` が13種類と、
**一点物の数字**で埋まっていた。画面ごとに手ざわりが違う直接の原因だった。

| 種類 | 段 |
|---|---|
| `SPACE`（余白・**4の倍数**） | `hair` 2 / `xs` 4 / `sm` 8 / `md` 12 / `lg` 16 / `xl` 24 / `xxl` 32 |
| `TYPE`（文字・7段） | `nano` 7 / `micro` 9 / `small` 11 / `body` 13 / `lead` 16 / `head` 20 / `display` 26 |
| `RADIUS`（角丸） | `sm` 4 / `md` 8 / `lg` 12 / `xl` 18 / `sheet` 28 / `pill` 999 / `circle` "50%" |

- `hair`(2) は**罫と光学的な詰め**だけ。それ以外の余白は必ず4の倍数。
- ★**入力欄（`input` / `textarea`）は必ず `TYPE.lead`(16) 以上**。15 以下だと
  iOS Safari がフォーカス時に画面を勝手に拡大し、以後レイアウトが崩れたまま
  戻らない。`lead` を 16 に置いたのはこの閾値に合わせるため。
- `nano`(7) は**小さな操作部品に焼き付いたラベル**（NAME / TAG / 物理キーの名前）
  専用。文章には使わない。使いたくなったら、まず器が小さすぎないかを疑う。

**目盛りの外に居てよいもの**（ここ以外に例外を作らない）
1. `env(safe-area-inset-*)` を含む式 … `TAB_PAD_TOP` / `NAV_BOTTOM_GAP` /
   `NAV_H` / `NAV_OFFSET`。端末が決める値なのでこちらの目盛りには乗らない。
2. **図形の座標系** … `GeoType` / `SolidCanvas` / matter.js / Leaflet /
   `TabIcons` のアイコン内部。これは「UIの余白」ではなく絵の寸法。
3. 噛み合って高さが決まっている部品寸法 … `TAB_MARK`(52) / `NAV_PILL_PAD`(6) /
   `HEADER_CHIP_SIZE`(40)。★タブバーの目印の行（丸 5 + 余白 8 = 13）は
   `NAV_H`(77px) に**組み込まれている**ので、動かすなら両方直す。

### ★ボタン（`components/Button.tsx`）— 押せる面はここだけ

第33巡まで押下の作法が3流派に分かれていた（`useState`＋跳ね返りカーブ /
`data-pressed` を DOM へ直に書く / CSS の `:active` 頼み）。1ファイルへ集めた。

**使い分けは1行で言える … 入力画面（キーボードを出したまま触る面）＝ `Press`
／ それ以外＝ `Button`。**

- `Press` … `<div>`。**`pointerdown` で即座に走る**。`touchstart` の既定動作を
  素の listener（`{ passive: false }`）で止めてフォーカス移動を防ぐ。
  `<button>` を使わないのは、iOS が `<button>` のタップで入力欄を blur するため。
  ★離上を待たないので、**取り返しのつかない操作（削除など）には使わない**。
- `Button` … `<button>`。離上で走る。`variant`（`primary` / `secondary` /
  `ghost` / `icon`）× `size`（`sm` 28 / `md` 36 / `lg` 48）。寸法は `lib/tokens.ts`
  から引く。**輪郭は「文字と同じ色の 45%」**（`color-mix`。以前は BLUE=そのまま /
  RUST=45% / INK=30% とバラバラだった）。1画面に `primary` は1つまで。

### 幾何アルファベット（`components/GeoType.tsx`）
見本から**画像解析して転写**した書体。1 文字＝162×162 の正方形を
「セル 78px＋溝 6px の 2×2 グリッド」に割り、`full` / 四半円 / 端丸帯 / 空 の
4 種を置き、**繋がっているところだけ溝を塗る**。等幅。A–Z と 0–9。
**使うのは `Masthead` のアプリ名だけ**。タグ・棚の見出しは本文の書体
（`SectionLabel`、`components/common.tsx`）。

### ★画面の地色（`lib/ground.ts`）— 持ち主はここだけ

**背景が途切れたら、まずここを見る。**

- `html` の `background-color` と **`<meta name="theme-color">` を必ずセットで**
  書く。ホーム画面へ追加した PWA では、**iOS が自分で塗る領域**
  （キーボードの手前の帯・画面のいちばん下・セーフエリア）に theme-color を
  使うので、片方だけ合わせても帯が残る（2026-08-17 に
  `themeColor: "#1A1A18"` の固定値のままだったのが原因で、
  「キーボードのところで背景が途切れる」「全タブの下端で途切れる」の両方が出た）。
- ★★**積み木は「後勝ち」ではなく「高い層が勝つ」**（2026-08-19・第26巡）。
  `pushGround(color, level)` の `level` は `"app"`（アプリの地）か
  `"overlay"`（全画面の面＝入力画面・録音）。**いちばん高い層**が地色を持ち、
  同じ高さなら後から積んだ方。返り値を呼ぶと外れる（`useEffect` の後始末で必ず）。
  以前は素直に「最後に積んだ層が勝つ」だったが、**積む順は重なり順とは無関係**
  なので、入力画面が開いている最中にアプリ側が積み直すと**アプリが地色を
  奪った**。「画面の一番下だけ背景が適応されない」が何度も再発した正体はこれ。
  **書き手を2つにしないこと**（以前 `AppBackdrop` と `TaskComposer` が両方
  `html` を書いていて、閉じても戻らないことがあった）。
- ★★★**塗る人は3人いるが、色を決める人は1人**（2026-08-19・第27巡）。
  第26巡は「時間」だけ揃えて**色そのものが2つある**まま放置していた。
  帆布（`AppBackdrop`）だけが `groundOf(appId)` を直に見ていたので、
  **入力画面が開いているあいだ `html` は暗いのに帆布はアプリの明るい色**
  という状態になる。帆布は `zIndex: -1` で html の上にあるから、
  **html の色は帆布の外側 — 画面のいちばん下 — にしか出られない**。
  これが「一番下だけ背景が適応されない」の残り半分だった。
  いまは `onGround(cb)` で**勝っている色を購読**し、帆布はそれを塗る。
  ★**全画面に色を塗る面は、自分でアプリの色を決めないこと。**
- ★★**帆布の寸法は `position: fixed; inset: 0`**（同巡）。
  `width: 100vw; height: 100lvh` をやめた。iOS のスタンドアロン（ホーム画面へ
  追加した PWA）では `lvh` が下のセーフエリアを含まないことがあり、そのぶん
  **帆布が画面の下まで届かない**。届かない所は端末が manifest の色で塗る。
  `viewport-fit=cover` の固定要素の `inset: 0` は**セーフエリアを含む画面全体**
  なので、`lvh` がどう計算されようと届かない場所が無くなる。
- ★★★★**`apple-mobile-web-app-capable` を自分で出す**（2026-08-19・第29巡）。
  **これが「画面の下端だけ別の扱い」の正体だった。**
  Next は `appleWebApp.capable` から **`mobile-web-app-capable`（Android 用の
  名前）しか出さない**。iOS はそちらを見ないので、ホーム画面から起動した
  アプリが「マニフェスト方式のスタンドアロン」になり、**web ビューが画面の
  下端まで届かない**。実測（実機の写真を画素で解析）… 円が **y=796.7pt で
  どの x でもまっすぐ**切れ、その下 **47pt** はページが一切塗れない領域で、
  そこは **iOS が `theme-color` で塗っていた**。
  だから「コンポーネントが途切れる」「色の変化がそこだけ遅い」「一応色には
  連動する」が全部同時に出ていた。`app/layout.tsx` の `other` で明示する。
  ★**この値はホーム画面へ追加した時点で端末に焼き込まれる。** 反映するには
  一度ホーム画面から消して、追加し直すこと。
- ★★★★**`statusBarStyle` は `black-translucent` のまま**（2026-08-19・
  第29巡・一度 `default` を試して差し戻した）。`default`/`black` は
  「ステータスバーの見た目だけ変える設定」ではなかった —
  **iOS はステータスバーぶんを web ビューの外(OS が別に確保する帯)として
  扱うようになり**、そこが黒い帯として残り、しかも中身全体がそのぶん下へ
  押し出されて**タブバーの位置までずれた**（実機で「上に変な黒い帯」
  「タブバーが下寄りすぎ」と報告）。`black-translucent` は中身が画面の裏側
  まで1枚で伸び、ステータスバーはその上に透けて重なるだけなので、帯もずれも
  起きない。時計とアイコンが白くなって明るい地色の上で読みにくいのは
  **既知のトレードオフ**（iOS の3択にこれ以外の選択肢が無い。第26巡の写真で
  実際に白く潰れていた）。★**この値を変えて試すこと自体を今後もしないこと** —
  `apple-mobile-web-app-capable` だけで下端の問題は解決している。
- ★★★**`theme-color` は毎フレーム自分で混ぜる**（同巡）。CSS では補間できない
  が、**iOS が画面のいちばん下を塗るのはこの値**なので、1回だけ差し替えると
  そこだけ遅れてパッと切り替わる（第26〜28巡は `GROUND_MS / 2` で1回だけ
  書いていた ＝「そこだけ遅い」の直因）。`lib/ground.ts` が `requestAnimationFrame`
  で `GROUND_EASE` と同じ曲線を数値で解き、`GROUND_MS` かけて混ぜる。
  実測 … 動き出しのずれ 0ms・途中 16 色・html と同じころ終わる。
- ★**`app/manifest.ts` の `theme_color` / `background_color` もアプリの地色
  （`BD_GREY` `#ECECEA`）に揃える**（同巡）。この2つは**ホーム画面へ追加した
  時点で端末に焼き込まれ**、iOS が自分で塗る領域に使われる。`#1A1A18` のまま
  食い違っていた。★変えても既にホーム画面にあるアプリには反映されない —
  一度消して追加し直すこと。
- ★★**塗る人は3人いる。時間を必ず揃える**（同巡）。
  ①列（`AppColumn` の地色。`.app-track` の横スライド **380ms**）
  ②帆布（`AppBackdrop`。シェルの外側＝オーバースクロールとセーフエリア）
  ③`html` ＋ `theme-color`（iOS が自分で塗る領域）。
  以前は 380ms / 420ms / **即座** だったので、**画面の一番下だけ先に切り替わった**。

### ★モーションの語彙（`app/globals.css` の `:root` ＋ `lib/motion.ts`）

**曲線は4本、時間は5つだけ。増やさないこと**（2026-08-19・第26巡にユーザー確定）。
以前は曲線が 8 種類バラバラに散っていて、画面ごとに手ざわりが違った。

考え方 … **初速を高く、終点へ向けて長く滑らかに収束させる（非対称な減速）**。
対称な ease-in-out は使わない（動き出しと止まりに機械的な硬さが出る）。

| 名前 | 値 | 何に使うか |
|---|---|---|
| `--ease-settle` | `cubic-bezier(0.16, 1, 0.3, 1)` | 主役。定位置への吸着 |
| `--ease-sheet` | `cubic-bezier(0.32, 0.72, 0, 1)` | 面が出入りする（iOS のシート）。**地色もこれ** |
| `--ease-press` | `cubic-bezier(0.4, 0, 1, 1)` | 押し込み。速く沈む |
| `--ease-exit` | `cubic-bezier(0.4, 0, 0.2, 1)` | 去る |

| 名前 | 値 | 何に使うか |
|---|---|---|
| `--t-press` | 90ms | 押した瞬間（指の反応は 0.1s 以内） |
| `--t-in` | 700ms | 大きな面が開く |
| `--t-out` | **600ms** | 閉じる（2026-08-23・第33巡にユーザー確定。第27巡の 350ms を戻した） |
| `--t-item` | 420ms | 中の要素ひとつ |
| `--t-step` | 50ms | 時間差（視線誘導） |

JS 側は `lib/motion.ts` が同じ数字を**秒**で持つ（`T_IN` = 0.7 など）。
**CSS と JS で数字がずれたら、どちらかを直すのではなく両方をここへ合わせる。**
JS のタイマー（「閉じ終わってからアンマウントする」等）は `ms(T_OUT)` のように
`lib/motion.ts` から引くこと。**数字を書き写さない** — 片方だけ変えると
閉じ切る前に消える。`BottomSheet` の閉じ待ち・`LEAVE_MS`・`POP_OUT_MS`・
`GROUND_MS`・`DIAL_OUT_MS`・`MAP_FULLSCREEN_MS`・`SLIDE_MS`・`DASH_MS` が該当。

★**環境の動き**（止まらずに回り続けるもの）は上の5つの対象外。状態の遷移では
ないので「開く/閉じる/押す」の語彙に乗らない。`--t-amb-load`(3.6s) /
`--t-amb-reel`(3.2s) / `--t-amb-tape`(260ms) / `--t-amb-blink`(1.15s) /
`--t-amb-bob`(5.4s) の5つ。**対称な `ease-in-out` を許すのはここだけ。**

曲線の例外は2つだけで、理由を CSS にその場で書いてある …
読み込み中のループ（対称な in-out。同じ形が延々と行き来するので行きと帰りの
手ざわりが違うと目に付く）と、ダイヤルを画面の外へ捨てる動き（もっと深く沈める）。
`lib/ground.ts` の `GROUND_EASE` は `--ease-sheet` と**同じ値**を文字列で持つが、
これは theme-color の補間に**数値として**必要なため（CSS 変数は JS で解けない）。

★**押した手ざわりは全アプリ共通**（`.press` クラス。第33巡に `.tc-lamp` から改名）。
**押した瞬間に `--t-press`（90ms・`--ease-press`）で `scale(0.94)` まで沈み、
離すと `--t-out` で静かに戻る。** `app/globals.css` の素の `button` にも同じ
規則を当ててあるので、`Button` へ移していないボタンも同じ手ざわりになる。

- ★★★**入力画面の出入りは「＋から広がって、＋へ戻す」**（第26巡にユーザー
  確定）。**やり方は「器を円で切り抜く」**（`clip-path: circle()`。第27巡）。

  `27px` → **器の四隅までの最大距離 × 1.08** へ広げる。閉じるときは逆。

  ★★★**Framer Motion の共有要素（`layoutId`）は撤回した**（第27巡）。

### ★★★★iOS のホーム画面アプリ「上下の帯」— **第35〜36巡で解決**

**結論だけ先に。** `apple-mobile-web-app-status-bar-style` は **`default`**。
`black-translucent` に戻さないこと。タブバーの位置は `NAV_BOTTOM_GAP` が
`env(safe-area-inset-bottom)` を**比率(2.382)で使って**吸収している
（`env(safe-area-inset-top)` ではない。理由は下の「2つの副作用」参照）。

#### 実測（実機の写真を画素で解析。すべて 390×844 の端末）

| | web ビューの高さ | 画面の下 47px | 画面の上 47px |
|---|---|---|---|
| `black-translucent` | **797**（画面 − 上のセーフエリア） | **どの要素も塗れない帯** | 中身が描かれる |
| `default` | **797**（同じ）だが**画面の下端まで**置かれる | 中身が描かれる ✓ | iOSが**固定の**白背景+黒文字（★下記） |

★★★**第37巡で訂正: `default`/`black`の上47pxは`theme-color`を見ない。**
Appleは`apple-mobile-web-app-status-bar-style`に`default`(白地に黒文字・
固定)/`black`(黒地に白文字・固定)/`black-translucent`(中身の背景色が
そのまま透ける)の3値しか公開しておらず、**`default`/`black`はどちらも
静的固定で、`theme-color`を一切読まない**(Web App Manifestの`theme_color`
もiOSでは無視される。Apple公式フォーラムでも既知の制限として言及されている)。
動的に色を追従させたい場合に使えるのは**`black-translucent`だけ**
(中身がその領域まで描かれ、そこに置いた背景色がそのまま見える)。
つまり「`default`で下の帯を消す」と「状態に応じて上の帯の色を変える」は
**両立しない**(iOSの制約であり、CSS/JSでは回避できない)。
第35巡で「入力画面を開くと上47pxも`theme-color`で暗くなるはず」として
実装した`lib/ground.ts`の`setTimeout`保険は、DOM上の`<meta name="theme-color">`
の値そのものは正しく追従させる(Android PWA・Safariのタブ色には効く)ので
無駄ではないが、**iOSのホーム画面アプリの状態バーには効かない**。
実機で「入力画面を開くと上に白い帯が残る」という報告はこれが原因
（コードの不具合ではなく、iOSの仕様上の制約）。

- `black-translucent` … 中身は y=0 から始まるのに高さが 47px 足りないので、
  **下 47px が誰も塗れない帯**になる。実測: 円の下端が **796.7pt**（どの x でも
  同じ y でまっすぐ）。★**`position: fixed` の面を伸ばしても描かれない** —
  ビューポートの外は要素では塗れない（第34巡に `--screen-h:
  calc(100% + env(safe-area-inset-top))` で試し、実機で**1pxも動かず**撤回）。
  **同じ手を二度試さないこと。**
- `default` … web ビューが**画面の下端まで**置かれる。実測（第29巡の写真）:
  最下部まで地色 `#ECECEA` で**帯が無い**。

#### `default` にすると出る2つの副作用と、その直し方

1. **タブバーが 47px 下がる**（web ビューが下へ伸びたぶん、下端に貼り付く
   ものが下がる）。実測: ピルの下端 783.0pt → 830.0pt、画面下までの余白
   60.7pt → 13.7pt でホームインジケーターに乗っていた。
   → 第35巡は `NAV_BOTTOM_GAP` に **`+ env(safe-area-inset-top)`** を
   足して戻そうとしたが、**`default` ではこの値が 0 になるらしく**
   実機で足した前後のピル位置が 0.1pt も動かなかった（第36巡に実機写真の
   画素比較で発覚）。`default` は「web ビューが物理的にステータスバーの
   下に無い」モードなので、そこに「不安全な領域」という概念自体が無い、
   という理屈で説明はつく。
   ★★**足し戻す信号が無いので、代わりに `env(safe-area-inset-bottom)` を
   比率で使う**（第36巡）。これは実機でだけ非ゼロ(34pt)になる値で、
   Chromium・検証環境では常に0なので、そこでの見た目・既存の検証は
   **今までどおり4px**のまま。実機だけ、必要な47ptぶんを足す比率(2.382)を
   掛ける（34 × 2.382 − 26 ＝ 55 ＝ 元の8px ＋ 47px）。
   ```
   export const NAV_BOTTOM_GAP =
     "max(4px, calc(env(safe-area-inset-bottom) * 2.382 - 26px))";
   ```
   ★★★**この比率は今の端末(セーフエリア下34pt)専用の逆算値。** 別の端末
   （例: 下34pt・上59ptのような機種）では比が変わるので合わなくなる。
   ずれたら「画面の数値を出す」の`safe`の値と実機の写真を見比べて、
   `目標(旧の55px相当) ÷ 実測のsafe-bottom` へこの数字を計算し直すこと。
2. **上 47px が `theme-color` の帯になる**。これは**うちの色**なので、
   地色に合っていれば見えない（`lib/ground.ts` が同期させている）。
   第29巡に「黒い帯」と報告されたのは iOS の仕様ではなく、
   **入力画面の色 `#33332E` が残っていた**もの（写真の実測で判明）。
   → 原因は `theme-color` の補間が `requestAnimationFrame` 頼みだったこと。
   **rAF は画面が隠れている間や iOS が絞っている間は止まる**ので、止まった
   ところの色で固まっていた。`GROUND_MS + 40` の `setTimeout` で
   **行き先を必ず書き込む保険**を置いた。

**検証は `scratchpad/chin35.mjs`。** メタが `default` か／`--screen-h` が
復活していないか／`lib/constants.ts` の実際の式を読んで、セーフエリア0で
4pxのまま・実機相当(下34pt)で目標55pxに一致するか／
★**rAF を殺した状態で入力画面を閉じても `theme-color` が地色へ着地するか**。

### ★構造的な約束（破ると必ず壊れる）

0. ★★★**全画面のオーバーレイは「画面いっぱいの板」を必ず1枚敷く**
   （2026-08-19・第28巡）。器（`[data-composer-shell]`）は
   **`visualViewport` の矩形**なので、**キーボードの高さぶん、画面の下に
   「器の外」が残る**。iOS のキーボードの上に出る帯（`^ v ✓` の操作バー）は
   **半透明**で、その裏に器の外が透ける — そこに後ろのアプリが居ると
   **「キーボードの後ろにアプリが見えている」**になる（実機で3度報告）。
   `pushGround(色, "overlay")` は `html` と `theme-color` を塗るが、
   **`html` はアプリのシェルの下**なので、そこには出られない。
   → `[data-composer-plate]`（`position: fixed; inset: 0; zIndex: 59`・
   **色は帯と同じ `LIFT`**）を敷き、器はその子にする。
   ★**板と器は同じ円で切り抜く**（円は板が持ち、器はその子）。第26巡に
   「板が居ると後ろが退がるのが見えない」と言って撤去したが、それは板に
   切り抜きが無かったからで、切り抜けば広がる途中も後ろがちゃんと見える。
1. ★★**シェル（`[data-app-shell]`）は絶対にスクロールさせない**
   （2026-08-19・第26巡）。`overflow: hidden` でも、ブラウザは
   「画面の外にある要素へ焦点が移った」とき**勝手にこの箱をスクロールする**
   （iOS のキーボード表示・要素の可視化）。列は3つぶん（幅の3倍）並んでいるので、
   隣の列のボタンが焦点を取った瞬間に `scrollLeft` が数百 px になり、
   **指では二度と戻せない**（スクロールバーも慣性も無い）。
   実測で `scrollLeft = 320` のまま固定され、画面全体が左へ 320px ずれた
   ＝「レイアウトが崩れたまま直らない」。`AppShell` が document の**捕捉相**で
   `scroll` を受け、シェルなら 0 へ戻す（scroll は上へ伝わらないが capture なら拾える。
   ★シェルは読み込み中には居ないので、`ref` に張ると効かない）。
2. **CSS の 3D 変形を使わない。** `perspective` / `preserve-3d` / `rotateX/Y` は
   Safari の合成で 5 回崩れた（archive: ui-binder §5 / §7.9 / §7.14、
   shell-redesign §7.32 / §7.35）。
3. **`position: fixed` は必ず `createPortal` で `document.body` 直下へ。**
   `.app-track` が `transform` を持つので、その中の fixed は画面ではなく
   トラックを基準に解決され、画面外へ飛ぶ（archive: shell-redesign §26.1）。
4. **アプリの地色を塗ってよいのは `AppColumn` だけ。** 出どころが 2 つあると
   遷移中に混ざって境目が出る（同 §51）。地色を変えるときは
   `components/AppBackdrop.tsx` の `groundOf` だけを直す。
5. **`body` に `background` を書かない。** body 直下の負の z-index にある地を
   塗りつぶす。地色は `html` にだけ書く（同 §27.1）。
6. **タブバーはフローから外す**（`position: absolute; bottom: 0`、`fixed` は
   iOS の URL バー伸縮でズレるので禁止）。本文の領域は常に画面いっぱい。
   画面の四隅まで敷きたいタブは **`.full-bleed` を付けるだけ**で、
   タブバーの高さの計算をタブ側に書かない。高さを知っているのは
   `lib/constants.ts` の `NAV_H` / `TAB_PAD_TOP` と、それを CSS 変数
   `--nav-h` / `--pad-top` として配る `AppShell` だけ（同 §50）。
7. **`document.querySelector("[data-tab-scroll-root]")` は使わない。**
   スクロールルートは 3 つ同時に存在し、先頭は必ずタスクの列。
   自分の列は `el.closest("[data-tab-scroll-root]")` で引く。
8. **共有する定数は `lib/constants.ts` へ。** `AppShell` に置くと
   `Dashboard → AppShell → Dashboard` の循環参照でビルドが落ちる。
9. ★★★★**キーボードが出る全画面の器は、`visualViewport` の矩形そのものにする。**

   ```ts
   el.style.top    = `${vv.offsetTop}px`;
   el.style.height = `${vv.height}px`;   // ★resize のときだけ書く
   ```

   そうすると帯・図形・ポップオーバー・日程シートの位置は**全部ただの
   レイアウト**になり、追従のための CSS 変数も transform も要らなくなる。

   ★★★**撤回**（2026-08-19・第24巡）: ここには第13巡から
   「一度置いたら二度と寸法を書き換えない。録音のオーバーレイ `VoiceOverlay`
   と同じ書き方にする」と書いてあった。**成り立たない類推だった** —
   `VoiceOverlay` には**入力欄が 1 つも無い**（キーボードが出ない画面）。
   滑らかなのは「書き換えないから」ではなく**追う相手が居ないから**。
   この一文が正典に載っていたせいで、以降 11 巡ぶん
   「器を動かさずに動いたことにする」代用品（`--kb` / `--vvtop` / ずれ残りの
   閉ループ / 上限）を積み上げ、そのたび実機で崩れた。詳しくは §4。

   ★**キーボードが出ない全画面**（`VoiceOverlay` など）は今までどおり
   `position: fixed; inset: 0; height: 100lvh` の置きっぱなしでよい。
   追う相手が無いのだから、書き換える理由も無い。
10. ★★**スクロールする器の中に `Press` を置かない。**
   `Press`（`components/tasks/Popover.tsx`）は iOS のフォーカス移動を止める
   ために**非 passive な `touchstart` で `preventDefault()`** している。
   **それはスクロールも打ち消す。** 時刻のダイアルの各値を `Press` にしたら
   指で回せなくなった（2026-08-17 に実機で「操作できません」と報告）。
   スクロールで選ぶものは**押せる面にしない**（`<span>` で置く）。
11. ★**題が空のタスク・候補は保存しない／読み込みで捨てる。** 「＋」は題が
   空のまま作って開くので、閉じる処理を通らずに終わる（背面へ回る・アプリを
   落とす）と残骸になり、円環に**無題の図形**として並び続ける
   （2026-08-18 に報告）。`migrate()` が読み込み時に捨て、背面での保存
   （`visibilitychange`）も題が空なら行わない。

### ★性能の作法
- **毎フレーム変わる値を React の state に入れない。** ref と、CSS カスタム
  プロパティ（`--drag` / `--dash`）への直接書き込み、canvas で扱う。
  ドラッグ中の React のレンダーは 0 回が正しい。
- **`@property` は使わない**（Safari 16.4 未満に無い）。トランジションは
  カスタムプロパティ自身ではなく、そこから `calc()` で導かれる
  transform / width / opacity の側に掛ける。
- **重いものは合成レイヤーへ上げる**（`will-change: transform`）。巨大な図形の
  隣で canvas を毎フレーム描くと、同じレイヤーを汚して図形ごと塗り直される。
- **`animation-direction: reverse` では再生し直されない。** 逆再生させたい
  ときは**別名のキーフレーム**を用意して `animation-name` ごと差し替える。
- **`animation-fill-mode`** … `both` にすると最後のコマの transform が
  残り続け、JS が書く値を上書きする。遅延の間だけ見せたいなら `backwards`。

## 4. タスクアプリ（§53 で確定）

### ★★縦の空間とカメラ（2026-08-24・第38巡にユーザー確定）

タスクアプリの画面は**ページの差し替えではない**。4つの層が**1本の縦の空間**に
積まれていて、動くのは**カメラだけ**。上から順に:

| # | 層 | 視点 | 中身 | 状態 |
|---|---|---|---|---|
| 0 | **DRIFT** | 立面 | 期限未定の候補が散らばって浮遊 | 第1段階で実装 |
| 1 | **GRAVITY** | 立面 | 確定したタスクが落ちて積まれる | 第1段階で実装 |
| 2 | **TOP VIEW** | 見下ろし | 日付の「黒い穴」が規則的に並ぶ | 第2段階 |
| 3 | **UNDERGROUND** | 断面 | その日のタスクの実務リスト（黒地） | 第2段階 |

**持ち主は `components/tasks/TaskSpace.tsx` 1つ**。層の並び（`TASK_LAYERS`）・
`--cam` の駆動・縦のドラッグ・画面に固定した `Masthead` を全部ここが持つ。
★`TASK_LAYERS` の順は `lib/apps.ts` のタブの並びと**必ず揃える**（タブバーの
印とカメラが同じ向きへ動くのはこれが揃っているから）。

#### 守ること

1. ★★**CSS の 3D 変形（`perspective` / `preserve-3d` / `rotateX` / `rotateY`）を
   使わない。** このコードベースは CSS の 3D で Safari の描画崩れを**5回**踏んで
   いる。縦の空間は **`translateY` だけ**で作る。第2段階の「真上を向く」も
   `scaleY` のすり替えで錯覚として作ること。
2. ★**指の追従で React の state を動かさない**（§14 の性能の落とし穴）。
   ハンドラは器へ `--cam` を書くだけ。タブバーの `--drag`・ダッシュボードの
   `--dash` と同じ手。
3. ★**タスクアプリの枠だけ `key` を固定し、`tab-in` を外す**（`AppShell`）。
   タブごとに作り直すと matter.js の山が毎回崩れ、カメラの行き先に何も無く
   なる。opacity のフェードもカメラのパンと二重になる。
4. ★**入力画面が開いている間はカメラを掴ませない**。オーバーレイは器の
   **内側**に出るので、素通しだとカレンダーやダイアルをなぞるたびに空間ごと
   動く。判定は入力画面が html へ立てる `[data-overlay]` を見る
   （出どころを増やさない）。**回帰の網は `scratchpad/space38.mjs` の [8]**。
5. 時間は **`--t-item` ＋ `--ease-settle`**。タブバーの印と同じ速さで動く。
   引いている間だけ `[data-drag]` で `transition` を切る。
6. 行き止まりは**抵抗**（`RUBBER 0.28`）。止めるのではなく重くする。

#### 動きの約束

- 指を**上**へ払うと空間が上へ流れ、**下の層**が出てくる（`--cam` が増える）。
- 送るのは「画面の 18%（`SNAP_RATIO`）動いた」か「0.45px/ms 以上で払った
  （`FLICK_V`）」とき。指を止めてから離したら惰性はゼロ（声のダイヤルと同じ罠）。
- ★**輪から作ったタスクは、タスクアプリを見ているときだけ GRAVITY へ降りる**
  （`AppShell` の `saveNewTask`）。他のアプリに居るときに勝手に画面を変えない。
  降りた先で `GravityTab` が画面の上端の外から落としてくる（既存の `makePiece`）。

#### DRIFT の散らし方

**ゆらいだ格子**。件数から列（1/2/3）と行を決め、マスの真ん中へ置いてから
id 由来の値でずらす。★ずらす量は**マス1つの寸法**に掛けること — 器の幅に
掛けると3列のとき器の12%（=44px）動き、右端の候補が画面の外へ出た。
ずらした後も中心±半分が器に収まるよう `clamp` する。
揺れは環境ループ `--t-amb-bob`（5.4s）で、始まりを id からずらす。

**候補の大きさは揃える**。重さ（重要度 × 切迫度）を持つのは確定してからで、
漂っているうちはまだ量られていない、という区別を形で示す。

### 寸法の対応
```
塗られる面積 = 重要度 … weightArea(小1.6/中3.6/大8.0) × 期限の倍率
  期限の倍率 … 今日・過ぎ 2.2 / 1〜2日 1.6 / 3〜7日 1.1
               8〜30日 0.7 / 31日〜 0.45 / 期日なし 0.55
  → 面積の幅 24.4:1（辺の比 4.9:1）。★大きさに効くのはこれだけ
  形ごとの塗り率(inkRatio)で外接箱を広げるので、**形が違っても同じ重要度なら
  色の量が同じ**（円/半円 0.78・三角 0.50・四角 1.00）
縦横比 … **四角だけ**題の長さのはしご 1:2 / 3:4 / 1:1 / 3:2 / 5:2 / 4:1
        円 1:1・半円 2:1・三角 1.155:1 は**必ずその比を保つ**
形     … 埋まっている側面の数（1..4）      lib/solid.ts
        題だけ=円 / ＋日付=半円 / ＋メモ=三角 / ＋持ち物=四角
        ★2 番目の面は **dueDate**（自由文の `when` は 2026-08-16 に廃止）
スラブ … 残っている手順（大きさには効かない）
色・書体 … タグ                            lib/taskTags.ts
落ちる順 … 切迫度（期日）
```
★**幅に上限を置かないこと**。以前は `LEN_MAX 4.0` で頭打ちにして余りを高さへ
回していたため、本来 2:1 の半円が **1.06:1 のドームに潰れていた**。画面に
収める役目は一括スケールが持つ。
★`sectionOutline` は**縦横とも −0.5〜0.5** に正規化。`(w, h)` を掛けた外接箱が
ちょうど `w × h` になり、「箱の面積 × 塗り率 ＝ 塗られる面積」が形によらず
成立する。その形の本来の比は `naturalRatio()` が別に持つ。

### タイトルの組み方
`layoutInShape()` が **`max(16px, 0.34 × √面積 × unit)`**（上限 64px）から始め、
折り返し、それでも入らなければ縮める（最大 3 行）。
★基準に √面積 を使うのは**縦横比に左右されないため**。

★**折り返す幅は行ごとに違う**（2026-08-16 確定）。断面のその高さでの半幅を
`halfWidthAt(sides, y)` から引き、行の**狭い方の端**で測る。矩形 1 つ
（`innerBox`）に収めていた頃は三角が外接箱の 23% しか使えず（四角は 79%）、
同じ面積でも**三角だけ文字が半分以下**になっていた。いまは 1.5 倍。
縦の置き場所も形で決める — **三角は下寄せ**（広い方へ寄せる）、他は中央。
`innerBox` はタグビュー（`fitText` で英字を図形いっぱい）だけが使う。

  html の地色が同じ色になっているので、覆わなくても継ぎ目は出ない。

  ★★★**なぜ 11 巡かかったか**（同じ轍を踏まないために全部残す）。第13巡に

  と書いた。**`VoiceOverlay` には入力欄が 1 つも無い** — キーボードが出ない

  | 代用品 | 巡 | 実機で何が起きたか |

  3 巡続いた）。器の中を `clip` にしても消えなかったのは、**送っているのが器では

  1. `document.documentElement.dataset.overlay = "1"` を立て、CSS で
     **後ろのタブの列を止める**（`[data-overlay] [data-tab-scroll-root] { overflow: hidden !important; }`）。

     その場で `preventDefault()`**。「本当に送れる箱」＝ 祖先をたどって
     `overflow-y/x: auto|scroll` かつ**実際にはみ出している**もの
     （行の並び・カレンダー・ダイアル・タイムライン）。二本指も止める。

  流れ続ける。カレンダーの横払いも時刻のダイアルも生きたままである（実測済み）。
- ★**器の中に「はみ出し」を作らないこと**（2026-08-18）。

  そこを送ってくるし、右端にスクロールバーも出す。**`overflow: clip`** は
  箱そのものを作らないので、構造的に送れない。

  器より大きいものを置く面も `clip`。行の並びだけは `auto`（手順は増える）だが、
  `scrollbar-width: none` でバーは出さない。

  （`scrollHeight` の大小ではない — `clip` ははみ出しても送れない）。

### 一括スケールと間引き（`pileOf`）
「小さすぎるものは出さない」と「混雑しても大きい図形を残す」を同じ仕組みで解く。
面積の降順に並べ、先頭 N 件だけで縮尺を出しながら N を増やし、次のどちらかで止める。

- **これ以上入れると `SCALE_MIN 0.70` より縮めないと収まらない**
  → 縮めるのではなく**間引く**
- **その 1 件自身が `CULL_PX 30` を割る** → どうせ読めないので入れない

★最後に、**いちばん大きい 1 枚が画面に収まる**ところまで縮める
（幅 `FIT_W 0.86` / 高さ `FIT_H 0.62`）。面積の合計だけで決めていた頃は、
数件しか無いと縮尺が上限に張り付き、重要度の高い 1 枚が画面より大きくなって
壁に挟まったまま宙に浮いていた。渡す高さからは**見出しのぶん**
（`MASTHEAD_H 108`）も引く — 引かないと山が見出しに重なる。

含める数を増やすほど縮尺は単調に下がるので、この走査は一意に決まる。
実測: 4 件→4 件表示・最大 278px / 16 件→16 件・146px / 40 件→10 件・137px /
80 件→9 件・137px。★**間引かれたタスクは画面から触れなくなる**（ユーザー了承済み）。

LOD は代表寸法 `s = √面積 × unit` で決める。`>=48` 3 行 / `30〜48` 1 行 /
`<30` 文字なし / `<16` 切れ目なし。

### ★★書体が揃ったときの捨て方（2026-08-18・第17巡）

**`onFontsReady` は「購読しただけ」で呼び返してはいけない。**
以前は `document.fonts.ready.then(cb)` を置いていた。これは**もう揃っていれば
即座に解決する**ので、`SolidCanvas` が 1 枚マウントされるたびにコールバックが
走っていた。そのコールバックは `clearSolidBitmaps()` ＝ **みんなで使っている
焼き上がりの全消し**なので、

- 入力画面を開くだけで**山の絵が全部消え**、閉じたあとに焼き直されて
  **文字が点滅**する（実機で報告。Chromium でも閉じた 350ms 後に
  色数 241→51 と再現できた）。
- タブを行き来するたびに焼き直しが走る ＝「全体的に処理が間に合っていない」。

揃っていない面は `requestGlyphs` の `load().then` が拾うので、これは要らない。
`loadingdone` の安全網も、**面の顔ぶれ（`document.fonts.check` の並び）が実際に
変わったときだけ**動かす。

### ★守ること
- **`ctx.font` は CSS 変数を解決できない。** `var(--font-…)` を含む文字列を
  代入すると黙って失敗し、既定の 10px サンセリフのままになる。
  `resolveFamily()` で `getComputedStyle(document.documentElement)` から
  一度だけ解決する。
- **文字はグリフのアトラス経由で描く。** 和文の Web フォントは unicode-range で
  数百の `@font-face` に分割されており、`fillText`/`measureText` は
  **(書体, 文字) の組ごとに初回 5〜10ms** かかる。素直に描くと落下中に
  `fillText` だけで 2.4 秒。同じ (書体, 文字, 色) は一度だけ焼いて
  `drawImage` で使い回し、**1 フレームに数枚だけ**焼く（`GLYPH_BUDGET = 4`）。
  ★1 枚では足りない — 16 個 × 8 文字 ≒ 130 枚を 1 枚/フレームで焼くと 2 秒以上
  かかり、そのあいだに断片が届いて振り出しに戻るため文字が一度も出なかった。
  ★**焼く大きさをバケツ `[32, 64, 96]` に丸める**。常に 128px で焼いて
  13px へ縮めていた頃は 9.5 倍の縮小になり、`drawImage` が標本を落として
  文字がジャギーになっていた。ただし**段を増やしすぎない** — 同じ文字が段の
  数だけ焼き直されるので、7 段にしたら落下中の `fillText` が 868ms へ増えた。
  図形の絵は `bakeDpr = min(dpr, 1.5)` で焼く（1.25 では画面へ 1.6 倍に
  拡大されて滲み、2.0 では画素が 2.56 倍になって 800ms 級のひっかかりが出た）。
- **和文の送り幅は測らない。** 全角（かな・漢字・全角記号）の `advance` は
  必ず 1em なので、`measureText` を飛ばす。題の文字数ぶんが 1 フレームに
  まとまって走ると 666ms 止まった。
- **欧文（タグの英字）の送り幅は暇な時間に先に測っておく**
  （`primeAdvances` を `requestIdleCallback` で数組ずつ）。BOTTOM へ
  切り替えた瞬間に 5 書体ぶんがまとめて走ると 328ms 止まる。
- 実測（4× CPU 絞り・本番ビルド、16 個）… 落下 合計 1300ms 前後 / 最大 190ms、
  ビュー切替 最大 130ms、積み終わったあとと横スワイプは 0ms。
- **和文の Google フォントは 1 書体につき 1 ウェイトまで。** 3 書体 × 3
  ウェイトで turbopack が `Module not found` を出す。太字・斜体はブラウザの
  合成に任せる（`app/layout.tsx`）。
- **`document.fonts.load()` の Promise は必ず `.catch()` する**
  （unhandled rejection で pageerror が飛ぶ）。書体が届いたら
  `onFontsReady` でアトラスとビットマップを捨てて描き直す。
- ★★**「書体が届くまで文字を描かない」は必ず時間で門を開けること**
  （2026-08-17。実機で「文字が表示されない・アプリ全体が不安定」）。
  `textDrawable(face, text)` は「届いた **または** 頼んでから 600ms 過ぎた」で真。
  待つだけにしていたら、次の 3 つのどれか 1 つで**文字が永久に出なかった**:
  - **WebKit の `document.fonts.check()` が偽を返し続ける**
    （unicode-range で分割された和文の family に対し Blink と挙動が違う）。
    → `computeTextPlan` が `null` を返し、その `null` が `planCache` に載る。
  - **判定結果のキャッシュに「取りに行く前の偽」が焼き付く** →
    届いたあとの再判定も偽を読むので、**焼き直しの通知が一度も飛ばない**。
    取りに行く前後の比較は**キャッシュを通さない生の `check()`** で行う。
  - **`loadingdone` のたびにアトラスを全消し**していた → 断片は 100 以上
    あるので、1 フレーム数枚しか焼けないアトラスが焼き切る前に振り出しへ
    戻る。`pendingBake` が立ち続けて **rAF も止まらない**。
  → 捨てるのは **400ms にまとめて、届いた面のぶんだけ**（`dropFace`）。
  安全網の `loadingdone` は **`document.fonts.status === "loaded"`（＝読み込みが
  落ち着いた）ときだけ**動かす。
  ★**「何も出ない」より「一度 fallback で出てから本物に差し替わる」**方がまし。
  検証は `document.fonts.check` を偽で固定して実機を再現し、山の画素の色数を
  数える（修正前 125 色・文字の画素 19 → 修正後 336 色・6779）。
- **当たり判定は描く形そのもの**。断面の多角形
  （`Bodies.fromVertices`）。長方形で当てていた頃は、形の周りの見えない余白
  どうしがぶつかって図形が宙に浮いて見えた。**丸だけは `Bodies.circle`**
  （36角形は衝突判定が重く、転がりもカクつく）。物理の頂点は 12 点まで
  間引く — 半円の 37 点を 16 個ぶんまとめて `fromVertices` に通すと、
  凸包の計算で 400ms 級のひっかかりが出た。
  ★`fromVertices` は**重心**を `body.position` に置くが、絵は図形の原点を
  中心に焼いてある。三角形のように両者がずれる形では、そのズレ（`ox`/`oy`）を
  描画側で戻すこと。戻さないと絵と当たり判定が食い違う。
- 手順を済ませて形が変わったときは、位置と速度を引き継いで body を差し替える
  （ビュー切替は全部作り直すので、こちらは編集のときだけ）。
- **落下位置の hash に連番をそのまま使わない。** `"t1","t2",…` は hash も
  連番になり、全部が同じ x に落ちて 1 本の塔になる。黄金比の定数を掛けて混ぜる。
- ★★**`document.fonts` には「先頭の family だけ」を渡す。**
  `next/font` は `--font-dela-gothic-one` を
  `"Dela Gothic One", "Dela Gothic One Fallback"` に展開する。後ろの
  *Fallback* は**端末のフォントに寸法だけ合わせた `local()`** なので
  **常に読み込み済み**。スタックごと `load()` に渡すと、それで即 resolve して
  **本物の断片を取りに行かない**。実測（2026-08-17）:
  スタックで load → 塗り率 **17%**（素のサンセリフ）のまま /
  先頭だけで load → **37.9%**（本物の Dela）。
  ★これを間違えていたため、**和文のディスプレイ書体は一度も表示されて
  いなかった**（それまでの「書体の違い」は太さと斜体の合成だけ。だから
  「赤と黄が同じに見える」ことになった）。`primaryFamily()` / `checkFace()` /
  `textDrawable()` / `ensureGlyphs()` が唯一の窓口。`ctx.font` の方はスタックのままでよい
  （届いていない間は fallback で描くため）。
- **書体は待たずに「取りに行く」。** 断片の取得が始まるのは**その文字を
  初めて描いた瞬間**なので、`document.fonts.ready` も `loadingdone` も
  「鳴る前に焼いてしまった絵」は救えない。焼く直前に `ensureGlyphs()` を
  呼び、**まだ使えないときだけ**、届いた時点でアトラスと割り付けを捨てて
  購読者へ知らせる。
- ★**書体が届くまで文字を描かない**（`computeTextPlan` が `textDrawable` で
  門番をする）。グリフは 1 フレームに数枚しか焼かない（落下のガクつき対策）
  ので、焼いている途中で書体が届くと**前半 fallback・後半 本物**の絵になる
  （実機で「1 つの図形に 2 書体」として報告された）。
  **fallback で焼かなければ混ざった絵は存在し得ない。**
  ★★ただし**門は必ず時間で開ける**（600ms）。理由と再現手順は上の
  「性能の作法」の節に書いた — 待つだけにしたら実機で文字が永久に出なかった。
- **入力画面のプレビューは倍率を固定する**（`SolidCanvas` の `unit`）。
  器いっぱいに拡大すると、重要度や期限を変えても絵の大きさが変わらず
  「大きさ ＝ 重要度」が読めなくなる。

## 5. 声の記録（Journal）

`components/VoiceStudio.tsx` 1 つで完結。ジャーナルの RECORD タブと、
タブバー右端の録音ボタンから開くオーバーレイが**同じ部品**を使う。

- 画面下部に**画面をはみ出す巨大な円が 2 つ**（カセットのリールの抽象）。
  直径＝器の幅の 1.30、中心 x = ∓0.30、中心 y は
  「タイトルの下端とタブバーの上端の中間」。
- 操作は**トグル**。REC キーか**円の上**をタップで開始／停止。それ以外の
  余白は反応しない。止めても送らず `review` で待つ。
- 停止後、同じ 2 つの円が**トリミングのダイヤル**になる。左＝始点、右＝終点。
  1 回転で全体の 50%。惰性つき（指を止めてから離したら速さは 0）。
- 物理キー 4 つ（丸・直径 42・出っ張り 4）… `REC` / `PAUSE` / `SEND` / `CANCEL`。
  `MediaRecorder.pause()/resume()` で続きから録れる。止まっている間は数えない。
- 実際に切る … `lib/audioTrim.ts`。`decodeAudioData` で波形に戻し、必要な範囲
  だけを 16bit PCM モノラル WAV へ組み直す。デコードできない端末では
  **元の音声をそのまま送る**。
- 文字起こし … `app/api/transcribe/route.ts`。`OPENAI_API_KEY` があれば
  Whisper 系、無ければ `GEMINI_API_KEY` で Gemini の音声入力。結果は
  `AppState.voiceNotes` と my-brain の `days/YYYY-MM/voice.md` へ。

### ★守ること
- **マイクは必ず解放する。** 生ストリームを自分で持ち（`streamRef`）、
  二重起動を防ぎ（`startingRef`）、`onstop` が来なかったときの保険
  （1500ms）も置く。どの終わり方でも `releaseStream()` を通す。
- **波形の棒は「本数 × 等間隔」で置かない。** 測定の `setInterval` は
  45ms ちょうどでは来ないので、増えるたびに 1 本ぶん飛ぶ。測った瞬間の
  経過時刻を記録し、**時刻から位置を出す**。
- **`navigator.vibrate` は iOS Safari に無い。** 手応えはハプティクスでは
  返せないので、掴んだ合図は `transform: scale()` の視覚で出す
  （**塗りの色は変えない**。巨大な面が十数フレーム塗り直される）。
- **入場アニメーションの再生の合図は AppShell から prop で渡す。**
  IntersectionObserver で見え方から推測すると実機で閾値に達せず、
  円が出てこない。

## 6. ブリーフ生成（運用ポリシー）

パイプラインの詳細は `SYSTEM-DESIGN.md`、実装は `lib/briefPipeline.ts`。
**ここに書くのはユーザーが明言した「これを正とする」運用だけ。**

### 情報源とカードの関係（§8.15）
- **情報源の本体は、雑多で高品質なネットマガジン**（カルチャー・技術・生活・
  音楽・ファッション）。淘汰・入れ替えでゆっくり好みに追従する。
  ここから、興味に合致する＝**提案カード**、合致しない新着＝**情報カード**。
  **カルチャー誌の「記事」を第一級で扱う**のが中核の体験。
- 展覧会・映画・イベントの集約サイトは、**情報が集約されているから固定に
  しているだけ**で、他の情報源と完全に平等。**抽出・分類・枚数配分のどこにも
  「展覧会を優先する」構造を作らない。**

### 更新と枚数（§8.18）
- **1 日 2 回**（朝 06:30 JST / 夕 13:30 JST の Cron）、各 **10 枚くらい**。
  事前に生成してストックし、アプリを開いたら即出る。
- 未消化カードの保持は **3 日**。ストック上限 **40 枚**（超えている間は追加生成
  しない）。キーは**日付だけ**（`YYYY-MM-DD`。朝刊／夕刊の概念は撤去済みで、
  Cron は置き換えではなく **id 重複を除いた積み増し**）。
- **「今すぐ生成」はテスト用**。完成時に削除する。

### 構造（§8.19）
2 層＋コード検証。**AI に「落とす」判断をさせない**ので、候補が 1 件でもあれば
構造的に 0 枚にならない。
- 層 1（サイトごと・並列）… 抽出と関連度付け（0〜100）を 1 回で。
- 選抜（コードのみ）… 出典 URL の実在検証・終了済み／圏外／重複の除外の後、
  関連度順にサイト横断ラウンドロビン。`>=80` ストレート／`50〜79` 派生／
  `<50` 情報カード。**trigger もコードが関連度から決める。**
- 層 2 … 採用分だけ個別ページを取得して本文を詳細化。

### ★絶対の原則
- **LLM に URL を抽出させない。** 抽出のつもりが推測創作になる（§8.12.5 で
  実在しない展覧会を丸ごと捏造した）。URL は必ず**コードが実 HTML／Markdown
  から機械的に取り出した集合**で照合し、外れたカードは機械的に捨てる。
- **retrieval は Jina Reader 経由**（`r.jina.ai`）。生 fetch は IP ブロック・
  JS 描画・正規表現依存で繰り返し失敗した（§8.12.13）。
- **機械的な処理はコードで、LLM に投機させない**（日付の期限切れ判定、距離の
  計算、枚数の配分、重複の統合）。

### 情報源の淘汰（§8.20）
個別のスキップは記録しないので、打率は**集計値として別に持つ**。
`lib/sourceStats.ts` が `generatedDecks` と `briefs` からドメインごとの
`shown / kept / flagged` を積算し（`countedIds` で二重計上を防ぐ）、
my-brain の `sources/stats.md` へ書く。Cowork の発掘タスクはこの数字だけを
見て並べ替え・淘汰する。

## 8. 検証ワークフロー

```bash

#   next/font/google はビルド時に fonts.googleapis.com を取りにいくが、
#   Node の fetch は環境のプロキシを勝手には通らない。付けないと

#   付け直してもう一度走らせること（`npm run build` も同じ）。
NODE_OPTIONS="--use-env-proxy" setsid npm run dev > scratchpad/dev.log 2>&1 &
# 性能の計測は必ず本番ビルドで（dev は桁違いに遅く数字が無意味）:

# ★Playwright は入っていないので入れる（`--no-save` で package.json を汚さない）
npm i -D playwright@1.56.1 --no-save
#   import { chromium } from "playwright";
#   chromium.launch({ executablePath: "/opt/pw-browsers/chromium-1194/chrome-linux/chrome" })
#   ★`/opt/pw-browsers/chromium` は実体ではない。`chromium-<版>/chrome-linux/chrome`。
```

### ★★入力画面は「4 通りの型」で見る（第18巡・`scratchpad/geo4.mjs`）

**これまでの検証には「ずれた場合」が無かった。だから 3 巡続けて同じ所を壊した。**
キーボードの出方は端末で 3 通りあり、さらに**見えている矩形がずれる**型がある。

| 型 | 作り方 |
|---|---|
| A キーボード無し | そのまま |
| B レイアウトごと縮む | `setViewportSize` で縮める |
| C `visualViewport` だけ縮む | `vv.height` だけ差し替える |
| **D ずれる** | `vv.height` を縮め、さらに `vv.offsetTop` を 156 にする |

**どの型でも次の 3 つが成り立つこと**（入力画面の不変条件・第24巡で改訂）:

1. **器の上端 == 見えている上端**（`vv.offsetTop`）
2. **器の下端 == 見えている下端**（`vv.offsetTop + vv.height`）
3. 上のバーの上端が見えている上端のすぐ下（＋セーフエリア上）
4. **帯の下端 == 見えている下端**
5. 図形の中心が見えている範囲の中
6. 日程シートの下端 == 見えている下端

★★★**期待値は「見えている矩形」だけで書く**（第24巡）。第18〜23巡の判定は
`--kb` や `--vvtop` という**代用品の値**を見ていたので、代用品が壊れていても
「正しい」と判定できてしまった。実機の崩れを 14 巡ぶん通した直接の原因。
**位置だけを見ること。**

あわせて **D の型で入力画面が閉じないこと**。

### ★★★実機の崩れを Chromium で再現する（第24巡・`rect24.mjs`）

**ここがこのプロジェクトで一番外し続けた場所**（14巡）。原因のひとつは
**自動検証がその崩れを一度も再現できていなかった**こと — Chromium は素で
`visualViewport.offsetTop` に 0 しか返さず、`height` も縮まない。

★**getter を差し替える**と、実機と同じ条件になる:

```js
Object.defineProperty(vv, "height",    { configurable: true, get: () => 見えている高さ });
Object.defineProperty(vv, "offsetTop", { configurable: true, get: () => 180 });
vv.dispatchEvent(new Event("resize"));
```

`rect24.mjs` は 4 通りの型（無し／レイアウトごと縮む／`vv.height` だけ縮む／
**ずれる**）で上の 6 つを見て、あわせて ①ポップオーバーを開けて矩形を揺らしても
上のバーと帯が動かないか ②日程シートの下端が画面の外へ出ないか
③キーボードを閉じたら閉じる／焦点が外れただけでは閉じないか
④CPU 6× 絞りで＋を押しても即閉じないか。

★**直す前に、いまのコードでそれが落ちることを先に確かめる。**落ちなければ
見立ての方が違う。

### ★性能の測り方
`PerformanceObserver` で `longtask` を拾い、CDP の
`Emulation.setCPUThrottlingRate { rate: 4 }` を掛けて**本番ビルド**で測る。
- 比べてよいのは「**同じスクリプトで、変更あり／なしを続けて測った値**」だけ。
  スクリプトが変われば数字の意味も変わるので、過去の記録と比較しない。
- 重いときは Paint を疑う前に、まず **Layout かどうか**を CDP の `Tracing`
  （`devtools.timeline`）で確定させる。`textContent` への代入は**値が同じでも**
  レイアウトを汚し、`font-size` の遷移は遷移中ずっとレイアウトを走らせる。
- 「1 つずつ外して数字が動かない」ときは、**原因が 1 つではない**可能性を先に疑う。
